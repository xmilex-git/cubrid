## 1. Trigger Conditions — when a tuple becomes an overflow tuple

**Core threshold** (query_list.h:222):
```c
#define QFILE_MAX_TUPLE_SIZE_IN_PAGE  (DB_PAGESIZE - QFILE_PAGE_HEADER_SIZE)
```
`QFILE_PAGE_HEADER_SIZE` is a fixed **32 bytes** (query_list.h:52). `DB_PAGESIZE` (`storage_common.h:101`, aliasing `db_User_page_size`) is a **runtime** value, not a compile constant: `db_User_page_size = db_Io_page_size - RESERVED_SIZE_IN_PAGE` (storage_common.c:48,74), so the exact byte threshold is a deployment-time quantity, but the *formula* `DB_PAGESIZE - 32` is fixed and verified at this SHA. `qfile_Max_tuple_page_size` (list_file.c:209, a `static int`) is initialized to this macro at qfile module init (list_file.c:1166) and used everywhere at runtime instead of the raw macro.

**Enforcement point** — `qfile_add_tuple_to_list` (list_file.c:1613-1672), the primary tuple-append entry point used by essentially every list-file writer (`qfile_combine_two_list` list_file.c:2632, `qfile_union_list` list_file.c:2647/2650, act_left/act_right dispatch list_file.c:2787/2794-2795, generic sort-merge output list_file.c:4144/4212, `qfile_copy_tuple` list_file.c:3326):
```c
tuple_length = QFILE_GET_TUPLE_LENGTH (tuple);                              // list_file.c:1628
...
tuple_page_size = MIN (tuple_length, qfile_Max_tuple_page_size);            // list_file.c:1636
memcpy (page_p, tuple, tuple_page_size);                                    // list_file.c:1638
...
for (offset = tuple_page_size, tuple_p = (char *) tuple + offset; offset < tuple_length;
     offset += tuple_page_size, tuple_p += tuple_page_size)                 // list_file.c:1643-1644
  {
    new_page_p = qfile_allocate_new_ovf_page (thread_p, list_id_p, cur_page_p, prev_page_p,
                                               tuple_length, offset, &tuple_page_size);  // list_file.c:1646-1648
    ...
  }
```
**Exact trigger**: the loop body executes — i.e. at least one overflow page is allocated — **iff `tuple_length > qfile_Max_tuple_page_size` (= `DB_PAGESIZE - 32`)**. If `tuple_length <= qfile_Max_tuple_page_size`, `tuple_page_size == tuple_length`, `offset` starts already `>= tuple_length`, and the loop body never runs: the tuple lives entirely on one page, no overflow. The same `MIN(tuple_length, qfile_Max_tuple_page_size)` head-chunk pattern recurs at list_file.c:1636, 1869 (asserted `<=` for a fast-path that structurally excludes overflow), 2163, 2166, 6917 — all downstream of the same threshold, none introduce a second independent trigger condition.

**Corollary — overflow tuples always start on a fresh page.** `qfile_allocate_new_page_if_need` (list_file.c:1564-1592) is called with the **full, untruncated** `tuple_length` (list_file.c:1630), and internally:
```c
if (qfile_is_first_tuple (list_id_p) || qfile_is_last_page_full (list_id_p, tuple_length, is_ovf_page))  // list_file.c:1569
```
`qfile_is_last_page_full` (list_file.c:1439-1453) returns `(tuple_length + list_id_p->last_offset) > DB_PAGESIZE`. Since `tuple_length > DB_PAGESIZE - 32` for any overflow-triggering tuple, this is true for any non-trivial `last_offset`, forcing `qfile_allocate_new_page` (list_file.c:1468-1526) to hand out a brand-new page before the head chunk is written. Overflow tuples therefore never share their head page with a preceding tuple's tail.

**Write-time serialization order (upstream of list_file.c).** `qfile_add_tuple_to_list` receives an *already fully serialized* `QFILE_TUPLE` byte buffer and only reads its length header; the buffer's byte layout (today: legacy 8B tuple-length prefix + per-value 8B flag/length headers) is produced by upstream tuple builders that finalize the length **after** writing every value, then patch it in:
```c
/* now that we know the tuple size, set it. */
QFILE_PUT_TUPLE_LENGTH (tuple_record_p->tpl, tlen);         // query_opfunc.c:502-503 (also :568-569)
```
and equivalently at list_file.c:1692/1713/1749/1802/1939/2010/2094/2479/3284/3711, query_executor.c:5976/6027, query_hash_join.c:4233. **This two-phase construct-then-patch pattern is the mechanism by which "is this tuple oversized" becomes knowable** — the byte length isn't known until the tuple is fully materialized. This matters directly for §3.3 below.

## 2. Handling — write path → read/scan path trace

### 2.1 Write path: allocation of overflow pages

`qfile_allocate_new_ovf_page` (list_file.c:1528-1561), called only from the overflow loop above (list_file.c:1646-1648) and from `qfile_add_overflow_tuple_to_list` (list_file.c:2185-2187, the page-clone variant used by the sort/merge machinery — see its doc comment at list_file.c:2126-2139: "specific routine of `qfile_add_tuple_to_list` used by list file sorting mechanism"):
```c
new_page_p = qmgr_get_new_page (...)                                    // list_file.c:1537
QFILE_PUT_NEXT_VPID_NULL (new_page_p);                                  // list_file.c:1545
QFILE_PUT_TUPLE_COUNT (new_page_p, QFILE_OVERFLOW_TUPLE_COUNT_FLAG);    // list_file.c:1546  <-- the audited flag
QFILE_PUT_OVERFLOW_TUPLE_PAGE_SIZE (new_page_p, *tuple_page_size_p);    // list_file.c:1547
QFILE_PUT_OVERFLOW_VPID_NULL (new_page_p);                              // list_file.c:1548
QFILE_PUT_OVERFLOW_VPID (prev_page_p, &new_vpid);                       // list_file.c:1554 (chain link)
```
Two structurally distinct link fields exist per page (query_list.h:75/84-85, offsets differ — verified distinct macros `QFILE_GET_PREV/NEXT_PAGE_ID` vs `QFILE_GET_OVERFLOW_PAGE_ID`):
- **Regular page chain** (`QFILE_PUT_NEXT_VPID`/`QFILE_GET_NEXT_VPID`, `QFILE_GET_PREV_VPID`): links successive *list pages*, i.e. skips straight from an overflow tuple's head page to the next *unrelated* tuple's page. This chain is only rewritten by `qfile_allocate_new_page` (list_file.c:1507: `QFILE_PUT_NEXT_VPID (page_p, &new_vpid)`), which is **not** called for overflow continuation pages.
- **Overflow chain** (`QFILE_PUT_OVERFLOW_VPID`/`QFILE_GET_OVERFLOW_VPID`, field distinct from the regular chain, query_list.h:84-85/170-218): links the head page → 2nd continuation page → … → last continuation page (`QFILE_PUT_OVERFLOW_VPID_NULL` terminates it, list_file.c:1548/1665/2207/3071).

So an overflow tuple's continuation pages are **invisible to ordinary forward/backward page traversal** and reachable only by explicitly walking `QFILE_GET_OVERFLOW_VPID` starting from the head page. `QFILE_OVERFLOW_TUPLE_COUNT_FLAG = -2` (query_list.h:280) is written **only onto continuation pages**, never onto the head page (whose own tuple count is incremented normally by `qfile_allocate_new_page_if_need`, list_file.c:1584). It is a *page-role* marker ("this page is a continuation page, not a page of independent tuples"), while `QFILE_GET_OVERFLOW_PAGE_ID(head_page) != NULL_PAGEID` is a *head-tuple* marker ("the tuple that starts here continues elsewhere"). Both are checked, at different call sites, depending on whether the caller is inspecting a page opaquely (sector/page iteration) or a tuple already positioned at its head — see §3.2.

### 2.2 Read / scan path: peek vs. forced copy

The scan-side detection and dispatch is `qfile_retrieve_tuple` (list_file.c:5304-5350), invoked by every list-file scan-next/prev/jump caller:
```c
static SCAN_CODE
qfile_retrieve_tuple (THREAD_ENTRY * thread_p, QFILE_LIST_SCAN_ID * scan_id_p,
                      QFILE_TUPLE_RECORD * tuple_record_p, int peek)
{
  if (QFILE_GET_OVERFLOW_PAGE_ID (scan_id_p->curr_pgptr) == NULL_PAGEID)          // list_file.c:5310
    {
      if (peek) { tuple_record_p->tpl = scan_id_p->curr_tpl; }                   // list_file.c:5312-5315 (zero-copy)
      else      { ... memcpy (tuple_record_p->tpl, scan_id_p->curr_tpl, tuple_size); }  // list_file.c:5318-5327
    }
  else
    {
      /* tuple has overflow pages */
      if (peek)
        {
          if (qfile_get_tuple_from_current_list (thread_p, scan_id_p, &scan_id_p->tplrec) != NO_ERROR) // 5334
            return S_ERROR;
          tuple_record_p->tpl = scan_id_p->tplrec.tpl;                            // list_file.c:5338 <-- uses tplrec
        }
      else
        {
          if (qfile_get_tuple_from_current_list (thread_p, scan_id_p, tuple_record_p) != NO_ERROR)      // 5342
            return S_ERROR;
        }
    }
  return S_SUCCESS;
}
```
**This is the crux finding**: in the non-overflow branch, `peek=true` gives the caller a raw pointer into the live page (`scan_id_p->curr_tpl`, zero-copy). In the overflow branch, **`peek` has no effect on whether a copy happens** — both sub-branches call `qfile_get_tuple_from_current_list` (list_file.c:5071-5082), which calls `qfile_get_tuple` (list_file.c:4972-4995):
```c
if (QFILE_GET_OVERFLOW_PAGE_ID (first_page_p) != NULL_PAGEID)                   // list_file.c:4978
  return qfile_assemble_overflow_tuple (thread_p, first_page_p, dest_tplrec, list_id_p->tfile_vfid); // 4980
```
which reassembles the whole tuple via `memcpy` per continuation page (list_file.c:5008-5060, copy loop at 5030) into a **caller-owned scratch buffer**, growing it via `qfile_reallocate_tuple` if needed (list_file.c:5321/3319-ish pattern; buffer growth entry referenced at list_file.c:5319-5325 for the analogous non-peek path). **Overflow tuples are therefore always force-copied on read, regardless of the caller's peek/copy intent** — the only difference `peek` makes is *which* buffer receives the copy: the scan's own persistent `tplrec` (query_list.h:514, `QFILE_LIST_SCAN_ID.tplrec`, comment: "used for overflow tuple peeking") when peeking, or the caller-supplied `tuple_record_p` when copying.

**`tplrec`'s role, precisely**: it is a per-scan scratch buffer (one `QFILE_TUPLE_RECORD` — `{tpl, size}`, query_list.h:290-294) embedded directly in `QFILE_LIST_SCAN_ID` (query_list.h:503-516) that exists *solely* so that "peek" mode has somewhere to materialize an overflow tuple's reassembled bytes without forcing the *caller* to own/free a buffer. It is allocated/grown lazily by `qfile_reallocate_tuple` and is reused (realloc'd in place, not freed-and-reallocated) across successive overflow tuples encountered by the same scan — meaning **its contents/address can change on every subsequent overflow tuple the same scan visits**, independent of any page-transition or next/jump bump point. This is a lifetime detail not covered by the plan's existing bump-point enumeration (ralplan.md §3 P1.1(b)); see §3.3.

**Parallel/px_scan mirrors the identical detection+reassembly pattern** at `px_scan_slot_iterator_list.cpp:113-137` (`slot_iterator_list::next_qualified_slot_with_peek`):
```c
bool has_overflow_page = (QFILE_GET_OVERFLOW_PAGE_ID (m_curr_pgptr) != NULL_PAGEID);   // :116
...
if (has_overflow_page)
  {
    /* qfile_get_tuple delegates to qfile_assemble_overflow_tuple ... */
    qfile_assemble_overflow_tuple (thread_p, m_curr_pgptr, &m_tplrec, m_list_id->tfile_vfid);  // :126
    tpl = m_tplrec.tpl;
  }
else { tpl = m_curr_tpl; }
...
fetch_val_list (thread_p, m_scan_pred.regu_list, m_vd, nullptr, nullptr, tpl, PEEK)   // :142 — PEEK unconditionally
```
Note that `fetch_val_list` is called with `PEEK` **unconditionally** even in the overflow branch, where `tpl` actually points into the reassembled `m_tplrec` scratch buffer rather than live page memory — architecturally consistent with `qfile_retrieve_tuple`'s peek-into-tplrec behavior above, and a second, independent confirmation that "peek" for overflow tuples means "peek into an owned reassembly buffer," not "peek into the page."

**`px_scan_input_handler_list.cpp:144-148`** independently uses `QFILE_GET_TUPLE_COUNT(page) == QFILE_OVERFLOW_TUPLE_COUNT_FLAG` (the page-role signal, not the head-tuple signal) to *skip* raw continuation pages during page-level distribution: "Overflow continuations: the start-page owner walks the chain via `qfile_assemble_overflow_tuple`" — i.e. parallel page-sector distribution must not hand a bare continuation page to a worker as if it were an independent list page.

### 2.3 Interaction with jump / backward scan

`qfile_scan_next` (list_file.c:5095-5187) and `qfile_scan_prev` (list_file.c:5198-...) both navigate exclusively via the **regular** page chain (`QFILE_GET_NEXT_VPID`/`qfile_has_next_page` at list_file.c:5141-5143/6970-6973; `QFILE_GET_PREV_PAGE_ID`/`QFILE_GET_PREV_VPID` at list_file.c:5217-5219) and via intra-page tuple-length bookkeeping (`QFILE_GET_TUPLE_LENGTH`/`QFILE_GET_PREV_TUPLE_LENGTH` at list_file.c:5136-5137/5212-5213). **Overflow continuation pages are structurally unreachable from this traversal** — they hang off the head page's separate `OVERFLOW_VPID` field (§2.1), so forward/backward per-page stepping always lands on a tuple's *head* page, never mid-chain. `qfile_jump_scan_tuple_position` (list_file.c:5366+) is likewise VPID/offset-based (positions `curr_pgptr`/`curr_offset`/`curr_tpl` at list_file.c:5395-5396 etc.) and re-derives overflow status the normal way (via a subsequent `qfile_retrieve_tuple` call) once positioned — jump introduces no new detection path. **Practical consequence**: the overflow/legacy branch is a per-position concern resolved at the moment a tuple is retrieved, completely orthogonal to how the scan got to that position (next, prev, or jump); no additional interaction/gotcha exists for jump/backward scan beyond "detect at retrieval time" (§3.2).

**Client-side duplicate implementation.** `cursor.c` — compiled into the CS client library (`cs/CMakeLists.txt:263`: `${QUERY_DIR}/cursor.c`) — contains its own, independent reassembly routine `cursor_construct_tuple_from_overflow_pages` (cursor.c:665-724), structurally identical to `qfile_assemble_overflow_tuple` but fetching pages over the network (`cursor_get_list_file_page`, cursor.c:706) instead of via `pgbuf`/`qmgr_get_old_page`:
```c
tmp_tuple_p = cursor_id_p->buffer + QFILE_PAGE_HEADER_SIZE;
tuple_length = QFILE_GET_TUPLE_LENGTH (tmp_tuple_p);                     // cursor.c:680-681
...
tuple_page_size = MIN (tuple_length - offset, QFILE_MAX_TUPLE_SIZE_IN_PAGE);  // cursor.c:699
memcpy (tuple_p, buffer_p + QFILE_PAGE_HEADER_SIZE, tuple_page_size);     // cursor.c:700
```
invoked from `cursor_fetch_page_having_tuple` guarded by the same detection macro (cursor.c:1020: `QFILE_GET_OVERFLOW_PAGE_ID (cursor_id_p->buffer) != NULL_PAGEID`). This client-side copy hard-codes the legacy 8B tuple-length-prefix layout and is out of scope for an executor-internal project (non-goal: no client-library changes) — see §3.1.

## 3. Framing interaction — why overflow must stay legacy, the detection boundary, and per-list-tag gotchas

### 3.1 Why overflow tuples must retain legacy format on overflow pages

1. **Overflow never benefits from the new framing's value proposition.** The entire point of the planned recdes-style framing (ralplan.md §3 P1.1(e), line 185-188) is to let readers peek fields **in place** inside live page memory, avoiding materialization. §2.2 shows that overflow tuples are *already* always force-copied into a scratch buffer on read (`qfile_retrieve_tuple`'s overflow branch ignores `peek`, list_file.c:5330-5346) — there is no live-page pointer to peek into for a field of an overflow tuple in the first place. Making overflow pages new-format would add format-decoding complexity to `qfile_assemble_overflow_tuple`/`qfile_get_tuple` for zero net win, which is exactly why ralplan.md line 149/188/298 places qfile overflow tuples in the same "existing DB_VALUE fallback path" bucket as `REC_BIGONE` and MVCC old versions.

2. **Blast radius: the overflow-chain primitives are shared and format-oblivious by construction.** `qfile_get_tuple`/`qfile_assemble_overflow_tuple` (list_file.c:4972-5060), `qfile_add_overflow_tuple_to_list` (list_file.c:2141-2210, used by the generic sort/merge output path list_file.c:4154), `qfile_copy_tuple` (list_file.c:3306-3330, one of the five P0.2 cross-list copy sites), the px_scan/px_hash_join overflow branches (px_scan_slot_iterator_list.cpp:116-136, query_hash_join.c:1677, px_hash_join_task_manager.cpp:276/349/982/1245), and the page-size probes in `network_interface_sr.cpp:5631/6138` are **all single, non-list-class-parameterized implementations**. Making overflow-page framing format-dependent would require every one of these ~8 sites to become format-aware, for a code path proven (point 1) to yield zero benefit — directly contrary to the plan's stated risk driver #1 (ralplan.md line 17: "overestimating savings is the #1 project risk") and its narrow-direct-op-boundary principle (line 12).

3. **Client-visible boundary reuse forces a single static layout.** `cursor_construct_tuple_from_overflow_pages` (cursor.c:665-724) is a byte-for-byte mirror of the server's reassembly algorithm, compiled into the CS client library (cs/CMakeLists.txt:263) which this project does not and cannot modify (non-goal). It hard-codes the legacy 8B tuple-length prefix at a fixed page offset (cursor.c:680-681) and the legacy `QFILE_MAX_TUPLE_SIZE_IN_PAGE` chunk size (cursor.c:699). Since class-(a) client-visible lists are *already* mandated legacy end-to-end (ralplan.md line 81, "client-visible list-file format boundary" driver #3, line 19), and overflow reassembly is one algorithm shared identically by client and server, the only way to guarantee the client decoder never has to understand a second (new) framing is to make overflow-page bytes unconditionally legacy — independent of which list (even a class-(d) server-internal one) the tuple happens to live in.

### 3.2 Detection point — the exact fallback boundary a scan must branch on

**Head-tuple signal** (used once a scan/cursor is positioned at a tuple's head page — this is the boundary any new per-list-format reader must check *before* attempting to interpret new-format field/offset-table framing):
```c
#define QFILE_GET_OVERFLOW_PAGE_ID(ptr) \
  (PAGEID) OR_GET_INT ((ptr) + QFILE_OVERFLOW_PAGE_ID_OFFSET)     // query_list.h:84-85
```
Canonical call sites, all structured as `if (QFILE_GET_OVERFLOW_PAGE_ID (<head_page>) != NULL_PAGEID) { /* legacy reassembly */ } else { /* normal-page path, safe to consult format_version */ }`:
- `qfile_retrieve_tuple`, list_file.c:5310 (scan next/prev/jump — the primary server scan path)
- `qfile_get_tuple`, list_file.c:4978 (shared reassembly entry, called from `qfile_get_tuple_from_current_list` and directly by px_scan)
- `qfile_update_tuple_value` update path, list_file.c:7107/7224 (in-place tuple mutation)
- `slot_iterator_list::next_qualified_slot_with_peek`, px_scan_slot_iterator_list.cpp:116
- `qfile_hash_join`/`query_hash_join.c:1677`, `px_hash_join_task_manager.cpp:276/349/982/1245`
- `cursor_fetch_page_having_tuple`, cursor.c:1020 (client-side mirror)

**Page-role signal** (used when iterating raw pages of a tfile/sector, before any tuple is positioned — needed to know a page's byte-size and to skip it as an independent tuple container):
```c
#define QFILE_OVERFLOW_TUPLE_COUNT_FLAG -2                        // query_list.h:280
QFILE_GET_TUPLE_COUNT (page) == QFILE_OVERFLOW_TUPLE_COUNT_FLAG    // e.g. list_file.c:2395, :3757-3758, :3810-3811
```
Call sites combine both signals defensively, e.g. list_file.c:2395-2396 (`QFILE_GET_TUPLE_COUNT(page) == -2 || QFILE_GET_OVERFLOW_PAGE_ID(page) != NULL_PAGEID`) and `network_interface_sr.cpp:5631/6138` (identical `-2`-or-overflow-pointer disjunction) — because a *continuation* page (role signal true) is a different physical page than the *head* page of an overflow tuple (head-tuple signal true on a page whose own role/count is a normal positive value), and page-level iterators must reject/skip the former while tuple-level readers must redirect on the latter.

**The rule for a future per-`QFILE_LIST_ID` format reader**: check the head-tuple signal (`QFILE_GET_OVERFLOW_PAGE_ID`) first, for every tuple, before consulting `list_id->format_version`. Only when that signal is false is it safe to branch on `format_version` to choose new-offset-table vs. legacy-per-value decoding. When true, unconditionally use the existing legacy reassembly path and treat the result as legacy-framed bytes, irrespective of the list's tag.

### 3.3 Gotchas for a per-`QFILE_LIST_ID` format tag

1. **Overflow-ness is a per-tuple property discovered at write time, not a per-list property.** §1 shows the trigger is `tuple_length > qfile_Max_tuple_page_size`, evaluated independently for every call to `qfile_add_tuple_to_list` (list_file.c:1628-1644). A `QFILE_LIST_ID` tagged `format_version = 1` end-to-end (all of its normal-sized tuples in new framing) will **still physically contain legacy-framed pages** for any exceptional oversized tuple (e.g. a large compressed VARCHAR row) — mixed framing within one list-file is a structural certainty for class-(d) lists with wide variable-length columns, not a corner case that can be designed away by list-level tagging alone. Any implementation of `format_version` consultation must be per-tuple-gated by §3.2's detection point, never assumed uniform across a list's pages.

2. **The framing decision can't be made until the tuple is fully serialized.** §1's "two-phase construct-then-patch" pattern (`query_opfunc.c:502-503` et al.: values are written first, `QFILE_PUT_TUPLE_LENGTH` patches the length only after the fact) means a future new-format tuple builder faces the same ordering problem: it cannot know whether a given tuple will exceed `qfile_Max_tuple_page_size` until after serializing it. Two implementation strategies both carry cost: (a) serialize new-format speculatively, measure, and **re-serialize into legacy layout** if oversized (extra CPU on the rare overflow path, but simple); or (b) serialize into a superset scratch buffer capable of representing either layout and finalize the on-disk byte layout only at the point of calling `qfile_add_tuple_to_list`. Either way, `format_version` alone (a static, list-creation-time tag) is **necessary but not sufficient** — the tuple builder needs an additional per-tuple length check against `qfile_Max_tuple_page_size` before finalizing bytes.

3. **Cross-list copy governance (P1.1(d)) must special-case overflow tuples, per-tuple, inside otherwise-uniform list-copy routines.** `qfile_copy_tuple` (list_file.c:3306-3330, one of the five P0.2-enumerated cross-list sites) peeks a tuple from the source list (`qfile_scan_list_next(..., PEEK)`, list_file.c:3320) and hands the resulting `tuple_record.tpl` straight to `qfile_add_tuple_to_list(to_list_id_p, tuple_record.tpl)` (list_file.c:3326) with **zero format awareness** — it just moves whatever bytes it received. For a *normal* (non-overflow) class-(d) tuple this is exactly the hazard the plan's FORBID-by-default rule (ralplan.md line 180) targets: the routine would blindly propagate new-format bytes into a possibly-legacy destination. But because an *overflow* tuple's peeked bytes are (per §3.1) **always legacy already** — regardless of the source list's `format_version` — such a tuple is implicitly safe to flow through `qfile_copy_tuple` unmodified even from a class-(d) source, since both the reassembled source bytes and any destination overflow encoding are the same fixed legacy layout. **Gotcha**: this means the FORBID/INHERIT/transcode rule set for the five P0.2 cross-list sites (list_file.c:3306/2691/3362/4933/4816) cannot be a single per-list-pair verdict; it must be evaluated per-tuple (overflow tuples are exempt from the format-mismatch concern; non-overflow tuples are not), or the implementation will either over-block (needlessly forbidding copy of a list that is class-(d) purely because it contains overflow tuples) or under-block (missing that a *non-overflow* tuple from the same list is not exempt).

4. **The `tplrec` scratch buffer is an additional, list-scan-scoped lifetime hazard beyond the plan's existing bump-point set.** §2.2 shows `scan_id_p->tplrec` (query_list.h:514) is grown/overwritten by `qfile_reallocate_tuple` each time the *same* scan encounters a *new* overflow tuple, independent of the page-transition bump point (`qmgr_free_old_page_and_init`, list_file.c:5234-equivalent) already tracked by the plan (ralplan.md §3 P1.1(b), line 154). A `ValueHandle` built by "peeking" a field out of an overflow tuple's reassembled bytes is safe only until the *next* overflow tuple on the same scan is retrieved — a same-page-generation, no-jump, no-explicit-transition invalidation event that the plan's current bump-point enumeration (next/jump, page release, PEEK→COPY demotion, scan close) does not explicitly name. Since ralplan.md already routes all overflow tuples to the existing DB_VALUE fallback path (line 149), this is not a live hazard *if* that fallback routing is preserved, but it is a design constraint P1 should record explicitly: any handle sourced from `tplrec` must be materialized (or invalidated) no later than the scan's next retrieval call, not merely at the next page/scan boundary.

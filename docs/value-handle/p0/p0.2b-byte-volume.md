## 1. Accumulation point and bypass check

`qfile_add_tuple_to_list_id` (list_file.c:1595 pre-instrumentation) is called from every tuple-write
path found in `list_file.c`:

| Caller | Line (pre-instrumentation) |
|---|---|
| `qfile_add_tuple_to_list` (normal + overflow-continuation writes) | 1640, 1891 |
| `qfile_fast_intint_tuple_to_list` | 1951 |
| (two-int-value fast path, second variant) | 2039 |
| `qfile_fast_val_tuple_to_list` | 2118 |
| overflow-tuple continuation (elsewhere in `qfile_add_tuple_to_list`) | 2166, 6929 |

Its `written_tuple_length` parameter is the number of physical bytes written to the tuple's *head*
page. **[CORRECTED per architect review, 2026-07-09]** An earlier revision of this section claimed the
function is called once per overflow page chunk; that is wrong: in code (`qfile_add_tuple_to_list`,
list_file.c:1743 post-instrumentation) `qfile_add_tuple_to_list_id` fires **once per tuple with the
head-chunk size only** (`MIN(tuple_length, qfile_Max_tuple_page_size)`), while overflow continuation
pages are filled by a raw-`memcpy` loop (list_file.c:1746-1765; same pattern at 2268, 7036) that never
reaches the counter. **Overflow tuples are therefore undercounted to at most ~`DB_PAGESIZE-32` bytes
each.** The published numbers in this doc are unaffected — the measured workloads contain zero overflow
tuples (max tuple ≈ 300B payload ≪ page size) — but any future reuse of these counters on wide-varchar
workloads MUST first extend the accounting to continuation bytes (count full `tuple_length` at the head
call, or instrument the ovf loop). **No bypass exists for non-overflow tuples** — the assignment's
"check `qfile_fast_intint_tuple` etc." concern does not apply; all fast-path tuple writers funnel
through this one accumulation point.

## 2. Attribution mechanism

Per the SSOT ownership-contract rule (adding `QFILE_LIST_ID` fields requires extending
copy/clear/MOVE/SKIP/PROHIBIT handling — out of scope for temporary counters), attribution uses a side
table, not a struct field:

```cpp
std::unordered_map<const void *, const void *> vh_p0_bv_site_of;       // tfile_vfid ptr -> creation-site addr
std::unordered_map<const void *, std::uint64_t> vh_p0_bv_bytes_by_site; // creation-site addr -> cumulative bytes
```

- **Registration** (`qfile_open_list`, after `tfile_vfid` is confirmed non-NULL): records
  `__builtin_return_address(0)` — the return address into `qfile_open_list`'s immediate caller, i.e.
  the actual creation-site call instruction — keyed by the freshly-created `tfile_vfid` pointer.
- **Accumulation** (`qfile_add_tuple_to_list_id`): looks up the current list's site via its
  `tfile_vfid` pointer, adds `written_tuple_length` to that site's running total.
- **Readout + cleanup** (`qfile_destroy_list`, before the underlying temp file is freed): looks up and
  logs the site's cumulative total via `er_log_debug`, then erases the `tfile_vfid -> site` mapping
  (pointer reuse safety — `tfile_vfid` addresses can be reallocated to unrelated future lists).
- **Comprehensive final readout** (`qfile_finalize`, module shutdown): dumps every remaining
  `(site, cumulative_bytes)` pair — needed because, per §4, most lists in this workload are **not**
  torn down via `qfile_destroy_list` at all.

All three call sites are guarded by a `std::mutex` (CS-mode is multi-threaded; a temporary debug counter
does not need lock-free performance).

**(a)/(b)-eligible** — i.e. **not** a class-(d) forward-only intermediate. **Zero bytes were attributed

unanswered by this workload** — see §6 for what's needed to answer it.

Secondary observation: Q2/Q3 use `ORDER BY ... LIMIT 20`. The very small byte totals (800/960 bytes for
a 20-row result, vs. the ~10,000–40,000 candidate rows the `WHERE` clause matches before the `ORDER
BY`/`LIMIT`) indicate the sort's own intermediate buffering is **not** going through
`qfile_add_tuple_to_list_id` at the volume one might expect from a full external sort — consistent with
a Top-N in-memory heap optimization for small `LIMIT` values that avoids full list-file materialization.
Only the final ≤20-row result list is written through the counted path. **This means `LIMIT`-bounded
queries systematically undersample true sort-intermediate byte volume** — a full, unbounded `ORDER BY`
(no `LIMIT`) is needed to observe genuine sort-buffer byte cost.

## 4. Key methodological finding: `qfile_destroy_list` is not the common teardown path

Initial instrumentation dumped only at `qfile_destroy_list`. Running all 3 queries produced **zero**
dump lines — the byte counters were accumulating correctly (verified once TOP-level result-list byte
counts appeared via the `qfile_finalize` fallback, see below) but nothing was ever read out, because for
this workload, no `qfile_destroy_list` call ever fired for the queries' own result lists. Tracing why:

`qmgr_free_query_temp_file_helper` (query_manager.c:3254, called from `xqmgr_execute_query` and related
end-of-query cleanup at query_manager.c:1732/2025/2109/2376) frees a query's `QMGR_TEMP_FILE` chain
(`query_p->temp_vfid`) **directly**, via `qmgr_free_temp_file_list`, without ever calling
`qfile_destroy_list`. This is the **default** per-query temp-file teardown path in CS-mode.
`qfile_destroy_list` is reserved for specific internal callers within `list_file.c`/`query_executor.c`
(sort/merge/dedup helpers that explicitly own and discard an intermediate list mid-query) — exactly the
class-(d)-shaped call sites — not the top-level per-query result list.

Because `query_manager.c` is outside this assignment's edit scope (`heap_file.c`, `list_file.c`, at most
one shared header), the fix stays inside `list_file.c`: `qfile_finalize` (list_file.c, module-level
shutdown hook, called once at server stop) now also dumps every remaining `(site, bytes)` pair in the
map. This guarantees every creation site is reported at least once per server lifetime regardless of
which teardown path its list took, at the cost of granularity being "whole server run" rather than
"this one list's lifetime" — acceptable here because each profiling run restarts the server per query,
making "whole server run" equivalent to "this one query".

**Note for P3.5** (D-G6.3, "변환 경로 실행 횟수 = 0" AC): if P3 needs a per-list, not per-server-run,
byte/teardown-path signal, it should also hook `qmgr_free_query_temp_file_helper`/
`qmgr_free_temp_file_list` (query_manager.c) — outside this task's file scope, flagged here as a
join point for whoever owns P1.1(d)/P3.5.

## 6. Limitations

- **Measured on debug `wmloc` workload only.** TPC-H representative queries (per grilled_plan D-G6.1,
  "P0.3 debug 워크로드 + 가능 시 TPC-H 대표 쿼리") are **deferred to the release phase** — this
  assignment's non-goals explicitly exclude `tpch_sf10` and release builds for debug-instrumentation
  work ("debug builds must not touch large DBs").
- **No class-(d) site was exercised** by the 3 P0.3 queries (§3) — the class-(d) byte-volume occupancy
  number D-G6 needs (baseline proposal: <30% ⇒ defer framing to B/campaign) is **not yet measured**.
  Follow-up needs queries that hit `qdata_process_distinct_or_sort` (DISTINCT), `qexec_groupby`-forced
  sort (GROUP BY without index), or `hjoin_prepare_partition`/`hjoin_split_qlist` (hash join spill) —
  none of which the ralplan §P0.3 SQL triggers.
  **SUPERSEDED by §9** — a follow-up supplemental workload (DISTINCT / GROUP BY without index / forced
  hash-join / unbounded `ORDER BY`) was run against the same `vh_profile` fixture and *did* attribute
  nonzero bytes to confirmed class-(d) sites (`qdata_process_distinct_or_sort`,
  `qexec_alloc_agg_hash_context`); see §9 for the measured class-(d) byte-volume share.
- **`LIMIT`-bounded `ORDER BY` undersamples sort-buffer volume** (§3) — an unbounded sort is needed for
  a representative sort-intermediate byte count.
- Byte totals are **cumulative per server run**, not strictly per-query, because the reliable readout
  point (`qfile_finalize`) is a shutdown hook, not a per-list hook (§4). This was mitigated here by
  restarting the server before each query, but any future multi-query-per-run measurement needs the
  `query_manager.c` hook noted in §4 to get true per-query attribution.

## 7. Reproduction

Same build/fixture steps as `p0.3-peek-copy-profile.md` §5. For byte-volume readout specifically:

```bash
# after running a query, BEFORE stopping the server:
PID=$(pgrep -f 'cub_server wmloc')
cp /proc/$PID/maps /var/tmp/wmloc_maps_snapshot.txt   # base for addr2line offset math

cubrid-server-ctl.sh stop wmloc   # triggers qfile_finalize's comprehensive dump
grep 'VH-P0-TEMP-COUNTER list-byte-volume-final' $(ls -t $CUBRID/log/server/wmloc_*.err | head -1)

# resolve a logged "site=0x..." address:
BASE=$(awk '/libcubrid\.so\.11\.5$/ && /r-xp/ {print $1; exit}' /var/tmp/wmloc_maps_snapshot.txt | cut -d- -f1)
python3 -c "print(hex(0x<site_addr> - 0x$BASE))"
addr2line -e $CUBRID/lib/libcubrid.so.11.5 -f -C <offset_from_above>
```

- **Item (ii) note**: the `;plan simple` dump for Q2 shows `Sort(group by)` (sort-based grouping), yet the runtime
  dump shows `qexec_alloc_agg_hash_context`'s `part_list_id`/`sorted_part_list_id` buffers *did* receive bytes.
  Reading `qexec_groupby` (query_executor.c §5187-5610) confirms CUBRID's buildlist GROUP BY always attempts
  hash-based aggregation first when `g_hash_eligible`, and spills any tuples the in-memory hash table cannot

  exclusive on this code path; the `;plan` label describes the fallback/merge shape, not the absence of the

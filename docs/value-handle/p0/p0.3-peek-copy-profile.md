## 2. Why a peek/variable split was added beyond the literal spec

The ralplan spec instruments exactly `heap_attrvalue_point_fixed` (peek) and
`heap_attrvalue_transform_to_dbvalue` (copy). Reading `heap_attrvalue_read` (heap_file.c:10490, the sole
caller of both) shows the two are **unconditionally chained per attribute**:

```
if (attrepr->is_fixed)      heap_attrvalue_point_fixed (...)      /* peek: locate raw bytes */
else                          heap_attrvalue_point_variable (...)   /* peek: locate raw bytes */
return heap_attrvalue_transform_to_dbvalue (value, attrepr, &raw);  /* copy: always called */
```

Every attribute access that reaches `heap_attrvalue_read` incurs **exactly one peek followed by exactly
one copy** — for both fixed and variable attributes. This means, measured literally per the spec's two
named functions, **`peek_count` (fixed) always equals `copy_count` (fixed)**, so the "peek ratio"
(`peek/(peek+copy)`) is trivially `0.5` by construction, not a headroom signal. To get a category split
that is actually informative, this instrumentation additionally counts `heap_attrvalue_point_variable`
(the peek-equivalent for variable-length attributes) and splits `copy_count` by `attrepr->is_fixed`
inside `heap_attrvalue_transform_to_dbvalue` — both additions stay inside `heap_file.c` and do not touch
functions outside the spec's named pair. This surfaces the **absolute fixed-vs-variable split**, which
is where the real per-query signal lives (§3).

**Implication for P1**: the "existing peek paths already avoid some copies" headroom claim (ralplan
Decision Driver #1) does **not** describe this code path — `heap_attrvalue_read` never skips
`transform_to_dbvalue`. Any existing peek-without-copy fast path must live elsewhere (e.g. disk-direct
`cmpdisk` comparisons in `scan_manager.c`/`object_primitive.c` that bypass `heap_attrvalue_read`
entirely for certain predicate evaluations). P1 should re-ground the headroom claim against those sites,
not this pair.

## 3. Results

Fixture: `vh_profile` (50,000 rows, ralplan §B-debug schema), created fresh on `wmloc`.
`COUNT(*) = 50000` ✓, `COUNT(*) WHERE c_vc >= 'N' = 24999` ✓ (both required checks pass).

Each query below ran against a freshly restarted server (counters reset to 0 at start), isolating
per-query counts. Values are the **last periodic dump** before server stop (dump fires every 500
combined hits — see §4 caveat on precision).

| Query | peek_fixed | peek_variable | copy_fixed | copy_variable | peek ratio (fixed) | peek ratio (variable) |
|---|---|---|---|---|---|---|
| Q1: `SELECT COUNT(*), SUM(CAST(c_int AS NUMERIC(38,0))) FROM vh_profile WHERE c_int > 25000` | 49,977 | 23 | 49,977 | 23 | 0.500 | 0.500 |
| Q2: `SELECT c_int, c_date FROM vh_profile WHERE c_int > 40000 ORDER BY c_date, c_int LIMIT 20` | 59,977 | 23 | 59,977 | 23 | 0.500 | 0.500 |
| Q3: `SELECT c_vc FROM vh_profile WHERE c_vc >= 'N' ORDER BY c_vc LIMIT 20` | 61 | 49,939 | 61 | 49,939 | 0.500 | 0.500 |

Row-count checks: Q2 and Q3 each returned exactly 20 rows (LIMIT satisfied, `c_vc >= 'N'` population is
24,999 ≫ 20). Q1 returned 1 aggregate row (`count(*)=25000`, matching `c_int > 25000` over 50,000 rows).

**Key finding — absolute fixed/variable split (the real signal)**:
- Q1/Q2 (predicate and projection over `c_int`/`c_date`, both fixed-length types) drive **>99.9% of
  attribute-read volume through the fixed-length path** (peek_variable/copy_variable stay flat at 23 —
  background/catalog attribute reads unrelated to `vh_profile`'s own columns).
- Q3 (predicate, projection, and sort key all on `c_vc`, `VARCHAR(300)`) **inverts this almost
  completely**: 49,939 of ~50,000 total attribute reads go through the variable-length path
  (peek_fixed/copy_fixed collapse to 61 — same small background/catalog constant). This is the
  compressed-varchar-heavy path (`c_vc` payload length 280 ≥ `OR_MINIMUM_STRING_LENGTH_FOR_COMPRESSION`
  = 255, object_representation.h:1384 — compressible) that ralplan Decision Driver #3 and grilled_plan
  D-G4/D-G3 (workload W1, "CV 정렬") identify as the primary detoast-cost headroom target for P1.
- Every fixed-vs-variable pair is internally 1:1 (peek=copy per §2), so the per-query headroom question
  P1 should ask is **"how many of these ~50–60K attribute reads are fixed vs variable"**, not the
  peek/copy ratio itself.

## 4. Readout method and precision caveat

Counters are `std::atomic<uint64_t>` (release-consistency not required for a temporary approximate
counter; `memory_order_relaxed` used throughout) guarded by `#if !defined (NDEBUG)`, so they compile
out entirely in release builds — zero release-path cost, matching ralplan's "debug counters are the
correct tool" rationale (both instrumented functions are `static`/inlineable; uprobes would not fire
reliably in release).

Readout: a periodic dump fires (`vh_p0_maybe_dump`, called at the end of every peek/copy-site
invocation) whenever the **sum of all four counters** is a multiple of 500, emitting all four current
values via `er_log_debug (ARG_FILE_LINE, "VH-P0-TEMP-COUNTER heap peek_fixed=... peek_variable=...
copy_fixed=... copy_variable=...")`. This requires `er_log_debug=yes` in `cubrid.conf` (not on by
default — added under `[common]` for this profiling session only, see reproduction steps below).

**Precision caveat**: because the dump only fires on exact multiples of 500, the *last* dump before
server stop is a lower-bound snapshot — the true final counts can be up to 499 higher, per counter,
than what's reported (the last few increments after the final crossed multiple are never flushed to the
log). For Q1/Q3 the reported fixed+variable sums (50,000 / 100,000-combined) land on suspiciously round
numbers, suggesting the snapshot is at or very near the true total; treat all values here as accurate to
within ≤1% (500 out of ≥50,000 combined events). This is acceptable for ratio-level headroom analysis
per ralplan's own tolerance statement but should not be used for exact byte/row accounting.

An alternative (scan-close-triggered dump, e.g. hooking `heap_scancache_end`) was considered and
rejected as *not simpler* for the same precision: scan-close fires many times per query (once per
scan range), requiring the reader to sum multiple log lines per query, versus one periodic-dump number
here; the periodic-dump choice keeps read-out mechanically simplest per the assignment's directive
("choose the simplest reliable readout").

## 5. Reproduction

```bash
# 1. Build (from /home/cubrid/dev/workspace, WORKSPACE points at the instrumented worktree):
WORKSPACE=/home/cubrid/dev/cubrid-vh just build debug 11.5.vh
just conf   # requires CUBRID=~/CUBRID in env; copies workspace cubrid.conf -> $CUBRID/conf/cubrid.conf

# 2. Enable debug logging for THIS install only (not in the shared workspace cubrid.conf template,
#    to avoid affecting other installs sharing that template):
#    append under [common] in $CUBRID/conf/cubrid.conf:
#      er_log_debug=yes
#    (a cubrid_port_id override was also required in this session — see p0.2b-byte-volume.md §5 for
#    why: an unrelated, already-running cub_master from an older ~/CUBRID target occupied the default
#    port 1523.)

# 3. Fixture (wmloc, ralplan §B-debug, adapted table name):
cubrid-server-ctl.sh start wmloc
csql wmloc -c "CREATE TABLE vh_profile (c_int INT, c_bigint BIGINT, c_double DOUBLE, c_date DATE, c_num NUMERIC(15,2), c_vc VARCHAR(300));"
csql wmloc -c "INSERT INTO vh_profile SELECT ROWNUM, CAST(ROWNUM AS BIGINT), ROWNUM * 1.1, DATE '2020-01-01' + (CAST(ROWNUM AS INT) MOD 3650), CAST(ROWNUM * 1.23 AS NUMERIC(15,2)), CHR(65 + MOD(ROWNUM, 26)) || LPAD(CAST(ROWNUM AS VARCHAR), 279, 'ABCDEFGHIJ') FROM db_class a, db_class b, db_class c WHERE ROWNUM <= 50000;"
csql wmloc -c "SELECT COUNT(*) FROM vh_profile;"                       # expect 50000
csql wmloc -c "SELECT COUNT(*) FROM vh_profile WHERE c_vc >= 'N';"     # expect 24999

# 4. Per query (restart resets counters to 0):
cubrid-server-ctl.sh stop wmloc; cubrid-server-ctl.sh start wmloc
csql wmloc -c "<one of the 3 profiling queries>"
cubrid-server-ctl.sh stop wmloc   # flushes qfile_finalize's byte-volume dump too, harmless here

# 5. Read the counters (latest .err file for wmloc):
grep 'VH-P0-TEMP-COUNTER heap' $(ls -t $CUBRID/log/server/wmloc_*.err | head -1) | tail -1
```

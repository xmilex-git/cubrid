## 0. What changed from ralplan Rev.4, in one paragraph

ralplan.md P1.1(b) (line 151-162) defined the lifetime contract as a **detection-first** scheme: a full 4-category bump-point set (next/jump, page release/transition, PEEK→COPY demotion retry, scan close) enforced by a per-scan/per-handle `generation` counter that accessors assert against, with page-copy (`di-fixedscan-q8-20260708`) treated as a late-bound interaction to be resolved "in P1." grilled_plan.md D-G2 replaces this: the contract's **body** is now a structural guarantee (CopiedFrame: pointer validity is guaranteed by copy ownership, not merely checked after the fact), the bump-point set shrinks because the demotion-retry category structurally disappears under that basis, and the page-copy landing order is decided now rather than deferred. The generation counter survives only as a debug-only backstop that *detects* violations of a guarantee the structure is supposed to make impossible, not as the primary mechanism. This document states the structural guarantee first (§1) and the detection backstop second (§5), per the plan's own explicit ordering intent (D-G2 line 40: "계약의 본체는 구조적 보장").

## 1. Structural guarantee model: CopiedFrame as the first-class basis

### 1.1 PG analog

PostgreSQL's executor never lets a `TupleTableSlot`'s pass-by-reference Datums outlive the resource that backs them; the mechanism is **pin discipline coupled to slot ownership**, not a runtime generation check:

- `TupleTableSlot`'s doc comment (`~/dev/postgres/src/include/executor/tuptable.h:39-43`): "For a tuple in a disk page we need to hold a pin on the buffer until the TupleTableSlot's reference to the tuple is dropped."
- `TTS_FLAG_SHOULDFREE` ownership rule (tuptable.h:80-82): "the physical tuple is 'owned' by the slot and should be freed when the slot's reference to the tuple is dropped" — ownership is structural (a flag + a drop protocol), not a value staleness check.
- The `materialize` slot callback (tuptable.h:190-194): "Make the contents of the slot solely depend on the slot, and not on underlying resources (like another memory context, buffers, etc.)" — this is the PG operation that forcibly converts a pin-dependent/borrowed slot into a self-contained one, i.e. the PG analog of a forced-copy bump.
- **`BufferHeapTupleTableSlot`** (tuptable.h:293-298) is the concrete case that matters for the CUBRID translation: `Buffer buffer; /* tuple's buffer, or InvalidBuffer */` with the comment "If buffer is not InvalidBuffer, then the slot is holding a pin on the indicated buffer page; drop the pin when we release the slot's reference to that buffer." **The guarantee is: pin held ⇒ tuple pointer valid. Pin drop (buffer release) is the only bump.** There is no separate PG-side "generation" field checked on every access — validity is guaranteed by the pin, not detected after the fact.

### 1.2 CUBRID has no pin — the CopiedFrame translation

CUBRID's page-fix (`pgbuf_fix`) is not usable as a PG-pin equivalent for scan-lifetime purposes: holding a page fix for the duration of a scan (rather than per-tuple) is exactly the `fixed_scan` deadlock class the executor already avoids on purpose (`query_executor.c:16146-16224`, P0.1 row 51 — "may lead to page deadlocks" comment at query_executor.c:16151; spec f8). So CUBRID cannot reproduce "hold the pin, guarantee validity" directly.

**D-G2's resolution**: the PG-pin analog for CUBRID is **CopiedFrame** — the scan-owned page copy originally sketched under the `di-fixedscan-q8-20260708` design using the placeholder field names `HEAP_SCANCACHE.copied_frame`/`PEEK_FROM_COPIED_PAGE` (grilled_plan.md line 37; ralplan.md line 162). **Those placeholder names are superseded by UG1 decision ①** (`ug1-verdict.md` §①, 2026-07-09): the actual CopiedFrame basis is the `issue154-page-copy-heap-scan` ("cached scan") workstream, merged directly into this branch at `a3ccc1303`; §4.1 records the merge and the real mechanism — `HEAP_SCANCACHE.local_cache_handle`/`local_cache_vpid`/`read_mode` (`heap_file.h:170-172`, merged tree @ `a3ccc1303`). This is a copy, not a fix, so it sidesteps the deadlock class entirely while giving the same structural property PG gets from a pin:

> **Structural guarantee (the contract's body): copy alive ⇒ every pointer-type ValueHandle/ValueSlot entry sourced from that copy is valid. Copy replacement is the only heap-side bump.**

This is deliberately phrased as a guarantee, not a check — mirroring PG's "pin held ⇒ valid," not "check a counter on every access and hope it matches." §5's generation counter is the *debug instrument that verifies the guarantee held*; it is not what makes the pointer valid.

**Basis invariant (`[architect MEDIUM P2]`, pre-UG1 review; mirrored in `p1.1-valueslot-design.md` §a.5)**: the structural guarantee above only holds while a CopiedFrame actually exists for the scan in question. It follows directly, and is stated here explicitly rather than left implicit, that:

> Heap-scan `VC_RAW`/`VC_COMPRESSED` `VALUE_SLOT` pointer-type columns are **never enabled** for a given heap scan unless a CopiedFrame basis is actually present for that scan — concretely, `scan_cache->read_mode == HEAP_SCAN_READ_LOCAL_CACHE` with a non-NULL `scan_cache->local_cache_handle` (`heap_file.h:170-172`, merged tree @ `a3ccc1303`), the basis actually provided by the merged `issue154-page-copy-heap-scan` ("cached scan") mechanism (§4.1). **UG1 decision ①** (`ug1-verdict.md` §①, 2026-07-09) retired the former primary-plan/minimal-scope-fallback branch this sentence used to name — there is now exactly one CopiedFrame-providing mechanism, not two, and it is unconditionally in-branch as of the merge. Live-page PEEK paths (the 8 demotion sites of §2.1 and their non-migrated callers) stay on the legacy `DB_VALUE` path, unchanged — they are never a second, `VALUE_SLOT`-sanctioned basis for populating a pointer-type slot cell, even though "live-page PEEK today" is literally what those unmigrated callers do. Until this mechanism is active for a given heap scan — i.e. unless `qexec_is_cached_scan_eligible ()` (`query_executor.c:7469`) judged the scan eligible **and** `pgbuf_copy_buffer_alloc ()` did not degrade to `HEAP_SCAN_READ_COPY` under OOM (`heap_file.c:6874-6884`) — that scan's `VC_RAW`/`VC_COMPRESSED` heap columns MUST be classified `FALLBACK` at scan open (`p1.1-valueslot-design.md` §a.3) rather than wired onto live-page PEEK with only §5's debug-only generation counter as protection. The counter is a detection backstop for this structural guarantee; it is never a substitute basis for the guarantee itself — an implementer who wires a `VALUE_SLOT` pointer cell onto live-page PEEK "because the generation counter will catch misuse in debug builds" has violated this invariant, since release builds carry no such counter at all (§5) and the guarantee would then not hold structurally, only be hoped for.

Qfile (list-file) scans are **not** subject to this invariant: their `VC_RAW`/`VC_COMPRESSED` pointer validity already rests on the independent, always-available "re-deform before next read" structural property (§2 row 3 below), which needs no CopiedFrame at all. The invariant is heap-scan-specific because CopiedFrame is specifically the heap-side answer to the no-pin problem (§1.2 above).

### 1.3 Interaction with D-G1 (ValueSlot deform-once)

Per D-G2 line 41 and D-G1 (grilled_plan.md line 27-34, owned by `p1.1-value-slot.md`): after deform, the 9 fixed-length pass-by-value entries and the NUMERIC decode-once result are **slot-owned** (copied out of the page into the slot's `values[]` array at deform time) — they have no lifetime dependency on CopiedFrame at all once deform has happened. Only **pointer-type entries** (uncompressed-varchar peek, compressed-varchar payload indicator) remain bound to page lifetime, and therefore to the CopiedFrame guarantee above — and, per the basis invariant just stated, to CopiedFrame's actual presence, not merely its eventual availability. This document's bump-point set (§2) governs exactly that pointer-type subset.

## 2. Bump-point set (reduced per D-G2)

ralplan Rev.4's 4-category set (next/jump, page release/transition, PEEK→COPY demotion retry, scan close — line 152-156) is replaced by:

| # | Bump point | Trigger | Coordinate (`ebf08d080`) | Contract action |
|---|---|---|---|---|
| 1 | **Page/copy transition** | CopiedFrame is replaced with a new page's copy (heap-side; the CUBRID analog of PG buffer-pin release) | `di-fixedscan-q8-20260708` `copied_frame` replacement point (landing-order dependency, §4) | All pointer-type ValueSlot entries sourced from the old copy become invalid at the instant of replacement. No demotion/retry semantics — the copy is simply gone. |
| 2 | **Scan close** | Scan-owned CopiedFrame and ValueSlot are torn down | scan-scoped, no single coordinate (per-scan-type close routine) | All entries invalid; ValueSlot itself is deallocated. |
| 3 | **List-scan page transition** | `qmgr_free_old_page_and_init` frees the list-file scan's current page before advancing | `list_file.c:5233` **[P0.1 drift: ralplan.md line 154/298 cites `list_file.c:5234`; re-verified at `ebf08d080` — same statement, 1-line off, semantics unchanged (P0.1 row 10)]** | Naturally satisfied by re-deform: the very next `qfile_scan_next`/`_prev` call re-deforms the row into the slot before any pointer-type entry from the freed page could be read again. **Rule: pointer-type entries are valid until the next row's deform, full stop** — this bump point does not need independent enforcement beyond "deform-once per row" (D-G1), because there is structurally no window where a stale pointer from the *previous* page can be read after the *current* row has been deformed from the new one. |

Row 3 covers **jump** as well: `qfile_jump_scan_tuple_position` (list_file.c:5366+) re-derives page position and re-triggers a `qfile_retrieve_tuple`/deform cycle just like next/prev (P0.4 §2.3: "jump introduces no new detection path... orthogonal to how the scan got to that position"). ralplan's separate "next/jump" category (line 153) therefore collapses into row 3 rather than surviving as its own bump point — jump is not a special case requiring separate contract logic, only a separate *test case* (§6).

**Reduction accounting**: ralplan's 4 categories → this 3-row set. Category 3 (PEEK→COPY demotion retry) is not merely renumbered away — it is argued out explicitly in §2.1, because P0.1 found it recurs far more pervasively than ralplan's single citation suggested, and that finding must be addressed honestly rather than silently dropped.

### 2.1 Demotion-exclusion argument — addressing the P0.1 5×/3× recurrence finding `[P0-CONDITIONAL]`

**The finding this section is conditional on**: P0.1 row 8/52 (`p0.1-coordinates.md`) verified that the `PGBUF_IS_PAGE_CHANGED(...) → is_peeking = COPY; goto restart_scan_oid;` demotion pattern cited once by ralplan.md (line 155, `scan_manager.c:5986-5991`) actually recurs **5 times in the same function** (`scan_manager.c:5986-5991, 6164, 6185, 6202, 6223`, all read-verified in this task at `ebf08d080`), plus **3 times** in the parallel path (`px_scan_slot_iterator.cpp:131-136, 145-150, 159-164`, also read-verified). P0.1 explicitly flagged this as "relevant to D-G2's claim that this demotion-retry bump-point class disappears from the main line" and asked P1 to confirm the descope covers all 8 occurrences, not just the one ralplan cited.

**Confirmation**: it does, and for a structural reason rather than a coincidence of counting. Every one of the 8 sites shares the identical guard: `is_peeking == PEEK && scan_cache->page_watcher.pgptr != NULL && PGBUF_IS_PAGE_CHANGED(pgptr, &ref_lsa)`. This guard exists because **live-page PEEK** hands the caller a raw pointer into a buffer-pool page that a *concurrent writer* could still mutate; `PGBUF_IS_PAGE_CHANGED` (an LSA comparison) is the only way to discover, after the fact, that the page moved under the peek and the read must be redone as a COPY. This is a hazard **intrinsic to live-page PEEK against the shared buffer pool**, not a property of the ValueHandle/ValueSlot lifetime contract itself.

Under the CopiedFrame basis (§1.2), the slice-scan mainline does not peek into the live buffer-pool page at all — it reads through a scan-owned copy whose contents cannot be mutated by a concurrent writer (nobody else holds a reference to that copy), and which changes only wholesale, at the page/copy-transition bump point (§2 row 1), never mid-row. There is therefore no `PGBUF_IS_PAGE_CHANGED`-style condition to check and nothing to demote *away from* — the retry pattern's entire reason for existing (guard against concurrent mutation of a page you're pointing into) is structurally absent for CopiedFrame-based access. This is why all 8 occurrences descope together: they are one hazard class (live-page-PEEK-vs-concurrent-writer), not 8 independent bump points, and the class doesn't apply to the new basis.

**What happens on paths that still use live-page PEEK.** Not every heap-scan caller will be migrated to CopiedFrame-based access in this stage (per the minimal-scope AC, §4) — and per §1.2's basis invariant, any such non-migrated caller's columns simply stay `FALLBACK` from `VALUE_SLOT`'s point of view. Any caller still going through `heap_attrvalue_read`'s live-page peek (the 8 sites above, and their non-migrated callers) keeps its existing `PEEK→COPY` demotion-retry behavior **unchanged**, falling back to the existing `DB_VALUE` path exactly as it does today. **This is not an extension of the ValueHandle/ValueSlot lifetime contract** — the contract in this document governs CopiedFrame/ValueSlot-sourced pointer entries only; legacy live-page-PEEK call sites are simply outside its scope, governed by their own pre-existing (and unchanged) demotion logic. Concretely: no new bump-point category is added to handle demotion, and no ValueHandle/ValueSlot entry is ever constructed from a live-page-PEEK result that might later demote — this is the same rule the basis invariant (§1.2) states from the opposite direction (a slot cell must not be populated from a basis that hasn't structurally landed).

`[P0-CONDITIONAL]`: this whole argument is conditional on the P0.3 finding (`p0.3-peek-copy-profile.md` §2) that `heap_attrvalue_read` unconditionally chains peek→copy for every attribute access (peek ratio structurally 0.5) — i.e. that there is *no* existing live-page-peek-without-copy fast path that the new ValueSlot design would need to route through CopiedFrame to preserve headroom on. If a future audit found such a fast path reachable by ValueSlot's deform path, the demotion-retry category would need re-inclusion for that path specifically, scoped the same way class-(d) exceptions are scoped elsewhere in this plan.

## 3. tplrec overflow-tuple hazard — integrated as an explicit forbidden-reference rule `[P0-CONDITIONAL]`

**Source**: P0.4 finding 5 (`p0.4-overflow-audit.md` §3.3 point 4). This hazard was **not known to grilled_plan.md** — grilled_plan.md's D-G2 bump-point reduction (§2 above) predates P0.4's audit. It is folded in here per the assignment's explicit instruction, and the whole section is tagged `[P0-CONDITIONAL]` because it exists *only* because of, and is scoped entirely by, a P0.4 finding this document's authors did not independently derive.

**The hazard, precisely**: `QFILE_LIST_SCAN_ID.tplrec` (`query_list.h:514`, comment: "used for overflow tuple peeking") is a per-scan scratch `QFILE_TUPLE_RECORD` that `qfile_retrieve_tuple`'s overflow branch (`list_file.c:5304-5350`, specifically the `peek` sub-branch at list_file.c:5330-5338) reuses across every overflow tuple the scan encounters: `qfile_get_tuple_from_current_list` reassembles the *next* overflow tuple's bytes into the *same* `tplrec` buffer (grown in place via `qfile_reallocate_tuple`, not freed-and-reallocated), overwriting whatever the previous overflow tuple's peek pointed at. **This invalidation event is independent of every bump point in §2**: it is not a page/copy transition (the buffer's own identity doesn't change — only its contents), not a scan close, and not the list-scan page-transition row (which is about the *source* page chain, not this scan-owned scratch buffer). It fires on **the very next overflow tuple the same scan retrieves**, which can happen without any next/jump semantics changing in a way §2 would catch.

**Why this is not the same shape as §1's CopiedFrame guarantee**: CopiedFrame's structural promise is "copy alive ⇒ pointer valid; the copy is replaced wholesale at a declared bump point." `tplrec` breaks that shape — the *buffer identity* stays alive across the invalidating event (it's realloc'd in place, not swapped for a new object), yet its *contents* become stale without any of §2's bump points firing. This is exactly the kind of exception the structural model does not cover for free, so it must be recorded as its own rule rather than absorbed into §1 or §2.

**Contract rule (forbidden-reference rule, not a bump point)**:

> Any pointer-type ValueHandle/ValueSlot entry sourced from `scan_id->tplrec` must be materialized (copied to `DB_VALUE`) or discarded no later than the scan's *next* retrieval call (`qfile_scan_next`/`_prev`/`qfile_jump_scan_tuple_position`), never merely at the next declared bump point (page/copy transition or scan close). Equivalently: `tplrec`-sourced entries have scan-retrieval-call granularity, not page-generation granularity.

**Why this rule is currently dormant, and why it must be recorded anyway**: ralplan.md (line 149, carried unchanged by grilled_plan.md — P0 findings unchanged for P0.4) already routes **all** qfile overflow tuples to the existing `DB_VALUE` fallback path, never through ValueHandle/ValueSlot. Under that routing, no ValueSlot entry is ever sourced from `tplrec`, so the rule above has no live enforcement point today — it is `[P0-CONDITIONAL]` in the strict sense that it only becomes an active hazard if a future change (e.g. a campaign-stage extension of direct-op support to overflow tuples) sources a ValueSlot pointer entry from `tplrec`. It is recorded here, rather than left implicit, precisely so that future work does not silently violate it by assuming §2's bump-point set is exhaustive for pointer-type entries. Any design that considers bringing overflow tuples into ValueSlot scope MUST re-open this section.

  2. **No** changes to the `pgbuf` public API surface (no new opaque copy-buffer abstraction beyond what the slice path needs internally) — that generalization is exactly what `issue154`'s slice 1 is for; duplicating it here is explicitly out of scope.

  5. Single-buffer, no double-buffering/prefetch — one page's worth of copy, replaced wholesale at the page-transition bump point (§2 row 1), matching the structural model exactly; no speculative ahead-of-time copying.
  - **Any implementation that needs to cross one of these five boundaries is out of the minimal-scope AC and requires re-approval** (this is the erosion guard D-G2/grilled_plan.md §Risks "R-신규" calls for).

A heap scan for which neither (a) nor (b) is active — e.g. because the env gate covers a call site the fallback's 5-boundary scope (above) does not reach — MUST leave its `VC_RAW`/`VC_COMPRESSED` columns `FALLBACK`-classed for that scan rather than default to live-page PEEK under `VALUE_SLOT`. Acceptance test shape: a debug/engagement counter analogous to `Num_qfile_format_conversion_executions` (`p1.1-format-selection.md` §3) — e.g. `Num_valueslot_heap_pointer_without_copiedframe` — instrumented at the one place a heap-scan `VALUE_SLOT` pointer cell could be populated without an active CopiedFrame, asserted `0` across the full P3 slice test suite, mirroring D-G6.3's "transcode-path-executed = 0" pattern (grilled_plan.md line 75) and this document's own §6 `--negative-tplrec-invariant` test shape.

## 5. Generation counter (debug-only backstop), accessor discipline, join semantics, forced materialization, valgrind

Per D-G1/D-G2 (grilled_plan.md line 32, 40): detection is secondary to the structural guarantee in §1, kept only to catch a violation of that guarantee as a bug, not to define correctness.

- **Placement**: `generation` is a single `uint32_t` field **on the ValueSlot** (per-scan), not per-value — this differs from ralplan's per-`ValueHandle` `scan_generation_snapshot` field (line 144, 157), which D-G1 already rejected as reinventing a fat per-value handle (grilled_plan.md line 28). See `p1.1-value-slot.md` for the slot struct itself; this document only specifies the field's role in the lifetime contract.
- **Build gating**: debug-only (`#ifndef NDEBUG`-class gating, matching the pattern P0.3's temporary counters used — `p0.3-peek-copy-profile.md` §4). The release ValueSlot struct layout **omits the generation field entirely** — this is a compile-time size/layout difference, not a runtime-disabled field, so there is no release-path memory or branch cost, consistent with D-G1's "release 구조체에 세대 필드 불포함." This is also why §1.2's basis invariant cannot be "enforced" by the generation counter alone in release builds — there is no counter to check — and must instead be a structural precondition on which scans are even eligible to populate a pointer-type cell in the first place.
- **Accessor discipline**: all access to a pointer-type ValueSlot entry goes through an accessor. In debug builds, the accessor asserts the caller's captured generation matches the slot's current generation before dereferencing; in release builds, the accessor performs no check (the structural guarantee is what release actually relies on — see §1.2). Raw pointer extraction that bypasses the accessor is forbidden in both build types; debug builds can only catch bypass-and-then-use, not bypass-and-hold, so the accessor-only rule is a coding-standard requirement, not something the generation check alone enforces.
- **Join semantics**: a cross-scan predicate (e.g. a hash/nested-loop join comparing a left-scan ValueSlot entry against a right-scan ValueSlot entry) checks **both** slots' generations independently through the accessor before each comparison — a stale entry on either side fails fast (debug-only assert) rather than silently comparing against invalidated memory. This is unchanged from ralplan's join-accessor rule (line 158) except that it is now phrased as validating the structural guarantee rather than being the guarantee.
- **Forced materialization at scan-boundary crossing**: any pointer-type ValueSlot entry that must outlive its own scan's CopiedFrame guarantee — e.g. carried into a different scan's context, or held past a call that could bump the owning slot's generation — must be materialized to `DB_VALUE` **before** the crossing (ralplan line 160, unchanged `[ralplan-carry]`). This is the CUBRID analog of PG's `materialize` slot callback (tuptable.h:190-194, §1.1) and is the only sanctioned way to extend a pointer-type entry's effective lifetime beyond what §1's structural guarantee covers.
- **Valgrind backstop** (`[ralplan-carry]`, ralplan.md §G, line 853-870):
  ```bash
  # On CS-mode debug, wmloc, small query set. --trace-children=yes because
  # cubrid server daemonizes (cub_server is the child process).
  valgrind --leak-check=full --track-origins=yes --trace-children=yes \
    cubrid server start wmloc
  # ... exercise queries, stop server, then check:
  # - "Invalid read" / "Invalid write" / "Invalid free" = 0 for new-path code
  # - "definitely lost" bytes attributable to new allocations = 0
  ```
  This is the release/production-shaped last line of defense: it validates the structural guarantee (§1) end-to-end (no use-after-copy-replacement, no use-after-close) independent of whether the debug generation counter happened to be compiled in for that run.

## 6. Negative-test plan (P3.6 delta)

ralplan.md P3.6 (line 377-386) specified **4** negative tests, one per original bump-point category, run as `--negative-after-next`, `--negative-after-jump`, `--negative-after-peek-copy`, `--negative-after-close` (ralplan §C, line 668-672). Per §2's reduced bump-point set and §2.1's demotion-exclusion argument, this becomes:

| Test flag | Covers | Rationale |
|---|---|---|
| `--negative-after-page-transition` | Bump-point set row 1 (heap page/copy transition) **and** row 3 (list-scan page transition), **and subsumes the old `--negative-after-jump` case** | Jump is not a separate bump point (§2): `qfile_jump_scan_tuple_position` re-triggers the same detect-and-deform cycle as next/prev (P0.4 §2.3, "jump introduces no new detection path"). A single stale-access-after-page-transition test exercises next, prev, and jump identically because all three funnel through the same retrieval→deform path; jump is covered as a special case of "arrive at a page transition," not tested independently. |
| `--negative-after-close` | Bump-point set row 2 (scan close) | Unchanged from ralplan (`[ralplan-carry]`). |

The old `--negative-after-peek-copy` test is **dropped, not renamed** — per §2.1, the PEEK→COPY demotion category no longer exists for CopiedFrame-sourced ValueSlot entries, so there is no bump point left for it to test. (Legacy live-page-PEEK call sites keep their own existing behavior per §2.1's fallback clause, but that behavior was never a ValueHandle/ValueSlot-contract test target — ralplan's original test exercised `restart_scan_oid`'s effect on a *handle*, and no such handle is constructed on that path.)

**tplrec-overflow hazard test — feasibility assessment**: a classic fail-before-fix negative test (construct a stale-pointer repro, assert it fires) is **not feasible today** for the §3 rule, because the rule is currently dormant: overflow tuples route to the legacy `DB_VALUE` fallback (§3), so no ValueSlot entry is ever sourced from `tplrec` in the mainline design — there is no live handle to invalidate, hence nothing for a runtime assert to catch. Constructing one would require first building the out-of-scope extension (§3's "future work" caveat) purely to test a rule that guards against that same extension, which is backwards. Instead, the feasible form is a **routing-invariant counter test**, structurally identical to D-G6.3's "transcode-path-executed = 0" pattern (grilled_plan.md line 75):

- `--negative-tplrec-invariant` (proposed 3rd test, counter-based rather than assert-based): instrument a debug-only counter incremented at the one place a ValueSlot pointer-type entry *could* be constructed from `tplrec` (the accessor path feeding off `qfile_retrieve_tuple`'s overflow branch, `list_file.c:5330-5338`), and assert the counter is `0` across the full P3.6/P3.7 verification run. This tests the **routing invariant** ("overflow tuples never feed ValueSlot") rather than a stale-pointer repro, which is the only thing feasible to test while the rule remains dormant, and it fails loudly the moment any future change starts routing overflow tuples through ValueSlot without re-opening §3.
- **New (this revision)**: the same counter-test shape now also covers the §1.2/§4 basis invariant via the P3.1 AC's proposed `Num_valueslot_heap_pointer_without_copiedframe` counter (§4) — both are "assert a routing invariant stays at 0" tests over the P3 slice suite, run alongside `--negative-tplrec-invariant` rather than as a 4th named `--negative-*` flag, since neither is a stale-pointer repro in the `--negative-after-*` sense.
- **New (post-UG1 revision)**: the merged `issue154` tree (§4.1) already carries its own debug-only assertions from slice 4 — `assert (!is_cached_scan || scan_cache->page_watcher.pgptr == NULL);` at `heap_file.c:8205` and `heap_file.c:8488` ("latch-free invariant: cached-scan consumption never holds the live page"). **This covers a related but distinct invariant, not this document's routing invariant, and does not substitute for the `Num_valueslot_heap_pointer_without_copiedframe` counter (§4.1's revised P3.1 AC).** The slice-4 assertions check a *page-latching* discipline internal to the cached-scan mechanism itself (that consuming the copy never coincides with holding the live page fixed) — they fire regardless of whether `VALUE_SLOT`/ValueHandle exists at all, since `issue154` predates and is independent of this project's ValueSlot work. This document's proposed counter checks a *different* thing: whether a `VALUE_SLOT` pointer-type cell was ever populated from a heap scan for which `read_mode != HEAP_SCAN_READ_LOCAL_CACHE` — a ValueSlot-layer routing bug that the merged code's own assertions have no visibility into and cannot catch. The two are complementary defenses at different layers; neither is redundant with the other, and both remain in the P3 test plan.

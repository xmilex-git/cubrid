## §(a) ValueSlot (D-G1 replaces per-value ValueHandle)

### a.0 Why ValueHandle is rejected (recap, D-G1)

ralplan.md P1.1(a) specified a per-value `ValueHandle` struct: `{kind, type, len, ≤8B inline-or-ptr,
scan_generation_snapshot}` — roughly 24B per value, self-describing. grilled_plan.md D-G1 rejects
this: it re-invents a lightweight DB_VALUE (fat, per-value, self-describing) and gives up half of
the PG-philosophy gain — PG's `TupleTableSlot` carries type/length/lifetime information *once per
scan* (`tts_tupleDescriptor`, hoisted), not once per value
(`~/dev/postgres/src/include/executor/tuptable.h:129` `tts_tupleDescriptor`). A per-value tag
duplicates that hoisted information N times per row for no benefit; it also re-dispatches type
lookup per value instead of once per column-position, and it re-derives nothing that isn't already
knowable at scan-open time from the column list (`list_id.type_list` for qfile scans,
`attr_info->read_classrepr` for heap scans — see §a.2).

### a.1 ValueSlot: per-scan, not per-value

**ValueSlot replaces ValueHandle as the primary design object.** A ValueSlot is a single struct
owned by the scan (heap scancache or `QFILE_LIST_SCAN_ID`), not one struct per attribute per row.

- The scan owns **three parallel arrays**, each `natts` (or `ceil(natts/8)`) long, allocated once at
  scan open:
  1. `values[natts]` — one 8-byte cell per attribute. Interpretation of each cell (pass-by-value
     payload vs. pointer) is **not self-described** in the cell; it is looked up from the
     column-position-indexed type/class vectors below.
  2. `bound_bits` — one bit per attribute, `1`=bound/non-NULL, `0`=unbound/NULL (bitmap sized to a
     multiple of 8, mirroring `TupleTableSlot.tts_isnull`'s "size must always be rounded up to the
     next multiple of 8" convention, `tuptable.h:133-135`).
  3. `nvalid` — highest attno deformed so far (PG `tts_nvalid` analog, `tuptable.h:126`).
- The scan additionally owns **two column-position-indexed vectors, fixed once at scan open**
  (never touched again for the life of the scan):
  4. `att_types[natts]` (`TP_DOMAIN **`) — column domain per position. Sourced from
     `QFILE_LIST_ID.type_list.domp` (`query_list.h:311-315,431-432`: `TP_DOMAIN **domp; int
     type_cnt;` inside `QFILE_TUPLE_VALUE_TYPE_LIST`, embedded as `type_list` in `QFILE_LIST_ID`)
     for list-file scans, or `HEAP_CACHE_ATTRINFO.read_classrepr` (`heap_attrinfo.h:57-70`, an
     `OR_CLASSREP *` holding the `OR_ATTRIBUTE[]` array, each with `.domain`/`.is_fixed`/`.location`,
     `object_representation_sr.h:89-129`) for heap scans. Both sources are themselves already
     fixed once per scan lifetime in the existing engine (list types at `qfile_open_list`; class
     representation cached and pinned by `heap_attrinfo_start`'s indexing into the classrepr
     cache) — ValueSlot does not introduce a new "fix-once" mechanism, it *reuses* the one that
     already exists and hoists the *type dispatch decision* onto it.
  5. `att_class[natts]` — one of `{FL_INLINE, NUMERIC_DECODED, VC_RAW, VC_COMPRESSED, FALLBACK}`
     per column position, derived from `att_types[i]` (+ `attrepr->is_fixed` for heap,
     `attrepr` compression eligibility for VARCHAR/CHAR ≥
     `OR_MINIMUM_STRING_LENGTH_FOR_COMPRESSION`=255, `object_representation.h:1384`, verified
     `p0.1-coordinates.md` row 25) at scan open. This is schema-level information hoisted to scan
     granularity exactly like `att_types` — it is **not** a per-value tag, and it does not
     reintroduce the rejected ValueHandle's `kind`/`type` fields: no value cell carries it, every
     cell is interpreted by looking up `att_class[attno]` from the shared vector.

"Handle" = the slot entry itself (`values[attno]`, an 8-byte cell: a value or a pointer), consulted
through `att_types[attno]`/`att_class[attno]`. There is no separate self-describing per-value
object. This is the direct CUBRID analog of PG's `tts_values`/`tts_isnull` pair
(`tuptable.h:131-135`) keyed by the slot's single shared `tts_tupleDescriptor`.

### a.2 Deform-once, incremental (PG `tts_nvalid` analog)

Deform happens **once per row**, incrementally, up to the maximum attno actually requested by the
current row's evaluation — not once per attribute access. This mirrors PG's
`slot_deform_heap_tuple` exactly:

> "This is essentially an incremental version of `heap_deform_tuple`: on each call we extract
> attributes up to the one needed, without re-computing information about previously extracted
> attributes. `slot->tts_nvalid` is the number of attributes already extracted."
> (`~/dev/postgres/src/backend/executor/execTuples.c:1004-1007`, function `slot_deform_heap_tuple`,
> signature at `execTuples.c:1017-1018`)

**Correction to the grilled_plan/task citation**: the assignment cites `heaptuple.c:1246-1315` for
this routine; in the current `~/dev/postgres` tree, `heaptuple.c:1253-1254` (`heap_deform_tuple`) is
the **non-incremental, all-at-once** deform used by callers with no slot (e.g. system catalog
lookups) — the incremental, `tts_nvalid`-tracking routine PG actually uses for query-execution slots
is `slot_deform_heap_tuple` in `execTuples.c:996-1018+` (declared `execTuples.c:75-76`, called from
the three concrete slot kinds at `execTuples.c:352`/`550`/`757`). ValueSlot's incremental-deform
requirement is grounded against `execTuples.c:996-1018` (function contract) and
`tuptable.h:126`/`281`/`319` (`tts_nvalid`/`off` saved-state fields), not the cited `heaptuple.c`
range — flagging as a plan-citation correction, not a design change: the semantics ValueSlot needs
("deform up to the highest requested attno, remember where we stopped, resume from there next call")
are exactly `slot_deform_heap_tuple`'s contract regardless of which PG file it lives in.

ValueSlot's `nvalid` field is the direct analog of PG's `tts_nvalid` (`tuptable.h:126`) combined
with the saved `off`/byte-cursor state PG keeps per slot type (`tuptable.h:281,319`, "saved state
for `slot_deform_heap_tuple`"): CUBRID's heap-record layout is *not* single-pass-byte-cursor for
mixed fixed/variable columns the way PG's is (fixed attrs are direct-offset via
`OR_ATTRIBUTE.location`, variable attrs go through the variable-offset table,
`heap_attrvalue_point_variable`, `heap_file.c:10437-10466`), so ValueSlot's per-row deform loop
walks `att_types[nvalid..reqnatts)` and, per position, dispatches on `att_class[i]` (§a.3) rather
than tracking a single running byte offset — but the **contract is identical**: never re-derive
information for attnos `< nvalid`, extend `nvalid` monotonically within a row, reset `nvalid = 0`
on the next row (`qfile_scan_next`/heap scan advance).

### a.3 Per-`att_class` deform behavior

| `att_class` | Deform action (once per row, first access up to that attno) | `values[attno]` after deform |
|---|---|---|
| `FL_INLINE` (9 fixed types) | Read raw bytes at the column's fixed offset (heap: `OR_ATTRIBUTE.location`, direct; qfile: tuple's fixed-offset region), apply **one** `OR_GET_*` byteswap macro. Byteswap macros verified at `object_representation.h:102-131` (`OR_GET_SHORT`…`OR_GET_BIGINT`, covers SHORT/INT/BIGINT/FLOAT/DOUBLE) and `object_representation.h:171-210` (`OR_GET_TIME`…`OR_GET_DATETIME`, covers TIME/DATE/TIMESTAMP/DATETIME) — the 9-type set itself is `spec.md` finding f12: `INT/SHORT/BIGINT/FLOAT/DOUBLE/DATE/TIME/TIMESTAMP/DATETIME`. | The native-endian 8B (or narrower, zero/sign-extended into the 8B cell) value, pass-by-value. |
| `NUMERIC_DECODED` | Decode once via the disk-format parse in `mr_data_readval_numeric` (`object_primitive.c:8760-8836`): 3-byte header (`NUMERIC_HEADER_SIZE`, `object_primitive.c:131`) + variable-length truncated magnitude tail, reconstructed into a `DB_C_NUMERIC`-shaped 17-byte buffer (`DB_NUMERIC_BUF_SIZE`, `dbtype_def.h:647`) that the slot owns (not palloc'd/freed per access). | Pointer into slot-owned decode-once storage (never the raw disk bytes). See §sort-entry for the Datum1Cache int64-proxy treatment of this same storage. |
| `VC_RAW` (uncompressed VARCHAR/CHAR) | No materialization at all — just resolve the pointer (heap: `heap_attrvalue_point_variable`'s pointer-resolution logic, `heap_file.c:10450-10452`; qfile: `qfile_locate_tuple_value`, same as `fetch.c:4048`'s existing peek call). | Pointer directly into the live/CopiedFrame page (lifetime governed by P1.1(b)/D-G2, see §a.5). Zero-copy. |
| `VC_COMPRESSED` (VARCHAR/CHAR ≥255B, `object_representation.h:1384`) | **Lazy**: at deform time, store only a pointer to the raw compressed payload (no decompression yet). Decompression happens on **first actual access** that needs plain bytes (compare/filter needing byte content, not pointer-equality pass-through), into a **per-scan scratch buffer** (`db_private_alloc` per scan thread, one buffer reused across rows of the same scan — SSOT §4.3 pattern). Temp/pass-through paths that never need the decompressed form (`SELECT c_vc` with no predicate on `c_vc`) never pay the decompress cost. | Pointer: either still-compressed raw payload (not yet accessed) or the per-scan scratch buffer (accessed at least once this row). |
| `FALLBACK` | No slot participation. Attribute continues through the existing `heap_attrvalue_transform_to_dbvalue` (`heap_file.c:10478-10538`) / `fetch.c` `TYPE_POSITION` (`fetch.c:4039-4065`) DB_VALUE path unchanged. | N/A — `values[attno]` is unused for this column; consumers must check `att_class[attno] == FALLBACK` and read the parallel legacy `DB_VALUE` instead. |

`FALLBACK` is selected per-column at scan open for: overflow records (`REC_BIGONE`), MVCC old
row versions, unsupported types (BLOB/CLOB, SET/MULTISET/SEQUENCE, BIT/VARBIT, OID/CLASSOID —
i.e. everything not in `{9 FL types, NUMERIC, CHAR, VARCHAR}`), and **qfile overflow tuples**
(`QFILE_OVERFLOW_TUPLE_COUNT_FLAG`, `query_list.h:280`) — see §a.6.

### a.4 `[P0-CONDITIONAL]` — what deform-once actually eliminates, given P0.3's finding

**P0 finding 1 (must be honored explicitly)**: `p0.3-peek-copy-profile.md` §2 shows
`heap_attrvalue_read` (`heap_file.c:10490`, the sole caller of both instrumented functions)
**unconditionally chains peek→copy on every attribute access**:

```c
if (attrepr->is_fixed) heap_attrvalue_point_fixed (...);      /* peek: locate raw bytes */
else                    heap_attrvalue_point_variable (...);   /* peek: locate raw bytes */
return heap_attrvalue_transform_to_dbvalue (value, attrepr, &raw);  /* copy: always called */
```

This makes the literal peek/copy ratio structurally `0.5` for every query (measured: Q1/Q2/Q3 all
report exactly `0.500` for both fixed and variable, `p0.3-peek-copy-profile.md` §3) — **it is not a
headroom signal**, and the "existing peek paths already avoid some copies" claim in ralplan's
Decision Driver #1 does not describe this call chain. `heap_attrvalue_read` never skips
`transform_to_dbvalue`; there is no existing fast path here to preserve or lose.

**`[P0-CONDITIONAL]`** — Given that finding, the concrete, honest claim for what ValueSlot's
deform-once *does* eliminate at this exact boundary is narrower than "avoids the copy": it
eliminates ***repeat*** invocations of `heap_attrvalue_point_fixed`/`_variable` +
`heap_attrvalue_transform_to_dbvalue` for the **same attribute accessed more than once within the
same row's evaluation** — e.g. a column referenced by both a predicate and the SELECT list, or by
both a predicate and an ORDER BY key, is today re-peeked-and-re-copied via `heap_attrvalue_read`
once per `regu_variable` reference (each such reference independently calls into the fetch/attrinfo
machinery); under ValueSlot, the first reference populates `values[attno]` and every subsequent
reference to that attno within the row is an array read, zero calls into
`heap_attrvalue_point_*`/`transform_to_dbvalue`. The **first** access per attribute per row still
pays one peek+one materialize-into-slot-storage — this is structurally unavoidable (the heap→slot
boundary crossing) and is *not* eliminated, only the redundant re-crossings are. Whether this
"multiple regu_variable references to the same column" pattern is common enough to matter is a P2/P3
empirical question (not measured by P0.3, whose queries reference each column at most twice —
predicate + one projection/sort column); this decision's payoff is conditional on that P0.3
workload shape generalizing, hence the `[P0-CONDITIONAL]` tag.

For the three non-fallback pointer/decode categories the elimination is stronger and less
conditional: `VC_RAW` skips DB_VALUE materialization *entirely* (today's chain always calls
`transform_to_dbvalue` even for a pure pointer-peek use — see §(c) point 1), and `NUMERIC_DECODED`
and `VC_COMPRESSED` turn an *unconditional-every-read* cost into a *first-read-only* cost within
the row.

### a.5 Lifetime boundary (owned by P1.1(b)/D-G2 — noted here for completeness only)

Pointer-valued `values[attno]` cells (`VC_RAW`, `VC_COMPRESSED`-before-first-decompress) are bound
to whatever page-lifetime basis P1.1(b) defines: live-page PEEK today, or a scan-owned
`CopiedFrame` once the `issue154-page-copy-heap-scan` workstream lands (not on `develop` as of
2026-07-09, per this task's context). ValueSlot's incremental-deform structure is orthogonal to
that choice — `nvalid` resets to 0 on every row advance, so pointer cells are always re-derived at
the *next* row's deform regardless of which basis backs them; a slot never needs to "know" about a
page transition mid-row because there is no cross-row caching of pointer cells to invalidate. The
one boundary case that *is* mid-row-relevant is the compressed-varchar per-scan scratch buffer
(§a.3, `VC_COMPRESSED`): it is reused across rows of the same scan, so its contents (not its
existence) change on each row's first-decompress — a consumer holding a raw pointer into that
scratch buffer across a row boundary without re-deforming has a use-after-overwrite bug, structurally
identical to the qfile `tplrec` hazard in §a.6.

### a.6 `[P0-CONDITIONAL]` — overflow tuples: why `FALLBACK`, and a lifetime hazard beyond D-G2's bump-point set

**P0 finding 5 (must be honored)**: `p0.4-overflow-audit.md` §2.2/§3.3 establishes that qfile
overflow tuples are **already always force-copied on read regardless of peek/copy intent**
(`qfile_retrieve_tuple`, `list_file.c:5304-5350`: the overflow branch calls
`qfile_get_tuple_from_current_list` unconditionally for both peek and copy) — there is no live-page
pointer to peek into for an overflow tuple's field in the first place, so `VC_RAW`/`VC_COMPRESSED`
pointer semantics have nothing to attach to. This alone would already justify `FALLBACK` for
overflow tuples per ralplan's original design (line 149), but P0.4 surfaces something the plan's
existing bump-point enumeration does not name:

> "`scan_id_p->tplrec` (`query_list.h:514`) is grown/overwritten by `qfile_reallocate_tuple` each
> time the *same* scan encounters a *new* overflow tuple, independent of the page-transition bump
> point... A `ValueHandle`/slot entry built by peeking a field out of an overflow tuple's reassembled
> bytes is safe only until the *next* overflow tuple on the same scan is retrieved — a
> same-page-generation, no-jump, no-explicit-transition invalidation event."
> (`p0.4-overflow-audit.md` §3.3 point 4, condensed)

**`[P0-CONDITIONAL]`** — ValueSlot's design decision here is: **overflow-tuple columns are
`FALLBACK`-classed at scan open, unconditionally, and no slot cell (pointer or otherwise) is ever
populated from `tplrec`-backed bytes.** This decision is directly conditional on the P0.4 finding
above: if a future revision were to attempt `VC_RAW`-style pointer peeking into `tplrec` (e.g. to
capture the "detoast-once" win for a wide compressed VARCHAR that happens to overflow), it would
need a **sixth bump-point class** ("next overflow tuple on same scan", distinct from and stricter
than the existing four: next/jump, page release/transition, PEEK→COPY demotion retry, scan close) —
this design does not add that class; it avoids the problem by keeping overflow columns off the slot
entirely, deferring to whatever lifetime the existing legacy fallback path already has. Should P3
ever want to reconsider (unlikely — P0.2/D-G6 already found overflow tuples are rare on realistic
schemas, and `qfile_copy_tuple`'s "overflow tuples are already-legacy-so-exempt" special case in
P0.4 §3.3 point 3 only applies to bytes on the wire, not to slot lifetime), it must design that sixth
bump-point class first.

## §sort-entry — Datum1Cache (D-G4)

### s.1 What PG does, and what stage 1 takes

PG's `SortTuple` inlines the first sort key into the sort entry itself:

```c
typedef struct
{
  void  *tuple;      /* the tuple itself */
  Datum  datum1;      /* value of first key column */
  bool   isnull1;
  uint8  curbyte;      /* abbreviated-key radix-sort state — NOT taken in stage 1, see D-G5 */
  int    srctape;
} SortTuple;
```
(`~/dev/postgres/src/include/utils/tuplesort.h:114-121`)

> "Storing the first key column lets us save `heap_getattr`/`index_getattr` calls during tuple
> comparisons... for a pass-by-reference datatype, `datum1` points into the 'tuple' storage... When
> sorting single Datums, [for pass-by-value types] the data value is represented directly by
> `datum1`... If the datatype is pass-by-reference..., then `tuple` points to a separately palloc'd
> data value... 'tuple' is always used in preference to `datum1` as the authoritative value for
> pass-by-reference cases." (`tuplesort.h:94-112`)

**D-G4 scope for stage 1**: take PG's *first tier* only — inline the first sort key's value into the
sort entry's 8B `datum1`-equivalent slot when the type allows it losslessly; fall back to a pointer
into slot-owned storage otherwise. **Not** taken: abbreviated key (opclass-level lossy proxy +
tie-break + abort cost model, `sortsupport.h:172`) and radix sort — explicitly deferred to
campaign/bench sub-cell by D-G5.

The natural CUBRID home for this is the ValueSlot itself: at sort-entry construction, pull
`values[first_sort_key_attno]` straight out of the already-deformed slot (§(a)) into the sort
entry's inline cell. No new deform path — this is a read of a cell ValueSlot already populated.

### s.2 Sort-entry inline cell design

```c
typedef struct sort_entry
{
  void      *tuple;      /* authoritative full record — disk-direct image, unchanged serialization */
  uint64_t   datum1;      /* first-sort-key inline cache, D-G4. Meaning depends on att_class of the
                            * first sort key column (fixed once for the whole sort operation, since
                            * one sort has one fixed key-column list): */
  bool       isnull1;
  /* NO curbyte/abbreviated-key state — D-G5 defers this to campaign */
} SORT_ENTRY;
```

Per `att_class` of the first sort key:

| First-key `att_class` | `datum1` content | Comparator behavior |
|---|---|---|
| `FL_INLINE` (9 types) | The exact deformed value (native-endian 8B, or narrower zero/sign-extended). Free — already sitting in `values[attno]`. | Full `datum1`-vs-`datum1` integer/float compare, no tuple touch. |
| `NUMERIC_DECODED`, precision ≤ 18 | **Exact signed int64 of the unscaled value** (see §s.3) — a lossless, not abbreviated, proxy. | Full `datum1`-vs-`datum1` int64 compare, no tuple touch, whenever both sides carry a valid proxy (same column ⇒ always). |
| `NUMERIC_DECODED`, precision 19-40 | Pointer to slot-owned decode-once `DB_C_NUMERIC` storage (§a.3) — `tuple`-authoritative, PG pass-by-ref pattern. | Falls through to the existing `numeric_db_value_compare` / `mr_data_cmpdisk_numeric` machinery once per comparison (no new cost beyond what decode-once already saved at §a.3/§(c)). |
| `VC_RAW`/`VC_COMPRESSED` | Pointer to slot-owned peek/detoast storage — `tuple`-authoritative, PG pass-by-ref pattern (no 8B prefix abbreviation — that is D-G5's abbreviated key, out of scope stage 1). | Falls through to full string/disk-direct compare (`list_file.c:4505`, `subkey->sort_f = ...->get_data_cmpdisk_function()`), but compares against the **already-decompressed-once** buffer for `VC_COMPRESSED` rather than re-decompressing per comparison (see §s.4). |
| `FALLBACK` | N/A — sort entry carries the legacy `DB_VALUE`/tuple path unchanged, no `datum1`. | Legacy comparator, unchanged. |

### s.3 NUMERIC int64 proxy — concrete verdict

**Task**: grilled_plan.md §5 explicitly delegates this decision to P1 ("NUMERIC datum1 int64 프록시
가부: P1 판단"). This section gives the verdict.

**Format analysis** (`object_primitive.c:8706-8880`, per this task's required grounding):

- On-disk NUMERIC = 3-byte header (`NUMERIC_HEADER_SIZE`, `object_primitive.c:131`) + a
  variable-length, **leading-zero-truncated** magnitude tail. `mr_data_writeval_numeric`
  (`object_primitive.c:8706-8751`) writes `header[0]` = `disk_size | sign_bit`, `header[1]` =
  `precision (| scale_sign_bit)`, `header[2]` = `|scale|`, then
  `or_put_data(buf, numeric + (DB_NUMERIC_BUF_SIZE - disk_size), disk_size - NUMERIC_HEADER_SIZE)`
  — i.e. only the trailing (least-significant) bytes of the internal magnitude buffer that are
  actually needed for *this value's* magnitude are written; smaller values physically use fewer
  disk bytes even within one fixed-precision column.
- The internal magnitude buffer is `DB_C_NUMERIC` = `unsigned char[DB_NUMERIC_BUF_SIZE]`,
  `DB_NUMERIC_BUF_SIZE = 17` (`dbtype_def.h:647`), **unsigned magnitude only** — sign is tracked
  separately (`DB_VALUE_NUMERIC_IS_VALUE_NEGATIVE`), stored big-endian
  (`numeric_opfunc.c:25-26`: "the LSB's of the DB_NUMERIC are in `buf[DB_NUMERIC_BUF_SIZE-1]`").
  Maximum declarable precision is 40 digits (`DB_MAX_NUMERIC_PRECISION`, `dbtype_def.h:589`).
  `mr_get_fixed_numeric_size` (`object_primitive.c:8913-8973`) treats `buf[0]` as reserved/pad and
  the remaining 16 bytes (`buf[1..16]`) as two big-endian `uint64_t` words for a fast CTZ/CLZ-based
  magnitude-size computation — confirming the engine itself already treats the "real" magnitude as
  fitting in ≤128 bits (2 machine words) for its own internal fast paths.
- `mr_data_readval_numeric` (`object_primitive.c:8760-8836`) is exactly the P0-evidence-cited
  "decode-once" restoration this design's §a.3 relies on: it reconstructs the full `DB_C_NUMERIC`
  buffer from the truncated disk bytes via `db_make_numeric`, once per row, into slot-owned storage.

**Verdict — conditional, exact (not abbreviated) proxy, split at precision 18**:

Because **scale is a domain (column) property, fixed for every row a single sort compares against
every other row** (a `NUMERIC(15,2)` column has scale `2` for all 500K rows in a `NUM-sort`
bench cell — there is no cross-scale normalization problem to solve, unlike a generic
type-erased comparator), same-scale decimal ordering is *identical* to signed-integer ordering
of the unscaled value (`sign * magnitude`, i.e. the value with the decimal point removed). This is
a stronger result than the "sign + scale-normalized leading digits" framing in the assignment
implies: for columns within the safe range there is **no truncation or leading-digit
approximation at all** — the proxy is the exact value, and two `datum1` cells can be compared with
a plain signed 64-bit comparison and the result is *always* correct, never a "probably correct,
verify against `tuple`" abbreviated-key situation.

- **Safe range**: unscaled magnitude fits in a signed 64-bit int (max positive value
  `9223372036854775807 ≈ 9.223×10^18`) whenever the column's declared precision `p ≤ 18` (the
  largest 18-digit magnitude, `999999999999999999 ≈ 9.999×10^17`, is unconditionally smaller than
  the `int64` max for *every* value of that precision — this is a per-domain guarantee, not a
  per-value gamble). At `p = 19` a single value could still fit, but not *every* value of that
  precision can, so `p ≤ 18` is the conservative, always-safe cutoff. `p ≤ 18` covers the
  overwhelming majority of realistic schemas, including this project's own P0.3 fixture
  (`NUMERIC(15,2)`) and TPC-H's `DECIMAL` columns (`p=15` typically) — i.e. it covers exactly the
  W2 (NUM-sort) headroom target grilled_plan §4 names.
  - **Construction** (design, not yet implemented): given the slot-owned decode-once
    `DB_C_NUMERIC` buffer (`buf[0..16]`) and `is_value_negative`, read the low 8 bytes
    (`buf[9..16]`, guaranteed all-zero above that for `p ≤ 18` per the CTZ/CLZ argument above)
    as a big-endian `uint64_t`, byteswap to native (same one-time bswap treatment as the 9 `FL_INLINE`
    types, §a.3), cast to `int64_t`, negate if `is_value_negative`. This is a pure register op on
    already-decoded storage — no additional disk read, no additional `data_readval` call.
- **Unsafe range**: `p` in `[19, 40]` — magnitude can need up to 16 bytes (128 bits), no lossless
  64-bit encoding exists (and this stage does not want a lossy/abbreviated one — that is D-G5's
  territory, out of scope). **Grounded rejection for this sub-range only**: `datum1` for such a
  column is a pointer to the slot-owned decode-once storage (§a.3), i.e. the `VC_RAW`-shaped
  fallback row in the table above, not the `FL_INLINE`-shaped fast path. The comparator falls back
  to the existing `numeric_db_value_compare`/`mr_data_cmpdisk_numeric` path, but — critically —
  against the **already-decoded** buffer, so this sub-range still gets the decode-once win (§a.3),
  just not the `datum1`-only-compare win.

**Net**: this is not a binary accept/reject — it is a precision-gated design with an exact
lossless fast path for `p ≤ 18` and a grounded, decode-once-preserving fallback for `p ∈ [19,40]`.
Implementers should compute the split once per column at slot/sort-entry setup (reading the
column's static `precision` from its domain, `att_types[attno]->precision`), not per value.

### s.4 Interplay with disk-direct sort compare and R2 mitigation

Two existing mechanisms this design must not regress or duplicate:

- **Disk-direct sort compare** (`list_file.c:4505`, `subkey->sort_f =
  ...->get_data_cmpdisk_function()`, verified `p0.1-coordinates.md` row 29): today's sort assigns a
  disk-direct comparator per key column that operates on raw, still-serialized bytes with **zero**
  intermediate `DB_VALUE`/slot materialization — this is the *fastest* path that exists today for
  non-first-key columns and remains completely untouched by Datum1Cache. Datum1Cache only changes
  the **first** key's comparison path (§s.2); columns 2..N of a multi-key sort continue to use
  `get_data_cmpdisk_function()` exactly as today. This is why the comparator table in §s.2 says
  "falls through to the existing machinery" rather than proposing a new one.
- **R2 mitigation** (grilled_plan.md §3 Risks: "sort-ingestion decompress inflation"): R2's concern
  is that preparing a compressed VARCHAR for sorting inflates memory/CPU by decompressing at
  ingestion. Datum1Cache's `VC_COMPRESSED` row (§s.2) explicitly does **not** decompress the tuple
  body to build the sort entry — `tuple` keeps pointing at (still-compressed, or first-touch-detoasted
  per §a.3) slot storage, and only an 8B pointer goes into the sort array. This is the mechanism
  grilled_plan §2 D-G4 names directly: "본체는 압축 유지, 8B 프록시만 정렬 배열에" (the body stays
  compressed; only the 8B proxy goes into the sort array) — here the "8B proxy" for VARCHAR is a
  pointer (to already-decode-once storage), not an inline value, which is consistent with PG's own
  pass-by-reference `SortTuple` semantics (`tuplesort.h:107-112`) and avoids re-decompressing per
  comparison during the sort's `O(N log N)` compare phase — the exact amplification pattern P0
  evidence identifies at `object_primitive.c:11897-11960` (`mr_cmpdisk_char_type_common`,
  per-comparison `db_private_alloc` + decompress).

### s.5 Polymorphic sort utilities cannot carry a format tag — class must thread from the caller

Per this task's required P0 context: `qfile_sort_list_with_func` (`list_file.c:4654`) and the
other polymorphic sort/merge utilities cannot statically know at compile time whether they are
sorting a class-(d) forward-only intermediate or a class-(a) client-visible result — the class is a
property of the *caller's* `QFILE_LIST_ID`, not of the sort function. Datum1Cache is **class-agnostic
by construction**: it operates purely on `att_types`/`att_class` (schema-level, always available
regardless of list class) and the already-deformed `values[]` array — it has no dependency on
`format_version`/class tagging at all. This is a structural advantage over the temp-framing
workstream (P1.1(d)/(e), owned by a sibling task): Datum1Cache applies identically whether the
underlying list ends up legacy- or new-framed, because it operates one layer above the tuple's wire
format (on deformed slot values, not on tuple bytes).

## §(a) ValueSlot (D-G1 replaces per-value ValueHandle)

### a.0 Why ValueHandle is rejected (recap, D-G1)

ralplan.md P1.1(a) specified a per-value `ValueHandle` struct: `{kind, type, len, ≤8B inline-or-ptr,
scan_generation_snapshot}` — roughly 24B per value, self-describing. grilled_plan.md D-G1 rejects
this: it re-invents a lightweight DB_VALUE (fat, per-value, self-describing) and gives up half of
the PG-philosophy gain — PG's `TupleTableSlot` carries type/length/lifetime information *once per
scan* (`tts_tupleDescriptor`, hoisted), not once per value
(`~/dev/postgres/src/include/executor/tuptable.h:129` `tts_tupleDescriptor`). A per-value tag
duplicates that hoisted information N times per row for no benefit; it also re-dispatches type
lookup per value instead of once per column-position, and it re-derives nothing that isn't already
knowable at scan-open time from the column list (`list_id.type_list` for qfile scans,
`attr_info->read_classrepr` for heap scans — see §a.2).

### a.1 ValueSlot: per-scan, not per-value

**ValueSlot replaces ValueHandle as the primary design object.** A ValueSlot is a single struct
owned by the scan (heap scancache or `QFILE_LIST_SCAN_ID`), not one struct per attribute per row.

- The scan owns **three parallel arrays**, each `natts` (or `ceil(natts/8)`) long, allocated once at
  scan open:
  1. `values[natts]` — one 8-byte cell per attribute. Interpretation of each cell (pass-by-value
     payload vs. pointer) is **not self-described** in the cell; it is looked up from the
     column-position-indexed type/class vectors below.
  2. `bound_bits` — one bit per attribute, `1`=bound/non-NULL, `0`=unbound/NULL (bitmap sized to a
     multiple of 8, mirroring `TupleTableSlot.tts_isnull`'s "size must always be rounded up to the
     next multiple of 8" convention, `tuptable.h:133-135`).
  3. `nvalid` — highest attno deformed so far (PG `tts_nvalid` analog, `tuptable.h:126`).
- The scan additionally owns **two column-position-indexed vectors, fixed once at scan open**
  (never touched again for the life of the scan):
  4. `att_types[natts]` (`TP_DOMAIN **`) — column domain per position. Sourced from
     `QFILE_LIST_ID.type_list.domp` (`query_list.h:311-315,431-432`: `TP_DOMAIN **domp; int
     type_cnt;` inside `QFILE_TUPLE_VALUE_TYPE_LIST`, embedded as `type_list` in `QFILE_LIST_ID`)
     for list-file scans, or `HEAP_CACHE_ATTRINFO.read_classrepr` (`heap_attrinfo.h:57-70`, an
     `OR_CLASSREP *` holding the `OR_ATTRIBUTE[]` array, each with `.domain`/`.is_fixed`/`.location`,
     `object_representation_sr.h:89-129`) for heap scans. Both sources are themselves already
     fixed once per scan lifetime in the existing engine (list types at `qfile_open_list`; class
     representation cached and pinned by `heap_attrinfo_start`'s indexing into the classrepr
     cache) — ValueSlot does not introduce a new "fix-once" mechanism, it *reuses* the one that
     already exists and hoists the *type dispatch decision* onto it.
  5. `att_class[natts]` — one of `{FL_INLINE, NUMERIC_DECODED, VC_RAW, VC_COMPRESSED, FALLBACK}`
     per column position, derived from `att_types[i]` (+ `attrepr->is_fixed` for heap,
     `attrepr` compression eligibility for VARCHAR/CHAR ≥
     `OR_MINIMUM_STRING_LENGTH_FOR_COMPRESSION`=255, `object_representation.h:1384`, verified
     `p0.1-coordinates.md` row 25) at scan open. This is schema-level information hoisted to scan
     granularity exactly like `att_types` — it is **not** a per-value tag, and it does not
     reintroduce the rejected ValueHandle's `kind`/`type` fields: no value cell carries it, every
     cell is interpreted by looking up `att_class[attno]` from the shared vector.

"Handle" = the slot entry itself (`values[attno]`, an 8-byte cell: a value or a pointer), consulted
through `att_types[attno]`/`att_class[attno]`. There is no separate self-describing per-value
object. This is the direct CUBRID analog of PG's `tts_values`/`tts_isnull` pair
(`tuptable.h:131-135`) keyed by the slot's single shared `tts_tupleDescriptor`.

### a.2 Deform-once, incremental (PG `tts_nvalid` analog)

Deform happens **once per row**, incrementally, up to the maximum attno actually requested by the
current row's evaluation — not once per attribute access. This mirrors PG's
`slot_deform_heap_tuple` exactly:

> "This is essentially an incremental version of `heap_deform_tuple`: on each call we extract
> attributes up to the one needed, without re-computing information about previously extracted
> attributes. `slot->tts_nvalid` is the number of attributes already extracted."
> (`~/dev/postgres/src/backend/executor/execTuples.c:1004-1007`, function `slot_deform_heap_tuple`,
> signature at `execTuples.c:1017-1018`)

**Correction to the grilled_plan/task citation**: the assignment cites `heaptuple.c:1246-1315` for
this routine; in the current `~/dev/postgres` tree, `heaptuple.c:1253-1254` (`heap_deform_tuple`) is
the **non-incremental, all-at-once** deform used by callers with no slot (e.g. system catalog
lookups) — the incremental, `tts_nvalid`-tracking routine PG actually uses for query-execution slots
is `slot_deform_heap_tuple` in `execTuples.c:996-1018+` (declared `execTuples.c:75-76`, called from
the three concrete slot kinds at `execTuples.c:352`/`550`/`757`). ValueSlot's incremental-deform
requirement is grounded against `execTuples.c:996-1018` (function contract) and
`tuptable.h:126`/`281`/`319` (`tts_nvalid`/`off` saved-state fields), not the cited `heaptuple.c`
range — flagging as a plan-citation correction, not a design change: the semantics ValueSlot needs
("deform up to the highest requested attno, remember where we stopped, resume from there next call")
are exactly `slot_deform_heap_tuple`'s contract regardless of which PG file it lives in.

ValueSlot's `nvalid` field is the direct analog of PG's `tts_nvalid` (`tuptable.h:126`) combined
with the saved `off`/byte-cursor state PG keeps per slot type (`tuptable.h:281,319`, "saved state
for `slot_deform_heap_tuple`"): CUBRID's heap-record layout is *not* single-pass-byte-cursor for
mixed fixed/variable columns the way PG's is (fixed attrs are direct-offset via
`OR_ATTRIBUTE.location`, variable attrs go through the variable-offset table,
`heap_attrvalue_point_variable`, `heap_file.c:10437-10466`), so ValueSlot's per-row deform loop
walks `att_types[nvalid..reqnatts)` and, per position, dispatches on `att_class[i]` (§a.3) rather
than tracking a single running byte offset — but the **contract is identical**: never re-derive
information for attnos `< nvalid`, extend `nvalid` monotonically within a row, reset `nvalid = 0`
on the next row (`qfile_scan_next`/heap scan advance).

### a.3 Per-`att_class` deform behavior

| `att_class` | Deform action (once per row, first access up to that attno) | `values[attno]` after deform |
|---|---|---|
| `FL_INLINE` (9 fixed types) | Read raw bytes at the column's fixed offset (heap: `OR_ATTRIBUTE.location`, direct; qfile: tuple's fixed-offset region), apply **one** `OR_GET_*` byteswap macro. Byteswap macros verified at `object_representation.h:102-131` (`OR_GET_SHORT`…`OR_GET_BIGINT`, covers SHORT/INT/BIGINT/FLOAT/DOUBLE) and `object_representation.h:171-210` (`OR_GET_TIME`…`OR_GET_DATETIME`, covers TIME/DATE/TIMESTAMP/DATETIME) — the 9-type set itself is `spec.md` finding f12: `INT/SHORT/BIGINT/FLOAT/DOUBLE/DATE/TIME/TIMESTAMP/DATETIME`. | The native-endian 8B (or narrower, zero/sign-extended into the 8B cell) value, pass-by-value. |
| `NUMERIC_DECODED` | Decode once via the disk-format parse in `mr_data_readval_numeric` (`object_primitive.c:8760-8836`): 3-byte header (`NUMERIC_HEADER_SIZE`, `object_primitive.c:131`) + variable-length truncated magnitude tail, reconstructed into a `DB_C_NUMERIC`-shaped 17-byte buffer (`DB_NUMERIC_BUF_SIZE`, `dbtype_def.h:647`) that the slot owns (not palloc'd/freed per access). | Pointer into slot-owned decode-once storage (never the raw disk bytes). See §sort-entry for the Datum1Cache int64-proxy treatment of this same storage. |
| `VC_RAW` (uncompressed VARCHAR/CHAR) | No materialization at all — just resolve the pointer (heap: `heap_attrvalue_point_variable`'s pointer-resolution logic, `heap_file.c:10450-10452`; qfile: `qfile_locate_tuple_value`, same as `fetch.c:4048`'s existing peek call). | Pointer directly into the live/CopiedFrame page (lifetime governed by P1.1(b)/D-G2, see §a.5). Zero-copy. |
| `VC_COMPRESSED` (VARCHAR/CHAR ≥255B, `object_representation.h:1384`) | **Lazy**: at deform time, store only a pointer to the raw compressed payload (no decompression yet). Decompression happens on **first actual access** that needs plain bytes, into a **per-scan scratch buffer** (`db_private_alloc` per scan thread, one buffer reused across rows of the same scan — SSOT §4.3 pattern). Temp/pass-through paths that never need the decompressed form never pay the decompress cost. **This deform-time scratch is scoped to non-sort accesses — §s.2.1 explains why a sort's *first* sort-key column cannot use this same reused-per-row buffer as its `datum1` target.** | Pointer: either still-compressed raw payload or the per-scan scratch buffer. |
| `FALLBACK` | No slot participation. Attribute continues through the existing `heap_attrvalue_transform_to_dbvalue` (`heap_file.c:10478-10538`) / `fetch.c` `TYPE_POSITION` (`fetch.c:4039-4065`) DB_VALUE path unchanged. | N/A — consumers must check `att_class[attno] == FALLBACK` and read the parallel legacy `DB_VALUE` instead. |

`FALLBACK` is selected per-column at scan open for: overflow records (`REC_BIGONE`), MVCC old
row versions, unsupported types (BLOB/CLOB, SET/MULTISET/SEQUENCE, BIT/VARBIT, OID/CLASSOID —
i.e. everything not in `{9 FL types, NUMERIC, CHAR, VARCHAR}`), and **qfile overflow tuples**
(`QFILE_OVERFLOW_TUPLE_COUNT_FLAG`, `query_list.h:280`) — see §a.6.

### a.4 `[P0-CONDITIONAL]` — what deform-once actually eliminates, given P0.3's finding

**P0 finding 1 (must be honored explicitly)**: `p0.3-peek-copy-profile.md` §2 shows
`heap_attrvalue_read` (`heap_file.c:10490`, the sole caller of both instrumented functions)
**unconditionally chains peek→copy on every attribute access**:

```c
if (attrepr->is_fixed) heap_attrvalue_point_fixed (...);      /* peek: locate raw bytes */
else                    heap_attrvalue_point_variable (...);   /* peek: locate raw bytes */
return heap_attrvalue_transform_to_dbvalue (value, attrepr, &raw);  /* copy: always called */
```

This makes the literal peek/copy ratio structurally `0.5` for every query (measured: Q1/Q2/Q3 all
report exactly `0.500` for both fixed and variable, `p0.3-peek-copy-profile.md` §3) — **it is not a
headroom signal**, and the "existing peek paths already avoid some copies" claim in ralplan's
Decision Driver #1 does not describe this call chain. `heap_attrvalue_read` never skips
`transform_to_dbvalue`; there is no existing fast path here to preserve or lose.

**`[P0-CONDITIONAL]`** — the concrete, honest claim for what ValueSlot's deform-once *does*
eliminate at this boundary is narrower than "avoids the copy": it eliminates ***repeat***
invocations of `heap_attrvalue_point_fixed`/`_variable` + `heap_attrvalue_transform_to_dbvalue` for
the **same attribute accessed more than once within the same row's evaluation** — under ValueSlot,
the first reference populates `values[attno]` and every subsequent reference within the row is an
array read, zero calls into `heap_attrvalue_point_*`/`transform_to_dbvalue`. The **first** access per
attribute per row still pays one peek+one materialize-into-slot-storage — structurally unavoidable,
*not* eliminated, only the redundant re-crossings are. Whether "multiple regu_variable references to
the same column" is common enough to matter is a P2/P3 empirical question (not measured by P0.3,
whose queries reference each column at most twice); this decision's payoff is conditional on that
P0.3 workload shape generalizing, hence the `[P0-CONDITIONAL]` tag.

For the three non-fallback pointer/decode categories the elimination is stronger and less
conditional: `VC_RAW` skips DB_VALUE materialization *entirely* (today's chain always calls
`transform_to_dbvalue` even for a pure pointer-peek use — see §(c) point 1), and `NUMERIC_DECODED`
and `VC_COMPRESSED` turn an *unconditional-every-read* cost into a *first-read-only* cost within
the row.

### a.5 Lifetime boundary (owned by P1.1(b)/D-G2 — noted here for completeness only)

Pointer-valued `values[attno]` cells (`VC_RAW`, `VC_COMPRESSED`-before-first-decompress) are bound
to whatever page-lifetime basis P1.1(b) defines: live-page PEEK today, or a scan-owned
`CopiedFrame` once the `issue154-page-copy-heap-scan` workstream lands (not on `develop` as of
2026-07-09, per this task's context). ValueSlot's incremental-deform structure is orthogonal to
that choice — `nvalid` resets to 0 on every row advance, so pointer cells are always re-derived at
the *next* row's deform regardless of which basis backs them. The one boundary case that *is*
mid-row-relevant is the compressed-varchar per-scan scratch buffer (§a.3, `VC_COMPRESSED`): it is
reused across rows of the same scan, so a consumer holding a raw pointer into that scratch buffer
across a row boundary without re-deforming has a use-after-overwrite bug, structurally identical to
the qfile `tplrec` hazard in §a.6.

**Basis invariant (`[architect MEDIUM P2]`, pre-UG1 review)**: heap-scan `VC_RAW`/`VC_COMPRESSED`
pointer-type slot columns are **never enabled** for a given heap scan unless a CopiedFrame basis is
actually present for that scan — either the `issue154-page-copy-heap-scan` landing, or
`p1.1-lifetime-contract.md` §4's minimal-scope fallback. This sharpens the paragraph above: "bound to
whatever basis P1.1(b) defines: live-page PEEK today, or CopiedFrame" describes what the **legacy**
`heap_attrvalue_read` chain does, unchanged, on scans ValueSlot does not (yet) cover — "live-page PEEK
today" is not a second, ValueSlot-sanctioned basis for populating `values[attno]` pointer cells. Until
one of the two CopiedFrame-providing mechanisms is active for a heap scan, that scan's
`VC_RAW`/`VC_COMPRESSED` heap columns MUST be classified `FALLBACK` (§a.3) rather than wired onto
live-page PEEK with only the debug-only generation counter (`p1.1-lifetime-contract.md` §5) as
protection — the counter is a detection backstop for a structural guarantee
(`p1.1-lifetime-contract.md` §1.2), never a substitute basis in its own right. Qfile (list-file)
scans are unaffected: their `VC_RAW`/`VC_COMPRESSED` pointer validity already rests on the
independent, always-available "re-deform before next read" structural property
(`p1.1-lifetime-contract.md` §2 row 3), which needs no CopiedFrame. See
`p1.1-lifetime-contract.md` §1.2/§4 for the mechanism and its fallback trigger, and the named P3.1
AC line recorded there alongside this invariant.

### a.6 `[P0-CONDITIONAL]` — overflow tuples: why `FALLBACK`, and a lifetime hazard beyond D-G2's bump-point set

**P0 finding 5 (must be honored)**: `p0.4-overflow-audit.md` §2.2/§3.3 establishes that qfile
overflow tuples are **already always force-copied on read regardless of peek/copy intent**
(`qfile_retrieve_tuple`, `list_file.c:5304-5350`) — there is no live-page pointer to peek into, so
`VC_RAW`/`VC_COMPRESSED` pointer semantics have nothing to attach to. P0.4 additionally finds:

> "`scan_id_p->tplrec` (`query_list.h:514`) is grown/overwritten by `qfile_reallocate_tuple` each
> time the *same* scan encounters a *new* overflow tuple... A `ValueHandle`/slot entry built by
> peeking a field out of an overflow tuple's reassembled bytes is safe only until the *next*
> overflow tuple on the same scan is retrieved."
> (`p0.4-overflow-audit.md` §3.3 point 4, condensed)

**`[P0-CONDITIONAL]`** — overflow-tuple columns are `FALLBACK`-classed at scan open,
unconditionally; no slot cell is ever populated from `tplrec`-backed bytes. This decision is
conditional on the P0.4 finding above: a future `VC_RAW`-style peek into `tplrec` would need a
**sixth bump-point class** ("next overflow tuple on same scan"); this design avoids that by keeping
overflow columns off the slot entirely.

### a.7 Struct sketches — release has NO generation field

D-G1 point 3: "generation is a slot(scan)-level DEBUG-only field. Per-value duplication is
forbidden. The release struct does not include a generation field." Both sketches below show the
*complete* struct:

```c
/* ---- RELEASE build: this is the complete struct, ships in production binaries ---- */
typedef struct value_slot
{
  int          natts;          /* column count, fixed at scan open */
  TP_DOMAIN  **att_types;      /* [natts], fixed once at scan open (§a.2) */
  uint8_t     *att_class;      /* [natts], fixed once at scan open (§a.1) */
  uint64_t    *values;         /* [natts], 8B per attribute: inline value, or pointer */
  uint8_t     *bound_bits;     /* [ceil(natts/8)], 1 = bound, PG tts_isnull polarity inverted */
  int          nvalid;         /* highest attno deformed this row, PG tts_nvalid analog */
  char        *detoast_scratch;    /* per-scan lazy-decompress buffer, VC_COMPRESSED (§a.3). Reused
                                     * every row — NEVER the backing storage for a sort entry's
                                     * datum1 pointer (§s.2.1); sort entries get their own storage. */
  size_t       detoast_scratch_len;
  unsigned char *numeric_scratch;  /* per-slot decode-once storage, NUMERIC_DECODED (§a.3). Same
                                     * reused-per-row caveat as detoast_scratch above (§s.2.1). */
  /* -- NO generation field here. Contract enforcement is structural (D-G2), not counted. -- */
} VALUE_SLOT;

/* ---- DEBUG build (!defined(NDEBUG)): this is the complete struct ---- */
typedef struct value_slot
{
  int          natts;
  TP_DOMAIN  **att_types;
  uint8_t     *att_class;
  uint64_t    *values;
  uint8_t     *bound_bits;
  int          nvalid;
  char        *detoast_scratch;
  size_t       detoast_scratch_len;
  unsigned char *numeric_scratch;
#if !defined (NDEBUG)
  uint32_t     generation;     /* DEBUG-ONLY BACKSTOP (D-G2). Bumped on {page/copy-frame transition,
                                 * scan close}. Accessors assert a caller's remembered snapshot still
                                 * matches this before dereferencing a pointer cell. Never read in a
                                 * release build. */
#endif
} VALUE_SLOT;
```

This exact pattern already exists in this codebase for the P0.3 temporary counters (`heap_file.c`
`vh_p0_peek_count_fixed` etc., guarded identically) — ValueSlot's `generation` field reuses the
established idiom, not a new one.

## §sort-entry — Datum1Cache (D-G4)

### s.1 What PG does, and what stage 1 takes

PG's `SortTuple` inlines the first sort key into the sort entry itself:

```c
typedef struct
{
  void  *tuple;      /* the tuple itself */
  Datum  datum1;      /* value of first key column */
  bool   isnull1;
  uint8  curbyte;      /* abbreviated-key radix-sort state — NOT taken in stage 1, see D-G5 */
  int    srctape;
} SortTuple;
```
(`~/dev/postgres/src/include/utils/tuplesort.h:114-121`)

> "Storing the first key column lets us save `heap_getattr`/`index_getattr` calls during tuple
> comparisons... for a pass-by-reference datatype, `datum1` points into the 'tuple' storage... 'tuple'
> is always used in preference to `datum1` as the authoritative value for pass-by-reference cases."
> (`tuplesort.h:94-112`)

**D-G4 scope for stage 1**: take PG's *first tier* only — inline the first sort key's value into the
sort entry's 8B `datum1`-equivalent slot when the type allows it losslessly; fall back to a pointer
into owned storage otherwise. **Not** taken: abbreviated key (opclass-level lossy proxy + tie-break +
abort cost model, `sortsupport.h:172`) and radix sort — explicitly deferred to campaign/bench
sub-cell by D-G5.

The natural CUBRID home for this is the ValueSlot itself: at sort-entry construction, pull
`values[first_sort_key_attno]` straight out of the already-deformed slot (§(a)) into the sort
entry's inline cell for `FL_INLINE` and the `NUMERIC` p≤18 int64 proxy (§s.3) — both pass-by-value,
no new deform path. **This does not hold for the pointer-valued cases (`VC_COMPRESSED`, `NUMERIC`
p19-40)** — see §s.2.1, where the LEADER DESIGN DECISION's per-entry storage lives, precisely
because those two cases cannot simply "pull the already-populated slot cell."

### s.2 Sort-entry inline cell design

```c
typedef struct sort_entry
{
  void      *tuple;      /* authoritative full record — disk-direct image, unchanged serialization.
                            * Concretely: CUBRID's existing SORT_REC body (`external_sort.h:77-99`),
                            * populated once per row by `qfile_make_sort_key`
                            * (`list_file.c:3617-3744` [VERIFY: live-tree coordinate, see §s.2.1])
                            * into a per-entry slice of the sort's OWN memory budget (§s.2.1) —
                            * never the per-scan `VALUE_SLOT.detoast_scratch`/`numeric_scratch`
                            * fields (§a.3/§a.7). */
  uint64_t   datum1;      /* first-sort-key inline cache, D-G4. Meaning depends on att_class of the
                            * first sort key column (fixed once for the whole sort operation): */
  bool       isnull1;
  /* NO curbyte/abbreviated-key state — D-G5 defers this to campaign */
} SORT_ENTRY;
```

Per `att_class` of the first sort key:

| First-key `att_class` | `datum1` content | Comparator behavior |
|---|---|---|
| `FL_INLINE` (9 types) | The exact deformed value (native-endian 8B, or narrower zero/sign-extended). Free — already sitting in `values[attno]`. | Full `datum1`-vs-`datum1` integer/float compare, no tuple touch. |
| `NUMERIC_DECODED`, precision ≤ 18 | **Exact signed int64 of the unscaled value** (§s.3) — lossless, not abbreviated. | Full `datum1`-vs-`datum1` int64 compare, no tuple touch. |

### s.2.1 Concrete per-entry detoast/decode storage — owner, allocation, lifetime, spill, fallback, R2 accounting

**LEADER DESIGN DECISION** (spec.md f17, "정렬키는 정렬 진입 시 1회 해제(비교당 해제 금지)" —
user-confirmed R14): stage-1 CV-sort/NUM-sort(19-40) = **detoast/decode-once at sort ingestion into
sort-owned per-entry key storage**, distinct from the per-scan one-row `VALUE_SLOT` scratch (§a.3/§a.7).

**Why the ValueSlot scratch cannot back this**: §a.7's release struct carries exactly one
`detoast_scratch`/`numeric_scratch` pointer *per slot*, reused every row (§a.3). A sort must hold up
to `tot_buffers` worth of entries simultaneously during its in-memory run-build phase while comparing
and reordering them — a pointer into a buffer the *next* row's deform overwrites cannot be the
authoritative storage for an entry that must stay valid until the sort is done with it. This is the
same class of hazard §a.5 names for the qfile `tplrec` case, one level up (sort-entry granularity
instead of per-scan-scratch granularity).

**Owner**: the sort operation itself (`SORT_INFO`/`SORTKEY_INFO`/`SORT_PARAM`), not `VALUE_SLOT`.
The real-source analog of the `SORT_ENTRY` sketch (§s.2) is CUBRID's existing `SORT_REC`
(`external_sort.h:77-99`) + `SORTKEY_INFO`/`SUBKEY_INFO` (`external_sort.h:101-140`), built once per
row by `qfile_make_sort_key` (`list_file.c:3617-3744` `[VERIFY]`: live-tree coordinate —
`list_file.c` carries this doc-set's noted live-tree drift from `ebf08d080`, same as
`p1.1-format-selection.md`'s header records; not independently re-derived via `git show` this
session, since `bash`/`find`/`edit` tool access was unavailable — the identical tooling gap that
document's Blockers section records). `qfile_make_sort_key`'s existing "STEP 2: build body" loop
today `memcpy`s each key column's *raw serialized* field bytes (`field_data`,
`QFILE_TUPLE_VALUE_HEADER_SIZE + field_length`) straight into the `SORT_REC` body verbatim — for a
`VC_COMPRESSED`/`NUMERIC` p19-40 first-sort-key column, "raw" today means "still compressed / still
disk-truncated." **The edit is scoped to exactly this one copy step**: for the first-sort-key column
only, when its `att_class` is `VC_COMPRESSED` or `NUMERIC_DECODED` p19-40, `qfile_make_sort_key`
decompresses/decodes into the `SORT_REC` body instead of `memcpy`-ing raw bytes — same destination,
one extra `att_class` dispatch. The decompression call is the existing
`pr_get_compressed_data_from_buffer` (`object_primitive.c:13691-13725`, wraps
`cubcompress::decompress<cubcompress::LZ4>`) — the **same routine** `mr_cmpdisk_char_type_common`
calls today once *per comparison* (`object_primitive.c:11897-11960`); this design calls it once *per
entry build* and keeps the result durably.

**Allocation source — "the sort's memory budget," identified concretely**: `qfile_make_sort_key`'s
destination `RECDES` is a bump-allocated slice of `sort_param->internal_memory`, the sort's single
fixed in-memory work buffer, sized at `external_sort.c:1434-1441`:
```c
/* external_sort.c:1427-1441 (undrifted from ebf08d080) */
input_pages = prm_get_integer_value (PRM_ID_SR_NBUFFERS);                                 /* :1434 */
sort_param->tot_buffers = MIN (prm_get_integer_value (PRM_ID_SR_NBUFFERS), input_pages);   /* :1438 */
sort_param->tot_buffers = MAX (4, sort_param->tot_buffers);                                /* :1439 */
sort_param->internal_memory = (char *) malloc ((size_t) sort_param->tot_buffers * (size_t) DB_PAGESIZE);  /* :1441 */
```
`PRM_ID_SR_NBUFFERS` is the deprecated alias kept in lockstep with `sort_buffer_size`/
`PRM_ID_SORT_BUFFER_SIZE` (`system_parameter.c:1130-1144`,`5397`). This `tot_buffers * DB_PAGESIZE`
region **is** "the sort's memory budget": every in-memory-phase `SORT_REC` — including the
decompressed/decoded key body this design writes — is carved out of it by bump-pointer allocation
inside the sort's internal-sort loop (`item_ptr`/`index_buff`, `external_sort.c:1945-1970`), never
from `VALUE_SLOT`'s per-scan scratch.

**Lifetime**: entry build (the `qfile_make_sort_key` call, writing key bytes into its slice of
`sort_param->internal_memory`, or — once spilled — into a run file) → sort end, concretely
`sort_return_used_resources` (`external_sort.c:4218-4232`), which `free_and_init`s
`sort_param->internal_memory` at line 4232 (parallel workers identically at `external_sort.c:4519`).
Strictly longer-lived than the per-scan `VALUE_SLOT` scratch buffers, which are reused every row.

**Spill policy**: when `sort_param->internal_memory` fills (`SORT_REC_DOESNT_FIT`,
`external_sort.h:47`, raised at `temp_recdes.area_size <= SSIZEOF(SORT_REC)`, `external_sort.c:1970`),
`sort_run_flush` (`external_sort.c:2342+`) writes the accumulated `SORT_REC`s — bytes as already
built, including decompressed/decoded key bodies — verbatim to a run file via `sort_write_area`
(`external_sort.c:2402`/`2430`). **Decompressed keys are therefore written into run entries**: no
re-compress on spill, so run-merge comparisons read the run's bytes directly, still decompressed.
This is the "key-only inflation" the R2 accounting below counts; `tuple`'s non-key payload is
untouched (§s.4).

**R2 accounting — key-only inflation formula**: for `N_entries` rows with a compressed-VARCHAR (or
`NUMERIC` p19-40) first-sort-key column,
```
inflated_bytes = N_entries × (avg_decompressed_key_bytes − avg_compressed_key_bytes)
```
counted **only** against that column's key-body bytes inside `SORT_REC`, never against `tuple`'s
non-key payload. Not yet populated with a measured number — no P0/P1 CV-sort/NUM-sort byte-volume
instrumentation exists; populating it is a P2 bench-harness deliverable (`[X]_CV-sort`/`[X]_NUM-sort`
cells, `ug1-packet.md` §③ / `p1.3-proposals.md` (ii)). P2/P3 MUST instrument the two averages via the
same `Num_*`/statdump engagement-counter idiom used elsewhere (`CUBRID_SSOT.md` §1 실수2; e.g.
`p1.1-format-selection.md` §3's `Num_qfile_format_conversion_executions`).

**Fallback (correctness preserved, win lost)**: `qfile_make_sort_key` can know the decompressed size
of a `VC_COMPRESSED` field before committing any bytes — the on-disk compressed-string header stores
`expected_decompressed_size` directly, read (`or_get_string_header`/`or_get_varchar_compression_lengths`,
`object_primitive.c:11800`/`10499`) *before* any decompression call. If
`length + QFILE_TUPLE_VALUE_HEADER_SIZE + expected_decompressed_size` would exceed
`key_record_p->area_size` (the same overflow check `qfile_make_sort_key` already performs today,
`list_file.c:3666`/`3707`, currently against the *compressed* length), the design falls back to
today's exact behavior for that entry: `memcpy` the raw bytes unchanged, comparator falls through to
`get_data_cmpdisk_function()`/`mr_cmpdisk_char_type_common` (§s.4). **Correctness preserved**
(identical to today for that entry); **win lost** for that entry only. Counted via a new counter,
`Num_sort_key_decompress_fallback` (same `Num_*` idiom as `Num_qfile_format_conversion_executions`),
incremented per fallback entry — unlike the format-conversion counter's "0 is correct" contract, a
nonzero value here is expected and informative, for P2/P3 to correlate against the R2 formula above.

### s.2.2 A_sort_key mode (`use_original == 0`) — output reconstruction from SORT_REC [architect iter-2 NEW-2, LEADER decision: option (b)]

`qfile_make_sort_key` has two build modes selected by `key_info_p->use_original = (n != types->type_cnt)`
(`list_file.c:4580` live tree, `[VERIFY]` exact ebf08d080 line per this doc's list_file.c drift convention):

- **P_sort_key mode (`use_original == 1`)** — sort keys are a strict subset of output columns; output
  tuples are re-fetched via breadcrumbs after the sort. Everything in §s.2.1 applies as written; the
  output list file never sees the decompressed key bytes ("본체 압축 유지" holds unconditionally).
- **A_sort_key mode (`use_original == 0`)** — sort keys cover ALL output columns; the output tuple is
  RECONSTRUCTED from the `SORT_REC` key bytes by `qfile_generate_sort_tuple` (`list_file.c:3753`,
  invoked at `:4313`). **This is the headline W1 shape** (`SELECT c_vc, c_int … ORDER BY c_vc, c_int`
  — key set == output set), so it cannot be excluded from the detoast-once win.

**Decision (option b — spec the re-serialization; option (a) "scope to use_original==1" is rejected
because it would exclude exactly the W1 headline workload):**

1. When the first-key column is `VC_COMPRESSED` and the entry takes the detoast-once path, the
   decompressed bytes are written into the `SORT_REC` key slot **as a valid *uncompressed* varchar
   disk form**: the `QFILE_TUPLE_VALUE_HEADER` length field is rewritten to the decompressed length
   at build time (compression is per-value optional on disk — an uncompressed representation of a
   ≥255B string is legal; consumers dispatch on the value header, not on the column definition).
   `qfile_generate_sort_tuple`'s reconstruction is then correct **by construction** — no naive
   byte-splice of compressed-header + decompressed-body can occur.
2. Consequence, stated for UG1 honesty: in A_sort_key mode the reconstructed output list carries the
   first-key column **uncompressed** — "튜플 본체는 temp pass-through에서 압축 유지" holds for
   P_sort_key mode and for all non-key columns; in A_sort_key mode the first-key column itself IS
   output payload and is materialized uncompressed. For LIMIT-bounded headline shapes (W1: LIMIT 100)
   the inflation is bounded by the output row count, not N.
3. R2 accounting extension: in A_sort_key mode the formula in §s.2.1 gains an output-file term:
   `output_inflated_bytes = N_output_rows × (avg_decompressed_key_bytes − avg_compressed_key_bytes)`,
   instrumented by the same P2 bench-harness deliverable and reported alongside the run-file term.
4. NUMERIC p19-40 decode-once in A_sort_key mode: the decoded body is NOT a legal on-disk NUMERIC
   form, so for NUMERIC first keys in A_sort_key mode the entry keeps the raw disk bytes in the
   reconstruction slot and places the decoded body in adjacent per-entry storage (`datum1` targets
   the decoded body; reconstruction reads the raw slot) — decode-once win preserved, reconstruction
   untouched. This asymmetry (varchar rewrites the slot, NUMERIC keeps slot + sidecar) exists because
   uncompressed varchar is a legal disk form and decoded NUMERIC is not.

### s.3 NUMERIC int64 proxy — concrete verdict

**Task**: grilled_plan.md §5 explicitly delegates this decision to P1 ("NUMERIC datum1 int64 프록시
가부: P1 판단"). This section gives the verdict.

**Format analysis** (`object_primitive.c:8706-8880`):

- On-disk NUMERIC = 3-byte header (`NUMERIC_HEADER_SIZE`, `object_primitive.c:131`) + a
  variable-length, **leading-zero-truncated** magnitude tail. `mr_data_writeval_numeric`
  (`object_primitive.c:8706-8751`) writes only the trailing bytes actually needed for the value's
  magnitude — smaller values physically use fewer disk bytes even within one fixed-precision column.
- The internal magnitude buffer is `DB_C_NUMERIC` = `unsigned char[DB_NUMERIC_BUF_SIZE]`,
  `DB_NUMERIC_BUF_SIZE = 17` (`dbtype_def.h:647`), **unsigned magnitude only** — sign tracked
  separately, stored big-endian (`numeric_opfunc.c:25-26`). Max declarable precision 40 digits
  (`DB_MAX_NUMERIC_PRECISION`, `dbtype_def.h:589`). `mr_get_fixed_numeric_size`
  (`object_primitive.c:8913-8973`) treats `buf[0]` as reserved/pad and `buf[1..16]` as two
  big-endian `uint64_t` words for a CTZ/CLZ-based size computation.
- `mr_data_readval_numeric` (`object_primitive.c:8760-8836`) is the "decode-once" restoration §a.3
  relies on: it reconstructs the full `DB_C_NUMERIC` buffer from truncated disk bytes, once per row,
  into slot-owned storage.

**Verdict — conditional, exact (not abbreviated) proxy, split at precision 18**: because **scale is
a domain (column) property, fixed for every row a sort compares against every other row**, same-scale
decimal ordering is *identical* to signed-integer ordering of the unscaled value — for columns within
the safe range there is **no truncation or approximation at all**.

- **Safe range**: `p ≤ 18` (largest 18-digit magnitude `999999999999999999` is unconditionally
  smaller than `int64` max `9223372036854775807` for every value of that precision — a per-domain
  guarantee). Covers this project's own P0.3 fixture (`NUMERIC(15,2)`) and TPC-H `DECIMAL` (`p=15`
  typically), i.e. the W2 (NUM-sort) headroom target.
  - **Construction**: read the low 8 bytes (`buf[9..16]`) as big-endian `uint64_t`, byteswap to
    native, cast to `int64_t`, negate if `is_value_negative`. Pure register op on already-decoded
    storage.
- **Unsafe range**: `p ∈ [19, 40]` — no lossless 64-bit encoding exists (and this stage does not want
  a lossy one — D-G5's territory). `datum1` is a pointer into **sort-owned** decode-once storage
  (§s.2.1) — decoded once directly into the `SORT_ENTRY`'s own per-entry storage when this column is
  the sort's first key, not a pointer into the per-scan `VALUE_SLOT.numeric_scratch` (§a.3), which
  cannot durably back a sort entry for the same reuse-per-row reason §s.2.1 gives for
  `VC_COMPRESSED`. Comparator falls back to `numeric_db_value_compare`/`mr_data_cmpdisk_numeric`, but
  against the already-decoded, sort-owned buffer — decode-once win preserved, just not the
  `datum1`-only-compare win.

**Net**: precision-gated design, exact lossless fast path for `p ≤ 18`, grounded decode-once-preserving
fallback for `p ∈ [19,40]` whose per-entry storage is concretized in §s.2.1. Compute the split once per
column at slot/sort-entry setup (`att_types[attno]->precision`), not per value.

### s.4 Interplay with disk-direct sort compare and R2 mitigation

Two existing mechanisms this design must not regress or duplicate:

- **Disk-direct sort compare** (`list_file.c:4505`, `subkey->sort_f =
  ...->get_data_cmpdisk_function()`, verified `p0.1-coordinates.md` row 29): today's sort assigns a
  disk-direct comparator per key column operating on raw, still-serialized bytes with **zero**
  intermediate `DB_VALUE`/slot materialization — the fastest path for non-first-key columns, untouched
  by Datum1Cache. Datum1Cache only changes the **first** key's comparison path (§s.2); columns 2..N
  continue via `get_data_cmpdisk_function()` exactly as today.
- **R2 mitigation** (grilled_plan.md §3 Risks: "sort-ingestion decompress inflation") — concretized by
  the LEADER DESIGN DECISION in §s.2.1: R2's concern is that preparing a compressed VARCHAR for
  sorting inflates memory/CPU by decompressing at ingestion. An earlier framing of this bullet
  described the sort entry's `tuple` as "keeping pointing at still-compressed, or first-touch-detoasted,
  *slot* storage" — corrected here: that would mean pointing at the per-scan
  `VALUE_SLOT.detoast_scratch` (§a.3), which is reused every row and cannot be what a sort entry's
  pointer stays valid against once row N+1 deforms (§s.2.1). The concrete mechanism is §s.2.1's
  per-entry sort-owned storage: `datum1`'s pointer (for `VC_COMPRESSED`/`NUMERIC` p19-40 first-sort-keys)
  targets *this entry's own* decompressed/decoded body inside `sort_param->internal_memory` (or, once
  spilled, the run file), never the per-scan slot scratch. R2's actual mitigation, per spec f17/R14, is
  not "avoid decompressing at ingestion" (the LEADER DESIGN DECISION explicitly accepts decompressing
  once at ingestion) — it is **"decompress exactly once per entry at ingestion, never once per
  comparison."** `tuple`'s non-key payload stays compressed; the inflation is key-column-only and
  accounted per §s.2.1's formula; the per-comparison `object_primitive.c:11897-11960`
  (`mr_cmpdisk_char_type_common`) re-decompress that exists today for every row-pair comparison during
  the sort's `O(N log N)` phase is what gets eliminated, replaced by a plain byte compare against the
  already-decompressed-once `SORT_REC` body (§s.2/§s.2.1). This matches grilled_plan §2 D-G4's
  "본체는 압축 유지, 8B 프록시만 정렬 배열에" at the granularity D-G4 actually intended: the "8B proxy"
  is an 8B **pointer** into per-entry storage, never an 8B *content* proxy — abbreviated-key content
  proxying stays D-G5-deferred, campaign-only; the R2 8B-proxy mitigation language applies solely to
  the P2 abbrev sub-cell measurement, never to this stage-1 design.

### s.5 Polymorphic sort utilities cannot carry a format tag — class must thread from the caller

Per this task's required P0 context: `qfile_sort_list_with_func` (`list_file.c:4654`) and the
other polymorphic sort/merge utilities cannot statically know at compile time whether they are
sorting a class-(d) forward-only intermediate or a class-(a) client-visible result — the class is a
property of the *caller's* `QFILE_LIST_ID`, not of the sort function. Datum1Cache is **class-agnostic
by construction**: it operates purely on `att_types`/`att_class` and the already-deformed `values[]`
array — no dependency on `format_version`/class tagging. This is a structural advantage over the
temp-framing workstream (P1.1(d)/(e), sibling task): Datum1Cache applies identically whether the
underlying list ends up legacy- or new-framed. §s.2.1's per-entry storage design lives inside
`SORT_INFO`/`SORT_PARAM`/`SORT_REC` — machinery that is itself already class-agnostic in exactly
this sense.

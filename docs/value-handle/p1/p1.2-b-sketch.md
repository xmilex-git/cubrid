## 1. Concept: kill the 1-time bswap

### 1.1 What A안 keeps (and B안 removes)

A안 (ralplan.md §3 P1.1(a)) explicitly retains **network-byte-order (NBO) on disk** and performs a
**1-time bswap at handle creation** from the heap `recdes` — i.e. every fixed-length attribute read pays
one `OR_GET_*`/`ntohs`-class conversion (object_representation.h:102-131 short/int/int64/bigint/float/
double; :171-210 extended time/utime/timestamptz/date/datetime macros) each time a `ValueSlot` entry is
deformed from the on-disk record, on top of `htonf`/`htond`'s `#if !defined(OR_HAVE_HTONF/HTOND)`-guarded
software fallback (byte_order.c:159-199) when the write side used it. This is a *structural* concession:
PG's philosophy pillar P-6 ("PG 데이터 경로에 hton 없음" — grilled_plan.md §1) has no on-disk conversion
step at all, because PG's disk format **is** the machine's native representation. CUBRID's 1-time bswap is
the one place stage-1 diverges from P-6, by explicit, user-accepted design (grilled_plan.md §4: "못 가져
오는 것: native-endian(P-6 → B)").

### 1.2 B안's concept

B안 changes the **on-disk byte layout** itself so that no `bswap`/`hton`-class conversion exists on the
read (or write) path for any machine whose native endianness matches the on-disk tag — the disk bytes
*are* the in-memory representation, mirroring PG's approach exactly. Concretely:

1. **Per-page (or per-file) endianness tag.** Add a `format_endian` byte to the page/file header
   (analogous in spirit to the `format_version` tag A안 already introduces per `QFILE_LIST_ID` at
   list-file granularity — ralplan.md §3 P1.1(d); for B안 the natural unit is the **heap page header**
   and **disk-file header**, since B안's target is the storage byte layout, not just list-file
   intermediates). Values written by a little-endian host tag `LE`; a big-endian host (rare in current
   CUBRID deployment targets, but the format must not assume LE-only if it is to be genuinely
   "native-endian" rather than "always-LE") tags `BE`.
2. **Read path becomes tag-conditional.** `OR_GET_SHORT`/`OR_GET_INT`/… (object_representation.h:102-131)
   become a 2-way dispatch: if `format_endian` matches the running host's native order, read the bytes
   directly with no conversion (a plain load); if it mismatches (e.g. a page written on a BE host, now
   read on an LE host — the cross-endian migration/replication case), fall back to today's `OR_GET_*`
   conversion macros unchanged. **This is the entire performance win**: same-endian hosts (the overwhelming
   common case — CUBRID's practical deployment matrix is essentially all-LE x86_64) drop the conversion
   entirely; cross-endian hosts pay exactly what they pay today.
3. **Write path drops the always-on `OR_PUT_*` conversion** for the common case, writing native bytes
   directly and stamping the page/file's `format_endian` tag once at creation. `htonf`/`htond`
   (byte_order.c:159-199) become dead code on any LE-only build (compile-time eliminable) except when
   explicitly serving a cross-endian export/migration tool.

This concept only touches how bytes land on disk pages (heap records, index keys, list-file tuples,
catalog metadata) — it does **not** change `pr_type`/`DB_TYPE` dispatch (that is D-G8, retained/extended
regardless of A/B), and it does **not** change the executor-internal `ValueSlot`/`ValueHandle` design
(P1.1(a)/(b)) except to delete the one bswap step A안 keeps. B안 is therefore additive-on-top-of-A안 in
scope, not a replacement for it: A안's deform-once/lifetime-contract/framing work is a prerequisite either
way, and B안 only ever removes the endianness-conversion sub-step inside whatever deform path A안 lands.

## 2. Migration strategies (≥2, pros/cons)

Any B안 rollout must handle the fact that CUBRID databases persist on disk across upgrades — existing
databases are entirely NBO/legacy-byte-order today, and B안 changes what "correct bytes" means for every
persisted page, index entry, and catalog record. Two concrete strategies:

### 2.1 Strategy 1 — Version-tagged pages with lazy rewrite

- **Mechanism**: introduce `format_endian` as a per-page tag (heap page header + list-file page header +
  B-tree page header — every on-disk page type that carries a fixed-length value byte-for-byte). Existing
  pages default to `format_endian = NBO` (today's format, tagged explicitly rather than implicitly
  assumed) on first read after upgrade; newly-*written* pages (new heap inserts, page splits, list-file
  writes, index rebuilds) get `format_endian = <host native>`. Rewrite-on-write (a page is only ever
  converted to native format the next time something modifies it — no eager batch pass). Read path always
  checks the per-page tag (§1.2 point 2).
- **Pros**: zero downtime, zero explicit migration step, upgrade-in-place semantics identical to every
  other CUBRID minor-version upgrade to date; a page that is never rewritten (cold/archival data) never
  pays a conversion cost it wasn't already paying (it stays NBO, same as today, same bswap-per-read as
  A안). Naturally incremental — hot pages (which dominate read volume in any OLTP-shaped workload)
  converge to native-format fastest, which is also where the performance win matters most.
- **Cons**: **permanent format heterogeneity as a fact of life**, not a transitional state — a database can
  contain a permanent, unbounded mix of NBO and native-endian pages (cold archival partitions in
  particular may never convert). Every read path must carry the 2-way dispatch (§1.2 point 2) *forever*,
  not just during a migration window — this is a permanent, not amortized, branch-prediction/code-
  complexity cost, partially offsetting the win the format change is meant to buy. B-tree pages are
  materially harder than heap/list-file pages: a page split or rebalance that merges entries from a
  native-format page and an NBO page requires per-entry (not per-page) endian awareness during the merge,
  which is a much finer-grained version of the same problem A안 already solves at list-file granularity
  (`format_version` per `QFILE_LIST_ID`) — but now at the **index key** level, touching btree code that is
  explicitly out of scope for this project (ralplan.md §2 Non-Goals: "Heap write path / btree index /
  spage/qmgr page structure changes").

### 2.2 Strategy 2 — Offline migration tool (dump/convert/reload, or in-place page rewrite pass)

- **Mechanism**: a dedicated offline tool (`cubrid migratedb`-class utility, analogous to existing
  `cubrid_rel` compatibility tooling) walks every page of every volume in a full offline pass, converts
  NBO byte layout to native-endian in place (or via full dump-and-reload through `csql`'s unload/load
  pipeline, which is simpler to implement correctly — it reuses the existing DB_VALUE-based row
  representation as the intermediate — but costs an entire logical export+reimport rather than a raw byte
  rewrite), and stamps every page uniformly once the pass completes. The database is offline (or
  read-only) for the duration.
- **Pros**: format is uniform **immediately and permanently** after migration completes — the read path
  can drop the 2-way endian dispatch entirely once the tool guarantees no page tagged with the old format
  remains (no permanent branch cost, unlike Strategy 1). Migration logic is isolated in one tool, not
  smeared across every on-disk-page-touching code path in the server; failure/rollback semantics are a
  single all-or-nothing operation (keep the pre-migration volume copy until the tool reports success),
  which is easier to reason about and test than an indefinitely-long lazy-rewrite window.
- **Cons**: **requires downtime proportional to database size** — for CUBRID's production deployment
  profile (multi-TB warehouses are the stated performance-sensitivity target per this project's own W1/W2
  workload framing), a full-volume offline rewrite is the opposite of the "1단계 disk-invariant, zero
  on-disk migration" principle (ralplan.md §1 Principle 2) this entire project is built to preserve — B안
  is precisely the point where that principle is deliberately broken, and this strategy breaks it in the
  most operationally expensive way (whole-database blackout window) rather than the least. Dump/reload
  variant additionally risks losing exact-bytes fidelity for edge-case values (e.g. `NaN`/signed-zero
  `DOUBLE` representations, LOB external-file references) unless the tool is audited type-by-type against
  every one of the ~38 on-disk type representations (§3.2) — a nontrivial correctness surface that a raw
  in-place byte-rewrite pass (same mechanism, no logical re-derivation) avoids.

### 2.3 Parameterized B-entry condition (references [Z])

Per ralplan.md §3 P1.3(ii), B-entry is gated on **[Z] = bswap's share of remaining overhead after A안
lands**, to be measured in P3.8 (grilled_plan.md §3 P3 delta: "P3.8+: 예측표 vs 실측 대조 열 추가"). The
parameterized condition this sketch proposes for UG1 to formalize:

> **Enter B if, on the P3.8 slice-measured FL-filter/FL-sort/CV-sort/NUM-sort cells (post-A안 landing),
> the `OR_GET_*`/`OR_PUT_*` bswap-class conversion accounts for ≥[Z]% of the *remaining* per-value
> overhead** (i.e. of whatever CPU time A안 did **not** already eliminate — deform-once + lifetime-contract
> + detoast-once + datum1 having already landed). [Z]'s concrete provisional number is proposed in
> `p1.3-proposals.md` §2 item [Z] — this document only fixes the *shape* of the condition (a relative
> share of remaining overhead, not an absolute time), because grilled_plan.md §4 already establishes that
> B-entry is judged **after** A안's other wins are subtracted out, not against the pre-A안 baseline (double-
> counting A안's own deform-once/detoast-once savings into the bswap share would overstate B's marginal
> value).

`[Z]` is `[P0-CONDITIONAL]`: this parameterization assumes A안's headroom claims (deform-once,
detoast-once, structural lifetime) hold as measured in P3, not merely as designed in P1 — if P3.8's
prediction-vs-actual gap (D-G3.3) shows A안 underperforms its own W1/W2 prediction-table entries, the
"remaining overhead" denominator [Z] is measured against shifts, and the B-entry threshold must be
re-derived at UG3 rather than taken as fixed from this P1 sketch.

## 3. Engineer-month cost estimate

### 3.1 Stated inputs

**(i) A안 blast radius × migration/versioning multiplier.**
Per ralplan.md §3 P1.1(f) (the DB_VALUE boundary seam tradeoff table, D-G7-confirmed Shape A), **Shape A's
own blast radius is ~15–20 files** — this is the number the B안 cost model must scale, per the
assignment's framing ("A안 blast radius ~15-20 files × migration/versioning multiplier"), because B안's
on-disk byte-layout change is layered on top of whatever A안 already touches (B안 does not replace A안's
executor-internal work; it adds a disk-format layer beneath it — §1.2). A migration/versioning multiplier
of **×3–4** is proposed for B안's marginal scope beyond A안's 15–20 files, reflecting:
  - every one of A안's ~15–20 touched files needs an *additional* endian-tag-aware branch wherever it reads
    a fixed-length on-disk value (not a rewrite, but a second code path per site);
  - the per-page-type header format change itself (heap page header, list-file page header, B-tree page
    header — 3 distinct on-disk structures, none of which A안 touches, since A안 is explicitly executor-
    internal and disk-invariant per ralplan.md §1 Principle 2);
  - the migration-strategy implementation itself (§2: either the lazy-rewrite dispatch machinery, or the
    offline tool) — a wholly new subsystem, not a modification of an existing one;
  - `htonf`/`htond` (byte_order.c:159-199) and the `OR_PUT_*`/`OR_GET_*` macro family
    (object_representation.h:102-131, :171-210) are used far more broadly than the ~15-20 A안 files (every
    heap/index/catalog/network-wire-protocol write and read path in the server) — B안's read/write dispatch
    change is a systemic macro-level edit, not a localized file-level one, which is why the multiplier is
    applied to A안's count rather than an independent from-scratch file count.
  - **15-20 × 3 ≈ 45–80 file-equivalents of touched/added surface** as the raw scope driver.

**(ii) On-disk type count for migration test scope.**
Grounded directly from `tp_Type_id_map[]` (object_primitive.c:1716-1764), the dispatch table every
`DB_TYPE` value indexes into for its `data_writeval`/`data_readval`/`data_cmpdisk` function pointers (the
functions that would need endian-dispatch awareness under B안). The array has **41 slots**, one per
`DB_TYPE` enum value (`DB_TYPE_FIRST=0` .. `DB_TYPE_LAST=DB_TYPE_JSON=40`, dbtype_def.h:746-802 — the slot
count and enum range match exactly). Of these 41 slots:
  - **2 are non-representable placeholders** using `&tp_Null` (object_primitive.c:1738, :1753) for
    `DB_TYPE_DB_VALUE` (index 21, "special for esql," dbtype_def.h:769) and `DB_TYPE_TABLE` (index 30,
    "internal use only," dbtype_def.h:784) — neither has an on-disk byte representation to migrate.
  - **1 is a compile-time alias**: `#define tp_VarNChar tp_String` (object_primitive.c:1715) means
    `DB_TYPE_VARNCHAR_DEPRECATED`'s dispatch table entry (object_primitive.c:1749) is byte-identical to
    `DB_TYPE_STRING`'s — zero incremental migration-test surface beyond what `DB_TYPE_STRING` already
    requires.
  - **Net distinct on-disk representations requiring independent migration-test coverage: 41 − 2 − 1 =
    38.**

  This 38 is the number that drives migration-tool/dispatch test-matrix sizing (§2's offline tool, or
  Strategy 1's per-type endian-conditional read/write macro coverage) — every one of the 38 needs at least
  one round-trip byte-equality test (write native, read native, write NBO-legacy, read via the fallback
  conversion path, confirm identical decoded value) before B안 could be considered test-complete.

### 3.2 Output

**Point estimate: 9 engineer-months, ±50% band → 4.5–13.5 engineer-months.**

Derivation sketch (order-of-magnitude, not a detailed WBS — this is a UG1-evaluation input, not a P3-grade
estimate): treating the "45–80 file-equivalents" scope driver (§3.1.i) at a rough historical CUBRID rate
of ~1 engineer-week per touched/added file-equivalent for storage-layer format work (page-header changes

typical executor-internal edits, justifying a slower per-file rate than A안's own file count would imply

folding in the 38-type migration test matrix (§3.1.ii) as a mostly-parallelizable but non-trivial
additional test-authoring/execution tranche (~1–2 engineer-months, since round-trip byte tests are
mechanical once the harness exists) and applying a downward adjustment for the substantial code-pattern
reuse between the ~38 types' `OR_GET_*`/`OR_PUT_*` sites (most fixed-length numeric/date/time types share

not just toward it), and (b) whether Strategy 2's dump/reload correctness audit (§2.2) surfaces edge-case
byte-fidelity issues across the 38 types that require type-specific remediation rather than the assumed
mechanical/parallelizable test authoring.

**Reconciling the point estimate against the core subtotal** (architect LOW finding, pre-UG1 revision
pass): as drafted, the 9 EM point estimate sits *below* the core subtotal's own stated low end (10 EM,

**reuse-eligible share, assumed ≈70%** of the file-equivalent count (a stated, challengeable split; the
remaining ≈30% is the page-header/migration-subsystem work, §3.1.i's other bullets, which does *not*
benefit from type-level macro reuse and stays at the full ~1-engineer-week/file-equivalent rate). Applying
a **≈40% effective-rate discount** to the reuse-eligible 70% share (effective cost ~0.6 weeks/file-
equivalent instead of ~1 week, since the design/implementation work is shared across the macro family
rather than repeated per type) and leaving the non-eligible 30% at full rate:
`0.70×(45–80)×0.6 + 0.30×(45–80)×1.0` ≈ `18.9–33.6 + 13.5–24.0` ≈ `32.4–57.6` discounted week-equivalents ≈
**7.5–13.3 engineer-months** for the core, before the +1–2 EM test tranche (already the cheap,
mostly-mechanical tranche — not further discounted here). Discounted core+test range ≈ **8.5–15.3
engineer-months**: its low end (8.5) sits just under the stated 9 EM point estimate (consistent with, not
contradicting, the point estimate as a low-of-range pick) and its high end (15.3) is covered by the stated
±50% band's ceiling (13.5) for all but the extreme tail, which the band's own named unknowns (btree-merge
complexity, dump/reload byte-fidelity audit, both above) already account for. This bridges the 10–18 EM
*undiscounted* core subtotal down to the 9 EM point estimate via an explicit, quantified reuse discount
rather than an asserted one; the ±50% band itself (4.5–13.5) needs no change.

**Acceptance check**: estimate present (9 engineer-months), inputs stated (A안 blast radius 15–20 files ×

## 4. Client-visible framing extension review (사용자 지시 2026-07-09)

### 4.1 The question

Stage-1's A안 scope is explicitly bounded to **P0.2-approved class-(d) server-internal forward-only
intermediates** (ralplan.md §3 P1.1(d); grilled_plan.md D-G6 tightens this further to volume-conditioned
class-(d) framing, and per `p0.2b-byte-volume.md` §9's D-G6.1 headline the measured class-(d) write-byte
share is 12.12% on the combined P0.3+supplemental workload — below the proposed <30% baseline, though
`[P0-CONDITIONAL]`-flagged as workload-mix-sensitive: Q1+Q2-only reweighting pushes the same numerator/
denominator to 99.2%, per p0.2b-byte-volume.md §9's composition caveat). Client-visible **result** lists
(P0.2 class (a)) are mandated legacy end-to-end today and under A안 — they are read by `cursor.c`, which is
compiled directly into the CS client library (cs/CMakeLists.txt:263: `${QUERY_DIR}/cursor.c`), and that
client binary is not something this project's non-goals permit modifying (ralplan.md §2 Non-Goals; P0.4
§3.1 point 3 independently confirms `cursor_construct_tuple_from_overflow_pages`, cursor.c:665-724, is a
byte-for-byte legacy-format mirror the client hard-codes). The 2026-07-09 user directive asks this sketch
to evaluate, as a **campaign-roadmap** item (not stage-1 scope), whether new framing should ever extend to
client-visible result lists at all, and under what mechanism.

### 4.2 Three options

**Option 1 — Keep fetch-boundary conversion (status quo, extended indefinitely).**
New-format intermediate lists convert to legacy format at the point they become a query result destined
for `cursor.c` (already how A안 is designed — ralplan.md §3 P1.1(d): "새-format 중간 → legacy format at
fetch boundary when becoming query result for cursor.c"). Client-visible bytes never change; only
server-internal intermediates benefit from new framing, forever.
  - *Pros*: zero client-library risk, zero protocol/wire-format versioning burden, zero interaction with
    JDBC/CCI/PHP/ODBC driver compatibility matrices across CUBRID's supported client-version skew. This is
    the only option requiring **no** coordination with client-library release cadence.
  - *Cons*: caps the framing win at whatever fraction of total query byte volume never reaches the client
    as the final result — i.e. exactly the class-(d) byte-share number D-G6.1 measures (12.12%–99.2%
    depending on workload mix, per §4.1). For workloads dominated by `SELECT *`-shaped final projections
    with little internal sort/aggregate/join spill, this option captures near-zero of the framing benefit.

**Option 2 — Client library format support (cursor.c gains new-framing decode logic).**
Extend `cursor.c`'s tuple-decode path (the same file that currently hard-codes the legacy 8B-prefix
layout, e.g. `QFILE_GET_PREV_TUPLE_LENGTH` at cursor.c:1590 per P0.1 row 5) to understand
`format_version = 1` framing, so a class-(a) client-visible result list could itself carry new framing all
the way to the wire, with the client decoding it directly instead of forcing a server-side transcode.
  - *Pros*: closes the Option-1 gap entirely — the framing win now covers final-result byte volume too,
    which for `SELECT *`-shaped OLTP workloads is where most byte volume actually lives (the inverse case
    of what Option 1 captures).
  - *Cons*: this **is** a client-library change, which every one of this project's governing documents
    (ralplan.md §2 Non-Goals, spec.md, P0.4 §3.1 point 3) currently treats as out of scope by design — it
    requires shipping new client-library binaries in lockstep with (or ahead of) new server binaries, and
    every driver built against `cs/CMakeLists.txt`'s `cursor.c` (JDBC's native-glue path, CCI, ODBC, PHP,
    Python — CUBRID's full client matrix) needs the update before any client-visible new-format list could
    safely reach it; a client on an old library talking to a new server would decode new-format bytes with
    legacy logic and silently corrupt results unless gated by a protocol version negotiated *before* this
    option, which folds Option 2 into requiring Option 3 as a prerequisite in practice.

**Option 3 — Protocol versioning (explicit wire-format capability negotiation).**
Add a protocol-level capability flag (negotiated at connect time, alongside CUBRID's existing
CAS-protocol version handshake) that lets the server know whether the connecting client's library
understands new framing; only clients advertising support ever receive `format_version = 1` client-visible
results, everyone else gets legacy (falling back to Option 1's fetch-boundary transcode for old clients).
  - *Pros*: solves Option 2's rollout-safety gap directly — old clients are structurally protected from
    ever receiving bytes they cannot decode, enabling incremental client-library rollout rather than a
    flag-day cutover. This is the standard pattern CUBRID's own CAS-protocol versioning already uses for
    other wire-format evolutions, so it reuses an established mechanism rather than inventing one.
  - *Cons*: strictly a superset of Option 2's cost (still requires the client decode logic, §Option 2's
    cons) *plus* the negotiation-protocol design/implementation/test matrix itself (every client-version ×
    server-version combination in the support matrix needs explicit behavior verification) — the highest
    implementation cost of the three, and the longest to fully retire the legacy path (old clients persist
    in the field for years, so the fetch-boundary fallback code never gets to be deleted, unlike a
    hypothetical flag-day migration).

### 4.3 Recommendation for the campaign roadmap

**Recommend Option 1 (keep fetch-boundary conversion) for stage-1 and near-term campaign, with Option 3
(protocol versioning) as the only acceptable path to ever revisit Option 2 — never Option 2 alone.**

Rationale: Option 1 is already A안's design (no incremental campaign cost to *keep* it); the D-G6.1
class-(d) byte-share measurement (12.12%, `[P0-CONDITIONAL]` on workload mix per §4.1) shows the
uncaptured client-visible-result byte volume is workload-dependent but the measured coverage workload sits
well under the 30% baseline that would make Option 1's gap the dominant remaining inefficiency — i.e.
there is currently no P0 evidence that client-visible framing extension is where the next unit of campaign
effort has the best return, relative to B안 (native-endian, this document §1-3) or the deferred
abbreviated-key/radix-sort campaign items (grilled_plan.md D-G5). If a future campaign phase's own
byte-volume remeasurement (on a broader, production-representative workload mix — see §4.1's caveat that
12.12% is not a fixed engine property) shows client-visible result-list bytes dominate, Option 3 is the
only responsible entry point, because Option 2 alone reintroduces exactly the flag-day-cutover client/
server version-skew corruption risk this project's own non-goals were written to avoid. This same
recommendation and its evidence should be posted verbatim to the campaign roadmap (P4.1) per ralplan.md
§3 P1.2's instruction to duplicate this review item there.

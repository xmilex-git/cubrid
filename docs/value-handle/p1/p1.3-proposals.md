## Proposal (i): pr_type/DB_TYPE — hook list (D-G8 closes the retain/extend decision)

Per grilled_plan.md D-G8, "PG는 타입 디스패치를 제거한 적이 없다(P-7). pr_type 유지 + 훅 증설... DB_TYPE
제거는 캠페인에서도 반-PG적 — 논외." **DB_TYPE removal is out of scope, permanently, including for the
campaign.** This proposal's deliverable is therefore not a retain/merge/deprecate decision — that decision
is closed — but the concrete **hook list** grilled_plan.md defers to P1.

### (a) P0 evidence citation

- `pr_type`'s existing dispatch surface: object_primitive.h:59-111 (the 20 `*_function_type` typedefs and
  the `protected` function-pointer members they back, e.g. `f_data_readval`/`f_data_writeval`/
  `f_data_cmpdisk` at :102-103/110) and object_primitive.h:165-179 (the public `data_writeval`/
  `data_readval`/`data_cmpdisk` accessor methods that wrap those pointers) — verified at `ebf08d080` in this
  document (§ read above), consistent with P0.1 row 33 (object_primitive.h:73-180, full `pr_type` class
  body, "VERIFIED").
- `tp_Type_id_map[]` (object_primitive.c:1716-1764) — 41 `DB_TYPE`-indexed dispatch slots, 38 of them
  distinct on-disk representations (2 non-representable placeholders + 1 alias — derivation in
  `p1.2-b-sketch.md` §3.1.ii) — every one of these needs a well-defined (possibly no-op/fallback) value
  for each new hook, so the hook list's blast radius is bounded and known.
- P0.3 (`p0.3-peek-copy-profile.md` §2) — `heap_attrvalue_read`'s unconditional peek→copy chaining
  (`heap_attrvalue_point_fixed`/`_variable`, heap_file.c:10366/10394, then unconditionally
  `heap_attrvalue_transform_to_dbvalue`, heap_file.c:10431) is exactly the call chain the **slot deform
  hook** (below) replaces for types that support pass-by-value/decode-once `ValueSlot` deform.

### (b) Concrete recommendation: 3-hook list

| Hook | Purpose | Stage | PG analog |
|---|---|---|---|
| **Slot deform hook** (`f_slot_deform`) | Fill one `ValueSlot` entry (`values[i]`/bound-bit/type-vector, D-G1) directly from a `recdes` attribute, replacing the per-attribute `heap_attrvalue_point_fixed`/`_point_variable` + `heap_attrvalue_transform_to_dbvalue` chain (heap_file.c:10366/10394/10431) for the 9 fixed-length types (pass-by-value) and NUMERIC (decode-once, object_primitive.c:8706-8880). Signature shape: `int (*f_slot_deform)(RECDES *recdes, OR_ATTRIBUTE *attrepr, ValueSlot *slot, int slot_index)`. Types without a slot-deform implementation (compressed varchar, overflow, MVCC-old, unsupported) return "not handled," falling back to the existing `heap_attrvalue_read` path — same fallback semantics ralplan.md §3 P1.1(a) already specifies. | **Stage 1 (A안)** | `tts_values`/`tts_isnull` fill in `slot_getattr` (tuptable.h:131-135) — PG's per-attribute deform-once is likewise a per-type dispatch, not a single universal function. |
| **Datum1 extraction hook** (`f_datum1_extract`) | Given a deformed slot entry, produce an 8B inline sort-key proxy (D-G4 Datum1Cache) — identity int64 cast for the 9 fixed-length types, a NUMERIC int64 proxy where representable (precision/scale-dependent; "P1 판단" per grilled_plan.md §5, this hook's return contract must allow "no proxy possible" as a valid outcome for NUMERIC values outside int64 range). Signature shape: `bool (*f_datum1_extract)(const ValueSlot *slot, int slot_index, int64_t *out_proxy)`, `false` = no proxy, comparisons fall back to full-value compare (same "abort to full comparator" semantics PG's abbrev-key machinery uses, see below). | **Stage 1 (A안)** | Structurally the *simple* half of PG's abbreviated-key machinery — sortsupport.h's `abbrev_converter` (below) is the full campaign-scope version; datum1 is the "always-on, no abort-cost-model" 1-tier subset D-G4 scopes into stage 1. |
| **Abbreviated-key converter hook** (`abbrev_converter`-equivalent) | **Hook slot reserved now, implementation deferred to campaign** per D-G5 ("abbreviated key... 1단계 제외, 벤치 sub-cell만"). Reference: `Datum (*abbrev_converter) (Datum original, SortSupport ssup)` (`~/dev/postgres/src/include/utils/sortsupport.h:172`) is the PG pattern this hook slot directly mirrors — pass-by-reference original value → pass-by-value abbreviated key, paired with `abbrev_abort` (cost-model-driven abandonment, sortsupport.h ~182) and `abbrev_full_comparator` (fallback on inconclusive abbreviated comparison, sortsupport.h ~191). Reserving the slot in `pr_type` now (as a `NULL`-valued member for every type until campaign implementation lands) costs nothing at stage 1 and avoids a later ABI-adjacent struct-layout change to add it. | **Reserved now, implemented in campaign (Stage C, see Proposal iii)** | sortsupport.h:172/182/191 (`abbrev_converter`/`abbrev_abort`/`abbrev_full_comparator`), the exact 3-function group PG's `tuplesort.c` calls when `SortSupport.abbreviate` is set. |

Per D-G8, no hook here removes or bypasses `pr_type`/`DB_TYPE` dispatch — every hook is an *additional*
function-pointer member appended to the existing `pr_type` class (object_primitive.h:93-111 is where the
protected members live; new members append after `f_cmpval` at :111, a non-breaking layout change since
`pr_type` construction is entirely internal — no external ABI consumer constructs a `PR_TYPE` literal, per
D-G7/Shape-A's confirmation that DB_VALUE, not `pr_type`, is the ABI-adjacent boundary).

### (c) Rationale

grilled_plan.md P-7 establishes type dispatch as "확장 축, not 존폐 대상" (an extension axis, not a
removal target) — PG's own `sortsupport.h` is itself proof that PG doubles down on per-type dispatch hooks
rather than eliminating them. D-G8 downgrades P1.3(i) from "존폐 논의" (existence debate) to "확장 훅 목록
승인" (hook-list approval) explicitly. The 3-hook list above is the minimum set that (1) lets `ValueSlot`
deform-once bypass the peek→copy chain P0.3 shows is otherwise unconditional (§P0.3 finding — every
attribute read pays exactly one peek + one copy, ratio trivially 0.5, not a headroom signal in itself but
confirmation the chain has no existing bypass to reuse), (2) gives sort entries an inline comparison proxy
(D-G4) without committing to full abbreviated-key infrastructure, and (3) reserves campaign-scope
abbreviated-key capability at zero stage-1 struct-layout cost.

## Proposal (ii): Per-cell thresholds [X]×3 + prediction table (D-G3)

### Why the P0.3 headroom input is degenerate — re-grounding is mandatory

ralplan.md §3 P1.3(ii) originally specified: "[X] derived from P0.3 headroom ceiling." **This input is
degenerate.** `p0.3-peek-copy-profile.md` §2 shows `heap_attrvalue_read` (the sole caller of both
instrumented functions) unconditionally chains peek→copy for *every* attribute access — `peek_count` ≡
`copy_count` by construction, so the "peek ratio" is trivially 0.5 regardless of workload
(`p0.3-peek-copy-profile.md` §3 table: all three queries report exactly 0.500 for both fixed and variable
categories). There is no existing peek-without-copy fast path on this code path to measure a headroom
ceiling from — as `p0.3-peek-copy-profile.md` §2 itself concludes: "P1 should re-ground the headroom claim
against [disk-direct cmpdisk] sites... not this pair." **This proposal follows that instruction**: every
[X] below is derived from the `cmpdisk` disk-direct comparison cost structure P0.1 grounds
(object_primitive.c:11897-11960 compressed-varchar per-compare malloc+decompress; :8706-8880 NUMERIC
double-readval; list_file.c:4505 disk-direct sort-compare dispatch), **not** from the peek/copy ratio.

### (a) P0 evidence citation

- **FL-filter**: `f_data_cmpdisk`/`f_index_cmpdisk` dispatch (object_primitive.h:108-110, P0.1 row 7) +
  disk-direct sort-compare function assignment (list_file.c:4505-4536, P0.1 row 29/43) — fixed-length
  compares go straight through a dispatched `cmpdisk` call with a bswap-class `OR_GET_*` read
  (object_representation.h:102-131, P0.1 row 48) inline, no allocation, no multiplicative cost per compare
  beyond the dispatch+bswap itself.
- **CV-sort**: `mr_cmpdisk_char_type_common` (object_primitive.c:11897-11960, P0.1 row 46, "compressed
  varchar per-cmp malloc+decompress" — `db_private_alloc` + `pr_get_compressed_data_from_buffer` on *both*
  operands, *every* comparison) — this is the cell grilled_plan.md D-G3 identifies as the one cell with a
  genuine multiplicative (`O(N log N)`) cost structure, matching the prediction table's W1 "주 이득처"
  classification below.
- **NUM-sort**: `mr_data_cmpdisk_numeric` (object_primitive.c:8838-8880, P0.1 rows 27/47, "double-readval" —
  two `mr_data_readval_numeric` calls per comparison, one per operand) — also multiplicative over `O(N log
  N)` comparisons, but cheaper per-call than CV-sort's malloc+decompress (no allocation, a 3B-header
  truncated-buffer decode instead of a general-purpose decompressor).

### (b) Concrete provisional numbers with derivation (all `proposal-pending-UG1`)

| Cell | [X] (provisional) | Derivation |
|---|---|---|
| **FL-filter** | **[X]_FL = 3%** `proposal-pending-UG1` | Per-compare cost = 1 dispatched `cmpdisk` call (list_file.c:4505's `sort_f` function-pointer indirection) + 1 `OR_GET_*` bswap-class read (object_representation.h:102-131, a single `bswap`/`ror`-class instruction on x86 for 2/4/8B operands, issue-port throughput ~1/cycle). Per grilled_plan.md D-G3's own rationale ("행당 1회 비용이라 곱셈 효과 없음"), FL-filter has **no O(N log N) or repeat-per-row multiplication** — the bswap cost is paid once per attribute access regardless of A안, and A안's *own* contribution to this cell is deform-once/lifetime-structural (not bswap elimination, which stays — P-6 is B's scope, not A's). The dispatch-call overhead (indirect branch, likely mispredicted on type-heterogeneous columns) dominates the single-instruction bswap by roughly an order of magnitude, so [X]_FL is set low: a variant expected to show low-single-digit-percent median improvement over cmpdisk+lazy on this cell is *consistent with A안's design*, not a sign of failure — this is D-G3's explicit rationale for excluding FL-filter as a solo STOP gate (weakest cell, "잘못된 STOP을 권고할 수 있다"). |
| **CV-sort** | **[X]_CV = 35%** `proposal-pending-UG1` | Per-compare cost today = 2× (`db_private_alloc` + `pr_get_compressed_data_from_buffer` decompress) per object_primitive.c:11897-11960, repeated for **every** comparison in an `O(N log N)` sort (P2.3's CV-sort cell: 500K rows, ratio ≥2:1 compression ⇒ ~500,000 × log₂(500,000) ≈ 9.5M comparisons). D-G4's Datum1Cache replaces the vast majority of these with an 8B inline-proxy compare (a plain integer compare, no allocation, no decompression) for all non-tie-breaking comparisons, with only a small residual fraction needing the full decompress-and-compare fallback (tie-breaks on identical proxies). Malloc+decompress cost dominates sort time for this cell by a wide margin (a decompression call is orders of magnitude more expensive than an integer compare), so the ceiling is set high relative to FL-filter/NUM-sort, consistent with grilled_plan.md D-G3/§4 flagging CV-sort ("W1") as the *primary* expected-gain cell ("곱셈 효과가 있는 유일한 이득") — but capped below 50% to leave headroom for the residual full-comparison fraction and dispatch overhead that A안 does not eliminate. |
| **NUM-sort** | **[X]_NUM = 15%** `proposal-pending-UG1` | Per-compare cost today = 2× `mr_data_readval_numeric` (object_primitive.c:8838-8863 first call + :8865 second call, full range 8706-8880) per comparison, also `O(N log N)` over P2.3's NUM-sort cell (500K rows). D-G4 proposes replacing this with decode-once + an int64 datum1 proxy (Proposal i's `f_datum1_extract` hook) where NUMERIC(15,2)-class precision/scale fits in an int64 representation — cheaper to eliminate than CV-sort's decompression (no allocation, a fixed-width decimal decode rather than a general decompressor), so the ceiling is set lower than CV-sort but still meaningfully above FL-filter's single-instruction-bswap floor, matching D-G3's "중간" (medium) classification for this cell (W2) below. |

**[X]_FL, [X]_CV, [X]_NUM are all `[P0-CONDITIONAL]`**: each derivation assumes A안's own mechanisms
(deform-once for FL, Datum1Cache for CV/NUM) land as designed and are not offset by unmodeled overhead
(e.g. the datum1-proxy extraction cost itself, or increased branch complexity from the fallback path) — if
P2's microbench (P2.3) or P3.8's slice measurement shows a materially different per-compare cost structure
than assumed here, these three numbers must be re-derived, not merely re-approved, before UG1.5/UG3.

### [Y] — Slice adoption threshold (env-ON vs env-OFF on W1)

**[Y] = 10%** `proposal-pending-UG1`, `[P0-CONDITIONAL]`. Derivation: W1 (CV-sort-shaped workload) is the
cell with the highest ceiling ([X]_CV = 35% above measured against `cmpdisk+lazy` in isolation), but the
slice-adoption comparison (env-ON full pipeline vs env-OFF full pipeline on a real end-to-end workload, not
an isolated bench cell) dilutes the isolated cmpdisk-comparison win with everything else a real query does
(I/O, non-sort-cell work, fixed overhead) — a real full-pipeline median improvement is expected to be a
materially smaller fraction than the isolated-cell ceiling. [Y] is proposed at roughly 1/3 of [X]_CV,
reflecting typical dilution from isolated-microbenchmark-cell gain to end-to-end slice gain; this ratio
itself is a P1 judgment call, not derived from a P0 measurement, and should be revisited once P2's bench
numbers exist.

### [Z] — B-entry threshold (bswap share of remaining overhead)

**[Z] = 40%** `proposal-pending-UG1`, `[P0-CONDITIONAL]`. Per `p1.2-b-sketch.md` §2.3, [Z] is a *relative*
share of whatever per-value overhead **remains after A안's own wins are subtracted** (deform-once,
detoast-once, datum1), not an absolute time. Derivation: FL-filter is the cell where A안's other mechanisms
(deform-once, Datum1Cache) contribute the least marginal benefit (§Proposal-ii table, [X]_FL = 3%, no
multiplicative structure) — so for FL-filter-shaped workloads specifically, **most of what A안 leaves on
the table after landing IS the bswap** (object_representation.h:102-131/171-210 `OR_GET_*` conversion,
byte_order.c:159-199 `htonf`/`htond` software fallback). [Z] = 40% is proposed as the threshold at which
this residual-bswap dominance is judged material enough across the *combined* FL/CV/NUM remaining-overhead
mix (not FL-filter alone) to justify B안's cost (`p1.2-b-sketch.md` §3.2: 9 engineer-months, ±50%). This
number is explicitly conditional on A안's other mechanisms landing as measured (not merely as designed) in
P3.8 — see `p1.2-b-sketch.md` §2.3's own `[P0-CONDITIONAL]` flag on the same parameter.

### (c) Rationale (all three [X] + [Y] + [Z])

D-G3 replaces the single FL-filter STOP gate with a 3-cell gate specifically because FL-filter alone is
"최약체 셀" (weakest cell) and could produce "잘못된 STOP" (a wrong stop recommendation) — the prediction
table above is the reason: FL-filter's mechanism (deform-once only, no multiplicative effect) is
structurally incapable of showing the same magnitude of improvement as CV-sort/NUM-sort's multiplicative
malloc+decompress/double-readval elimination, so judging the whole project on FL-filter alone would
systematically underrate A안. Re-grounding every threshold on the `cmpdisk` cost structure (not the
degenerate 0.5 peek ratio) is the only way to derive threshold numbers that are falsifiable against a real
mechanism rather than an artifact of `heap_attrvalue_read`'s unconditional chaining.

## Proposal (iv): 4B prefix — volume-conditioned REJECT for stage-1 (D-G6.4)

### (a) P0 evidence citation

- **P0.2** (`p0.2-list-class-audit.md` §1/§2/§6): "reverse scan is actively used" — 4 real
  `qfile_scan_list_prev` call sites (query_executor.c:6142,23533,23567; scan_manager.c:7863) plus
  sort-key backtrack (list_file.c:3632) — confirming ralplan.md's pre-audit conclusion is correct: "Blanket
  4B reduction NOT viable. 4B potentially viable only for class-(d)." P0.2 §3 confirms only **10 class-(d)
  sites** exist (of 44 total creation sites), with **8 more FORBID-excluded** (would-be-(d) but disqualified
  as raw-copy sources into cross-list edges) — i.e. the 4B-eligible population is already the smallest,
  most narrowly-scoped class in the audit.
- **P0.2b** (`p0.2b-byte-volume.md` §9, D-G6.1 headline): class-(d) write-byte share = **12.12%** of total
  measured list-file write bytes on the combined P0.3+supplemental workload (1,226,400 / 10,117,848 bytes)
  — below the proposed <30% baseline (ralplan.md/D-G6's threshold for keeping framing, by extension 4B, in
  scope for stage 1) — **but** flagged workload-mix-sensitive: a Q1+Q2-only reweighting (dropping the
  forced-hash-join and unbounded-sort queries from the denominator) pushes the same class-(d) numerator to
  **99.2%** of that narrower total (`p0.2b-byte-volume.md` §9 composition caveat).

### (b) Concrete recommendation + computed byte impact

**Recommend REJECT the 4B prefix for stage-1**, per D-G6.4 ("4B prefix는 볼륨 숫자에 종속: class-(d) 점유율
× 튜플당 4B가 유의미할 때만 UG1 안건 유지, 아니면 자동 기각").

Computed byte impact:
1. `qdata_process_distinct_or_sort`'s Q1 measurement (`p0.2b-byte-volume.md` §9 table): 1,200,000 bytes
   attributed to the DISTINCT-dedup sort-input buffer, receiving all 50,000 `vh_profile` rows before
   reduction to 100 groups ⇒ ≈ **24 bytes/tuple average** for this class-(d) site.
2. An 8B→4B prefix reduction saves exactly 4 bytes/tuple ⇒ **4/24 ≈ 16.7%** local byte reduction *within
   this one class-(d) site*, if it were representative of class-(d) sites generally.
3. Applying that local 16.7% ratio to the measured class-(d) *share* of total list-file write volume:
   - Under the combined coverage workload (12.12% class-(d) share): **12.12% × 16.7% ≈ 2.0% of total
     measured list-file write bytes** — the stage-1-relevant number, since D-G6.1 already measured this
     exact workload as the basis for the <30% framing baseline decision.
   - Under the Q1+Q2-only reweighting (99.2% class-(d) share, the pessimistic/optimistic-for-4B-adoption
     case): **99.2% × 16.7% ≈ 16.6% of total list-file write bytes** — the upper bound this project's own
     evidence supports, and still workload-mix-dependent, not a fixed engine property.

Even at the upper end of this range (≈16.6%, only reachable under a workload mix this audit does not claim
is representative — `p0.2b-byte-volume.md` §9's own caveat: "there is no single representative mixture
ratio... defined anywhere in ralplan/grilled_plan"), the win is modest relative to the implementation risk:
threading a per-tuple class tag through the 2 polymorphic utilities P0.2 §6 finding 1 identifies
(`qfile_sort_list_with_func` list_file.c:4654, `qfile_combine_two_list`/`external_sort.c:5298`) that
"cannot carry a fixed class tag" at the creation-site level, plus covering the ~9 `VERIFY(shape)` rows P0.2
flags as needing an `S_BACKWARD`-reachability trace before they can safely default away from legacy
(scan_manager.c:7863's `scan_prev_scan_local` generic backward-scan mechanism, P0.2 §6 finding 2) — none of
which this project's stage-1 scope currently budgets for.

### (c) Rationale

D-G6.4 makes 4B prefix strictly *derivative* of the same class-(d) volume measurement that already gates
framing itself — there is no independent case for 4B once framing's own volume conditioning is applied,
because 4B is a refinement *within* framing (an even-smaller length-prefix for the same already-narrow
class-(d) population), not an independent lever. Given (1) the class-(d) population is P0.2's smallest,
most narrowly-defined class (10 of 44 sites, with 8 more explicitly excluded), (2) the computed byte impact
is low-single-digit percent under the measured coverage workload and only reaches double digits under an
unrepresentative reweighting, and (3) the implementation cost (per-tuple class threading through
polymorphic utilities, S_BACKWARD-reachability verification for ~9 unresolved rows) is nontrivial and
shared with — not separate from — framing's own already-budgeted P1.1(d) cross-list governance work,
stage-1 should not carry 4B as an additional deliverable. This defers cleanly into Stage B/campaign
(Proposal iii) where the native-endian format-versioning work (`p1.2-b-sketch.md` §1.2's per-page tag) is
already introducing new header-byte-layout machinery that a future 4B refinement could piggyback on at
much lower marginal cost than doing it standalone at stage 1.

### (d) Prompt

**REJECT** the 4B prefix for stage-1 scope; defer to Stage B/campaign (Proposal iii) where header-layout
work is already in scope. `APPROVE / MODIFY / REJECT`.

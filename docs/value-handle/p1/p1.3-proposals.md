## Proposal (ii): Per-cell thresholds [X]×3 + prediction table (D-G3)

### Why the P0.3 headroom input is degenerate — re-grounding is mandatory

ralplan.md §3 P1.3(ii) originally specified: "[X] derived from P0.3 headroom ceiling." **This input is
degenerate.** `p0.3-peek-copy-profile.md` §2 shows `heap_attrvalue_read` (the sole caller of both
instrumented functions) unconditionally chains peek→copy for *every* attribute access — `peek_count` ≡
`copy_count` by construction, so the "peek ratio" is trivially 0.5 regardless of workload
(`p0.3-peek-copy-profile.md` §3 table: all three queries report exactly 0.500 for both fixed and variable
categories). There is no existing peek-without-copy fast path on this code path to measure a headroom
ceiling from — as `p0.3-peek-copy-profile.md` §2 itself concludes: "P1 should re-ground the headroom claim
against [disk-direct cmpdisk] sites... not this pair." **This proposal follows that instruction**: every
[X] below is derived from the `cmpdisk` disk-direct comparison cost structure P0.1 grounds
(object_primitive.c:11897-11960 compressed-varchar per-compare malloc+decompress; :8706-8880 NUMERIC
double-readval; list_file.c:4505 disk-direct sort-compare dispatch), **not** from the peek/copy ratio.

**Sort-key storage mechanism (LEADER design decision, binding, pre-UG1 revision pass)**: the CV-sort/
NUM-sort derivations below use the *corrected* stage-1 mechanism, grounded in spec f17 ("정렬키는 정렬
진입 시 1회 해제(비교당 해제 금지)") and user-confirmed R14 — **not** the earlier "8B inline-proxy compare"
description this document previously carried for CV-sort (moved below to the abbrev sub-cell paragraph,
where it belongs per P2.3+/D-G5). Concretely: (1) a compressed-varchar (or NUMERIC precision>18) sort-key
column is decompressed/decoded **once per entry**, at sort-entry construction, into **sort-owned
per-entry storage** (allocated from the sort's own memory budget, not the per-scan one-row scratch);
(2) the sort entry's `datum1` holds a **pointer** into that storage for VARCHAR/CHAR — no 8B content
proxy for varchar in stage 1 (abbreviated keys stay deferred per D-G5); NUMERIC(p≤18) keeps its exact
int64 `datum1` proxy (§s.3, unaffected by this correction — the "no 8B proxy" rule is varchar-specific,
since NUMERIC's proxy is lossless-exact, not abbreviated); (3) the tuple **body** stays compressed in
temp pass-through — R2 ("sort-ingestion decompress inflation") is therefore a **key-column-only**
inflation, accounted as such, not a tuple-body inflation; (4) external-sort spill writes the
already-built bytes (including detoasted keys) **verbatim** into run entries (key-only inflation,
counted). The fallback trigger is **NOT a run/spill budget check**: it is a **per-entry `area_size`
pre-check at `qfile_make_sort_key` build time** (the compressed-string header's
`expected_decompressed_size` is read before any decompression) — on failure, **that entry only**
falls back to the legacy per-compare decompress path (correctness preserved, win lost for that entry,
counted via `Num_sort_key_decompress_fallback` — never silent) [wording synced to §s.2.1 per architect
iter-2 NEW-3]; (5) win model: per-compare malloc+decompress `O(N log N)` → per-entry decompress
`O(N)` + a plain byte compare per compare. **A_sort_key mode note** (key set == output set — exactly
the W1 headline shape): output tuples are reconstructed from SORT_REC, so the first-key column is
re-serialized into the output list as a valid *uncompressed* form (output inflation LIMIT-bounded,
counted by an R2 output-file term) — see §s.2.2. Full mechanism: `p1.1-valueslot-design.md`
sections §s.2/§s.2.1/§s.2.2/§s.4 revised
(peer-owned; not this document's file to edit, cited here for the threshold re-derivation below).

### (b) Concrete provisional numbers — cost-model derivation (all `proposal-pending-UG1`)

**Shared assumptions**: `N` = 500,000 rows (P2.3 bench cell row count, per ralplan's P2.3 matrix);
`log₂(N) ≈ 18.93`; comparisons `≈ N·log₂(N) ≈ 9.46M` (≈9.5M, matching the prior approximation). Each
cell's formula below states its own challengeable cost-ratio assumption explicitly — these are **not**
independently measured by any P0 artifact and must be re-derived once P2.3/P3.8 numbers exist (per the
`[P0-CONDITIONAL]` note after the table).

**FL-filter — relabeled "UG1 policy threshold (not derived)", formula shown to explain why:**

Per-row cost has two components: `C_dispatch` (the `cmpdisk` function-pointer indirection — an indirect
branch, likely mispredicted on type-heterogeneous columns) and `C_bswap` (one `OR_GET_*` instruction,
issue-port throughput ~1/cycle). For a column accessed exactly once per row (the common case):
`T_legacy = C_dispatch + C_bswap` and `T_new = C_dispatch + C_bswap` — **identical**, because A안 does not
remove either component (bswap survives to Stage B per P-6; dispatch is retained per D-G8). For a column
referenced `k≥2` times within the same row (predicate + projection/sort, the only case ValueSlot's
deform-once actually helps, `p1.1-valueslot-design.md` §a.4): `T_legacy(k) = k·(C_dispatch+C_bswap)` vs.
`T_new(k) = (C_dispatch+C_bswap) + (k-1)·C_arrayread` (subsequent references are a `values[]` array read,
`C_arrayread ≈ 0` relative to a dispatch+bswap). **The formula has no measured free parameter**: the
`k≥2` redundant-within-row-access frequency in a real filter-heavy workload is not measured by any P0
artifact (P0.3's own queries reference each column at most twice). Because the model cannot be evaluated
without a number nobody has measured, **[X]_FL = 3% is a "UG1 policy threshold (not derived)"** — a
conservative, low provisional pick consistent with D-G3's qualitative floor rationale (weakest cell, no
`O(N log N)` multiplication), not a computed output of the dispatch/bswap formula above. `do not fake a
derivation` — this label is the honest alternative the critic's finding requires.

**CV-sort — challengeable formula + assumptions, recomputed from the corrected mechanism:**

> `T_old ≈ N·log₂(N)·(2·C_decompress + C_cmp)` (today: both operands decompressed, every comparison,
> object_primitive.c:11897-11960)
> `T_new ≈ N·C_decompress + N·log₂(N)·C_cmp` (corrected mechanism: detoast-once per entry at sort
> ingestion, `N` decompressions total, then a plain byte compare per comparison against already-detoasted
> bytes)

Assumption 1 (challengeable): `r = C_decompress / C_cmp ≈ 50` — malloc+decompress assumed ~1-2 orders of
magnitude costlier than a plain post-decompress byte compare. Compare-path-only reduction:
`1 - (r+log₂N)/(log₂N·(2r+1)) = 1 - (50+18.93)/(18.93·101) = 1 - 68.93/1911.93 ≈ 96.4%`.

Assumption 2 (challengeable, and the one the prior draft's "8B inline-proxy" framing skipped): the
`T_old`/`T_new` model above only covers the **compare path** — a real CV-sort cell's wall-clock also
includes data movement into sort memory, external-sort run I/O, and merge-phase overhead the model does
not touch. Assume `f_cmp ≈ 40%` — the compare path's share of total CV-sort cell wall-clock (unmeasured
pending P2.3, stated as a challengeable split, not a derivation).

**[X]_CV = f_cmp × compare-path reduction ≈ 0.40 × 0.964 ≈ 38.6% → provisional [X]_CV ≈ 38%** (recomputed
honestly from the corrected mechanism; supersedes the prior placeholder 35%, same "primary gain cell" band
— the compare-path elimination is large under Assumption 1 regardless of its exact value, because
`C_decompress` is assumed to dominate `C_cmp` by construction, so the headline number is driven mostly by
`f_cmp`, the more genuinely uncertain of the two assumptions).

**Abbreviated-key sub-cell upside (P2.3+/D-G5 — explicitly out of stage-1 scope, moved here per this
revision pass)**: the previously-misplaced claim belongs here, not in the stage-1 CV-sort row above — PG's
abbreviated-key machinery (`sortsupport.h:172/182/191`, Proposal i's reserved-slot hook) would replace a
plain byte compare against detoasted storage with an **8B *lossy* inline proxy compare** for
non-tie-breaking comparisons, falling back to the full comparator only on proxy ties. This is a
**campaign-scope (Stage C) upside measurement target for the P2.3 abbrev sub-cell bench**, not part of the
stage-1 (A안) mechanism described above — stage-1's `datum1` for VARCHAR/CHAR is a pointer to per-entry
detoast-once storage, never an 8B content proxy (LEADER decision above; D-G5).

**NUM-sort — challengeable formula + assumptions, same treatment:**

> `T_old ≈ N·log₂(N)·(2·C_readval + C_cmp)` (today: `mr_data_readval_numeric` called twice per comparison,
> object_primitive.c:8838-8880)
> `T_new ≈ N·C_readval + N·log₂(N)·C_cmp` (decode-once at deform, `p1.1-valueslot-design.md` §a.3, plus the
> exact int64 `datum1` proxy compare for `p≤18` columns, §s.3 — this proxy is lossless, not abbreviated, so

Assumption 1: `r = C_readval / C_cmp ≈ 10` — a structural header-parse + bounded `memcpy` decode, assumed

Assumption 2: `f_cmp ≈ 20%` — lower than CV-sort's 40%, since NUM-sort's per-compare cost has no

(recomputed from the prior placeholder 15%, same order of magnitude, now formula-backed rather than a bare

### [Y] — Slice adoption threshold (env-ON vs env-OFF on W1) — operationalized

**Deciding P3.8 configuration**: **single-thread** is the **attribution-clean primary** measurement
config — it isolates A안's own mechanism effect from thread-contention/cache-state noise a multi-thread or
cold-cache run would fold in. **Multi-thread and cold-cache runs are measured and reported alongside for
context, but the adoption gate applies only to the single-thread configuration's W1 median.**

**Formula** (same `cubrid_rel` build, single runtime toggle):

> `PASS_Y ≡ (median_{env-OFF, single-thread, W1} − median_{env-ON, single-thread, W1}) / median_{env-OFF, single-thread, W1} ≥ [Y]`

`env-ON`/`env-OFF` gate the A-slot mechanism at runtime on an otherwise identical build (isolates the
mechanism's own effect from any build-level confound); `W1` = the CV-sort-shaped end-to-end slice workload
(D-G3 prediction table above).

**[Y] = 10% — relabeled "UG1 policy threshold (not derived)"**: the measurement formula above is fully
specified (env-ON vs env-OFF, same build, single-thread W1 median) — that part is not in question. The
*threshold value* itself rests on an unmeasured microbenchmark-to-slice dilution ratio: a prior draft
described [Y] as "roughly 1/3 of [X]_CV," which is a P1 judgment call about typical dilution from an
isolated cmpdisk-cell ceiling to a real end-to-end slice gain, not derived from any P0/P2 measurement —
presenting that ratio as a derivation would be dishonest, per the critic's finding. Kept at 10% as a
provisional policy pick (order-of-magnitude consistent with "~1/3 of [X]_CV≈38%" ≈13%, rounded down to a
rounder, slightly more conservative figure), explicitly revisitable once P2/P3.8 numbers exist.

### [Z] — B-entry threshold (bswap share of remaining overhead) — operationalized

**Measurement protocol**: `perf`/VTune attribution of bswap-class symbols (`OR_GET_*`/`OR_PUT_*` byte-swap
inlines, object_representation.h:102-131/171-210; `htonf`/`htond` software fallback, byte_order.c:159-199)
via **inline-aware source attribution on a release build** (per ralplan.md Decision Driver 1's
methodology — required because these are `static inline`/macro-shaped call sites a symbol-only profile
would fold into their caller, hiding the bswap-specific share), taken as a share of **remaining post-A안
query CPU on the FL cells**.

**Denominator**: total server-side query CPU **minus I/O wait** (I/O wait is excluded because it is
orthogonal to the bswap-vs-not-bswap question this threshold gates; including it would dilute the ratio by
an amount unrelated to B안's marginal value).

**Per-cell weights** (combining FL-filter and FL-sort into the "combined FL remaining-overhead mix" a
prior draft referenced only qualitatively):

> `[Z]_combined = w_FL-filter × [Z]_FL-filter + w_FL-sort × [Z]_FL-sort`

| Cell | Weight | Rationale |
|---|---|---|
| FL-filter | **w = 0.6** | Filter/predicate-shaped workloads (W3/Q6-shaped proxy) are assumed to dominate the FL-shaped share of a typical query mix's CPU time — filtering runs over the full scanned population, sorting only over the (usually smaller) post-filter result. |
| FL-sort | **w = 0.4** | ORDER-BY-on-fixed-length-column workloads contribute the remaining assumed share. |

**[Z] = 40%, and the 0.6/0.4 weight split, are both "UG1 policy thresholds (not derived)"** — the
measurement *protocol* above (perf/VTune inline-aware attribution, `CPU − I/O wait` denominator) is
concrete and mechanically well-defined; the *relative-frequency weighting* between filter-shaped and
sort-shaped FL workloads in whatever production query mix eventually matters is not measured by any
P0/P2 artifact, and picking it from first principles rather than a real workload profile is a judgment
call — flagged explicitly rather than dressed up as a derivation, per the critic's finding.

**Ablation alternative, if exact attribution proves infeasible in P3**: a **counter-instrumented
bswap-elision prototype variant** in the bench harness — a build variant that no-ops the
`OR_GET_*`/`OR_PUT_*` conversion on the FL cells' read path (correctness-unsafe, bench-only) and measures
the resulting delta directly, rather than relying on profiler symbol attribution; the ablation delta serves
as an upper-bound cross-check on the perf/VTune attribution number.

`[Z]` remains `[P0-CONDITIONAL]` beyond the labeling above: it assumes A안's other mechanisms land as
measured (not merely as designed) in P3.8 — see `p1.2-b-sketch.md` §2.3's own `[P0-CONDITIONAL]` flag on
the same parameter.

### (c) Rationale (all three [X] + [Y] + [Z])

D-G3 replaces the single FL-filter STOP gate with a 3-cell gate specifically because FL-filter alone is
"최약체 셀" (weakest cell) and could produce "잘못된 STOP" (a wrong stop recommendation) — the prediction
table above is the reason: FL-filter's mechanism (deform-once only, no multiplicative effect) is
structurally incapable of showing the same magnitude of improvement as CV-sort/NUM-sort's multiplicative
malloc+decompress/double-readval elimination, so judging the whole project on FL-filter alone would
systematically underrate A안. Re-grounding every threshold on the `cmpdisk` cost structure (not the
degenerate 0.5 peek ratio) is the only way to derive threshold numbers that are falsifiable against a real
mechanism rather than an artifact of `heap_attrvalue_read`'s unconditional chaining. This revision pass
additionally corrects two honesty gaps a pre-UG1 review surfaced: (1) CV-sort's cost model previously
attributed its win to an 8B content-proxy compare that is not part of the stage-1 mechanism (that claim now
lives in the abbrev sub-cell paragraph, §(b), where it is a P2.3+/D-G5 upside measurement target, not a
stage-1 design element); (2) FL-filter's threshold and both of [Y]/[Z] are now explicitly labeled as policy
picks rather than dressed-up derivations wherever the underlying model genuinely has no measured free
parameter to plug in — a threshold that cannot honestly be derived should say so, not simulate a derivation
it cannot support.

## Proposal (iv): 4B prefix — volume-conditioned REJECT for stage-1 (D-G6.4)

### (a) P0 evidence citation

- **P0.2** (`p0.2-list-class-audit.md` §1/§2/§6): "reverse scan is actively used" — 4 real
  `qfile_scan_list_prev` call sites (query_executor.c:6142,23533,23567; scan_manager.c:7863) plus
  sort-key backtrack (list_file.c:3632) — confirming ralplan.md's pre-audit conclusion is correct: "Blanket
  4B reduction NOT viable. 4B potentially viable only for class-(d)." P0.2 §3 confirms only **10 class-(d)
  sites** exist (of 44 total creation sites), with **8 more FORBID-excluded** (would-be-(d) but disqualified
  as raw-copy sources into cross-list edges) — i.e. the 4B-eligible population is already the smallest,
  most narrowly-scoped class in the audit.
- **P0.2b** (`p0.2b-byte-volume.md` §9, D-G6.1 headline): class-(d) write-byte share = **12.12%** of total
  measured list-file write bytes on the combined P0.3+supplemental workload (1,226,400 / 10,117,848 bytes)
  — below the proposed <30% baseline (ralplan.md/D-G6's threshold for keeping framing, by extension 4B, in
  scope for stage 1) — **but** flagged workload-mix-sensitive: a Q1+Q2-only reweighting (dropping the
  forced-hash-join and unbounded-sort queries from the denominator) pushes the same class-(d) numerator to
  **99.2%** of that narrower total (`p0.2b-byte-volume.md` §9 composition caveat).

### (b) Concrete recommendation + computed byte impact

**Recommend REJECT the 4B prefix for stage-1**, per D-G6.4 ("4B prefix는 볼륨 숫자에 종속: class-(d) 점유율
× 튜플당 4B가 유의미할 때만 UG1 안건 유지, 아니면 자동 기각").

Computed byte impact:
1. `qdata_process_distinct_or_sort`'s Q1 measurement (`p0.2b-byte-volume.md` §9 table): 1,200,000 bytes
   attributed to the DISTINCT-dedup sort-input buffer, receiving all 50,000 `vh_profile` rows before
   reduction to 100 groups ⇒ ≈ **24 bytes/tuple average** for this class-(d) site.
2. An 8B→4B prefix reduction saves exactly 4 bytes/tuple ⇒ **4/24 ≈ 16.7%** local byte reduction *within
   this one class-(d) site*, if it were representative of class-(d) sites generally.
3. Applying that local 16.7% ratio to the measured class-(d) *share* of total list-file write volume:
   - Under the combined coverage workload (12.12% class-(d) share): **12.12% × 16.7% ≈ 2.0% of total
     measured list-file write bytes** — the stage-1-relevant number, since D-G6.1 already measured this
     exact workload as the basis for the <30% framing baseline decision.
   - Under the Q1+Q2-only reweighting (99.2% class-(d) share, the pessimistic/optimistic-for-4B-adoption
     case): **canonical value 16.5%** of total list-file write bytes (`p1.1-format-selection.md` §4.3's
     directly-computed 204,400/1,236,024 ≈ 16.5396% ≈ 16.5% — the single sourced figure; this document's
     own `99.2% × 16.7% ≈ 16.6%` local arithmetic was a rounding drift against that canonical value, now
     retired) — the upper bound this project's own evidence supports, and still workload-mix-dependent, not
     a fixed engine property.

Even at the upper end of this range (≈16.5%, only reachable under a workload mix this audit does not claim
is representative — `p0.2b-byte-volume.md` §9's own caveat: "there is no single representative mixture
ratio... defined anywhere in ralplan/grilled_plan"), the win is modest relative to the implementation risk:
threading a per-tuple class tag through the 2 polymorphic utilities P0.2 §6 finding 1 identifies
(`qfile_sort_list_with_func` list_file.c:4654, `qfile_combine_two_list`/`external_sort.c:5298`) that
"cannot carry a fixed class tag" at the creation-site level, plus covering the **12** `VERIFY(shape)` rows
P0.2 flags (`p1.1-format-selection.md` §1.3, `p0.2-list-class-audit.md` §6 finding 2 — corrected from a
prior "~9" approximation to the audit's actual count) as needing an `S_BACKWARD`-reachability trace before
they can safely default away from legacy (scan_manager.c:7863's `scan_prev_scan_local` generic
backward-scan mechanism, P0.2 §6 finding 2) — none of which this project's stage-1 scope currently budgets
for.

### (c) Rationale

D-G6.4 makes 4B prefix strictly *derivative* of the same class-(d) volume measurement that already gates
framing itself — there is no independent case for 4B once framing's own volume conditioning is applied,
because 4B is a refinement *within* framing (an even-smaller length-prefix for the same already-narrow
class-(d) population), not an independent lever. Given (1) the class-(d) population is P0.2's smallest,
most narrowly-defined class (10 of 44 sites, with 8 more explicitly excluded), (2) the computed byte impact
is low-single-digit percent under the measured coverage workload and only reaches double digits under an
unrepresentative reweighting, and (3) the implementation cost (per-tuple class threading through
polymorphic utilities, S_BACKWARD-reachability verification for 12 unresolved rows) is nontrivial and
shared with — not separate from — framing's own already-budgeted P1.1(d) cross-list governance work,
stage-1 should not carry 4B as an additional deliverable. This defers cleanly into Stage B/campaign
(Proposal iii) where the native-endian format-versioning work (`p1.2-b-sketch.md` §1.2's per-page tag) is
already introducing new header-byte-layout machinery that a future 4B refinement could piggyback on at
much lower marginal cost than doing it standalone at stage 1.

### (d) Prompt

**REJECT** the 4B prefix for stage-1 scope; defer to Stage B/campaign (Proposal iii) where header-layout
work is already in scope. `APPROVE / MODIFY / REJECT`.

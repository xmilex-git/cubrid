## 0. Bottom line

**The user's intuition is correct.** Traced against the actual stage-1 mechanism (not just the
hypothesis in the task brief), **no CV-sort-shaped multiplicative win exists anywhere in the NL-join
family for stage-1** — not for heap-scan-inner, not for list-scan-inner, not for index-inner. The
per-visit "boundary-copy elimination" ValueSlot provides is real but is exactly the same small,
constant-per-access, non-multiplicative saving FL-filter already claims — it does not compound with
NL join's repeated-visit structure, because **the repetition itself (re-visiting the same physical
inner row once per outer probe) is exactly the part of the cost stage-1's per-scan lifetime boundary
cannot touch.** §7 below is a grounded rejection of the "NLJ-CV multiplicative bench cell" as
originally hypothesized, with a corrected, honest characterization of what a NL-join bench cell would
actually measure if built.

## 1. Mechanism trace, per inner-scan shape

### (a) inner = heap scan (naive `S_HEAP_SCAN`, no index)

Per-row attribute access goes through `heap_attrvalue_read` (`heap_file.c:10670`), which
unconditionally chains peek→copy (P0.3's finding, still true at this HEAD — confirmed by re-reading
the live function body):

```
heap_file.c:10702-10708   if (attrepr->is_fixed) heap_attrvalue_point_fixed (...)      /* peek */
                          else                    heap_attrvalue_point_variable (...)   /* peek */
heap_file.c:10712         return heap_attrvalue_transform_to_dbvalue (value, attrepr, &raw);  /* copy, always */
```

`heap_attrvalue_transform_to_dbvalue` (`heap_file.c:10598`) is where the actual per-type read happens,
at `heap_file.c:10644`:

```c
rv = pr_type->data_readval (&buf, &value->dbvalue, attrepr->domain, raw->length, false, NULL, 0);
```

`copy = false` is passed — but for `DB_TYPE_CHAR`/`DB_TYPE_VARCHAR` this dispatches to
`mr_readval_char_type_common` (`object_primitive.c:11761`), whose own doc comment states the
contract precisely: *"`copy`(in): false → peek (zero-copy **when uncompressed**); true → deep copy"*
(`object_primitive.c:11749`) — the qualifier matters. The actual branch is:

```c
object_primitive.c:11806   if (copy || (compressed_size > 0))   /* decompress regardless of copy=false */
```

I.e. **for a compressed column (`compressed_size > 0`), the function decompresses unconditionally,
even on the "peek" path** — `db_private_alloc` + `cubcompress::decompress<LZ4>` runs on every single
call to `data_readval` for that column, every time, full stop. There is no existing fast path here to
skip (P0.3's own conclusion, still true).

In a naive NL join, the inner scan is fully reset and re-executed once per outer-row probe
(`heap_scan_reset`-class rescan). Each of the `N_inner` physical rows is therefore re-visited, and its
join-key attribute re-read-and-decompressed, once **per outer probe** — total attribute-read/decompress
count = **O(N_outer × N_inner)**, not O(N_inner). This is the real per-probe-pair multiplicative cost,
but it lives in the **READ path** (`heap_attrvalue_read` → `data_readval` → `mr_readval_char_type_common`),
not, as traced below, the compare path.

### (b) inner = list-file rescan (`S_LIST_SCAN`, materialized inner)

Per-access value fetch for a materialized-inner (e.g. list-file-backed subquery or intermediate result)
goes through `fetch_peek_dbval_slow`'s `TYPE_POSITION` case (`fetch.c:4039-4065`):

```
fetch.c:4048   flag = qfile_locate_tuple_value (tpl, regu_var->value.pos_descr.pos_no, &ptr, &length);
fetch.c:4057   or_init (&buf, ptr, length);
fetch.c:4059-4060   if (pr_type->data_readval (&buf, *peek_dbval, regu_var->value.pos_descr.dom, -1,
                                                false /* Don't copy */, NULL, 0) != NO_ERROR) ...
```

Same `pr_type->data_readval` entry point as (a), same `copy=false`-but-decompress-if-compressed
behavior at `object_primitive.c:11806`. Every re-visit of an inner list-file tuple across outer
iterations re-triggers this call — same O(N_outer × N_inner) decompression count as (a), for the same
structural reason (the inner is fully re-scanned per outer probe).

### (c) index-NL (`S_INDX_SCAN` inner, with covering-index scratch)

The covering-index list buffer is `scan_init_indx_coverage` (`scan_manager.c:747`), confirmed class-(d)
in `p0.2-list-class-audit.md` §3 row 3 ("Index-covering-scan buffer (`indx_cov->list_id`). Opened via
`qfile_open_list_scan` only (forward); rotated in-place by `scan_reset_scan_block`/`scan_next_index_scan`
... never in `xasl->list_id`, cache, or `qfile_scan_list_prev` caller list."). This buffer avoids a
*second heap fetch* for output columns when the index covers the query — it is orthogonal to the
join-key comparison cost itself.

The join-key comparison during the B-tree descent is `btree_compare_key` (`btree.c:19461`). For a
**single-column** key (the common case — not `MIDXKEY`), it dispatches at `btree.c:19564`:

```c
c = key_domain->type->cmpval (key1, key2, do_coercion, total_order, NULL, key_domain->collation_id);
```

`cmpval` = `f_cmpval` = `mr_cmpval_string`/`mr_cmpval_char` (already-decompressed-DB_VALUE compare, see
§2 below) — **not** `cmpdisk`. Whatever DB_VALUE holds the visited node/leaf key must already be
decompressed by the time this runs (via the index's own `index_readval` path, same
decompress-if-compressed convention as (a)/(b)). Cost per outer probe is O(log N_inner) key
reads/decompresses (tree descent), not O(N_inner) — asymptotically far cheaper than (a)/(b), but this
is a legacy access-method property, unrelated to ValueSlot (B-tree internals are outside the pr_type
hook-list surface `p1.3-proposals.md` Proposal (i) scopes for stage 1).

### (d) where the join-predicate compare actually happens — and the critical correction

`eval_pred_comp0` (`query_evaluator.c:2150`, the single-node comparison-predicate evaluator that
handles a join condition like `o.k = i.k`) does:

```
query_evaluator.c:2164   fetch_peek_dbval (thread_p, et_comp->lhs, vd, NULL, obj_oid, NULL, &peek_val1)
query_evaluator.c:2173   fetch_peek_dbval (thread_p, et_comp->rhs, vd, NULL, obj_oid, NULL, &peek_val2)
query_evaluator.c:2186   return eval_value_rel_cmp (thread_p, peek_val1, peek_val2, et_comp->rel_op, et_comp);
```

`eval_value_rel_cmp` bottoms out in `db_value_compare`/`tp_value_compare`, which for CHAR/VARCHAR calls
`f_cmpval` = **`mr_cmpval_string`/`mr_cmpval_char`** (`object_primitive.c:10634`/`10884`) — confirmed by
reading the body: it calls `db_get_string(value1)`/`db_get_string(value2)` directly
(`object_primitive.c:10646-10647`) and does a plain `QSTR_COMPARE` (`object_primitive.c:10697`). **No
decompression happens here** — the strings are already plain bytes, because `fetch_peek_dbval`'s
underlying `data_readval` call already decompressed them once, at read time (per (a)/(b) above).

**This is the one place the task brief's framing needs correcting.** The brief attributes the
per-comparison malloc+decompress to `object_primitive.c:11897-11960`
(`mr_cmpdisk_char_type_common`) reached via the compare path. Tracing every caller of that function
(`f_data_cmpdisk`/`f_index_cmpdisk`, the `cmpdisk`-suffixed accessors) shows it is reached from exactly
two places, **neither of which is join-predicate/filter evaluation**:

1. **Sort comparator**: `list_file.c:4612/4616/4643`, `subkey->sort_f = types->domp[i]->type->get_data_cmpdisk_function ()`
   — this wires `mr_data_cmpdisk_string` (→ `mr_cmpdisk_char_type_common`, `object_primitive.c:10625`)
   as the **external-sort pairwise comparator**, invoked once per sort comparison (O(N log N) times),
   confirming `p1.3-proposals.md`'s CV-sort citation is correctly grounded for *that* cell.
2. **Index build / midxkey element compare**: `object_primitive.c:7921`
   (`dom1->type->index_cmpdisk (...)`, inside `pr_midxkey_compare` for composite-key elements) and
   `btree_load.c:4056` (`dom->type->index_cmpdisk (...)`, bulk index-load duplicate-key check) — both
   index-maintenance-shaped, not query-time join-predicate evaluation.

`data_cmpdisk` (the plain, non-index accessor `pr_type::data_cmpdisk`, `object_primitive.h:171`) has
**zero call sites anywhere in `src/`** other than the registration table itself — it is wired but
unused outside the sort-comparator wiring above, which retrieves the raw function pointer via
`get_data_cmpdisk_function()` rather than the `data_cmpdisk` accessor method. Single-column B-tree
search (§(c) above) also does not reach it — `btree_compare_key` uses `cmpval`, not `cmpdisk`, for
non-MIDXKEY domains.

**Net correction**: NL join's join-predicate comparison itself never re-decompresses. The
multiplicative-looking O(N_outer × N_inner) decompression count in (a)/(b) is real, but it comes from
**re-reading (readval) the same physical inner row from scratch on every outer probe**, not from a
compare-time re-decompression of an already-materialized value. This distinction is exactly why
ValueSlot's stage-1 mechanism (below) cannot help it.

## 2. Why ValueSlot stage-1 cannot capture this cost (lifetime-scope mismatch)

`p1.1-valueslot-design.md` §a.3 states the ValueSlot mechanism for `VC_COMPRESSED` explicitly:

> "**Lazy**: at deform time, store only a pointer to the raw compressed payload (no decompression yet).
> Decompression happens on **first actual access** that needs plain bytes, into a **per-scan scratch
> buffer** ... **one buffer reused across rows of the same scan**."

This is a real, useful mechanism — but its cache lifetime is exactly **one scan pass**. Two facts pin
this down precisely:

1. `p1.1-lifetime-contract.md` §2's bump-point table, row 2: **"Scan close"** — *"Scan-owned CopiedFrame
   and ValueSlot are torn down ... All entries invalid; ValueSlot itself is deallocated."* An NL join's
   inner scan is closed and reopened once per outer-row probe; ValueSlot (and its lazy-decompress
   scratch buffer) is rebuilt from nothing on every reopen.
2. For list-scan inners, `p1.1-lifetime-contract.md` §2 row 3 states the qfile-scan pointer-validity
   rule is *"valid until the next row's deform, full stop"* — i.e. the **same or narrower** per-row
   granularity; there is no cross-rescan persistence mechanism for list-scan inners either.

So: within **one** scan pass over `N_inner` rows, if a compressed-varchar column is referenced only
**once per row** (the ordinary shape of a simple equi-join predicate `o.k = i.k`), stage-1's
first-access-only lazy decompress and the legacy unconditional-every-read decompress do **the same
number of decompressions per row** — one. ValueSlot's win only appears when the **same row's** column
is referenced **k ≥ 2 times within that one visit** (e.g. the join key is also projected in the output
list, so the predicate's `fetch_peek_dbval` and the output list's separate `regu_variable` fetch both
touch the same attribute) — this is `p1.3-proposals.md`'s own FL-filter "k≥2 redundant-within-row
access" shape, ported to the compressed-varchar case, and it is a **small, linear** win (skip a second
malloc+decompress+`transform_to_dbvalue`, not skip N_outer−1 of the N_outer total decompressions).

The genuinely multiplicative CV-sort win works precisely *because* the sort's caching boundary is wider
than one comparison — `p1.1-valueslot-design.md` §s.2's corrected mechanism decompresses **once at
sort-entry construction**, and that single decompressed copy is then reused across **all** O(log N)
pairwise comparisons that entry participates in during the sort. NL join's structural shape is the
mirror image: the *same physical row* is touched `N_outer` times, but each touch is a **fresh scan
visit**, not a comparison against an already-cached copy — and stage-1's caching boundary (one scan
pass) is drawn exactly at the boundary that would need to be crossed (spanning the *entire outer loop*,
not one scan) to convert this into a CV-sort-shaped win. That would require caching a decompressed copy
of the *whole inner side* across the *entire join*, i.e. an inner-materialization mechanism — which is
what hash join already does structurally (build side hashed/read once, `O(N_inner)` total reads,
independent of `N_outer`), not something stage-1's per-scan ValueSlot design attempts or claims to do.

## 3. Cost-model math (T_old / T_new, explicit assumptions, no fake measurements)

Using the same `T_old`/`T_new` idiom as `p1.3-proposals.md` (ii):

**Varchar join key, heap-scan-inner NL join** (mechanism (a)/(b) above), single reference per row
(no output-list re-reference of the key):

> `T_old ≈ N_outer · N_inner · C_decompress`  (every visit: one `data_readval` call, `object_primitive.c:11806` always decompresses when `compressed_size>0`)
> `T_new ≈ N_outer · N_inner · C_decompress`  (**identical** — ValueSlot's lazy-decompress-once-per-row-within-scan changes *when* the decompress happens, not *how many times*, because each of the `N_outer` visits is a distinct scan pass per §2)

`T_new / T_old ≈ 1` for the dominant term — **no measurable win**, by the same reasoning
`p1.3-proposals.md`'s FL-filter derivation uses for `k=1`: *"For a column accessed exactly once per row
... T_legacy = T_new — identical, because A안 does not remove either component."* The varchar case adds
nothing structurally different for `k=1`; it just substitutes `C_decompress` for `C_dispatch+C_bswap`.

**If the join key (or another compressed column) is also referenced in the output list** (`k=2`
within one visit, the one case that does help):

> `T_old(k=2) ≈ N_outer · N_inner · 2·(C_decompress + C_dbvalue_wrap)`
> `T_new(k=2) ≈ N_outer · N_inner · (C_decompress + C_dbvalue_wrap) + N_outer · N_inner · C_arrayread`

Same shape as `p1.3-proposals.md`'s FL-filter `k≥2` formula (`T_new(k) = (C_dispatch+C_bswap) +
(k-1)·C_arrayread`), just with `C_decompress` substituted for the dispatch/bswap pair, and it is
**still O(N_outer × N_inner) overall** — the win is a constant-factor (~2×, for `k=2`) reduction of a
count that is *already* multiplicative in the join shape, not a reduction of the exponent/order itself.
This is qualitatively identical to what `p1.3-proposals.md` already labels **"UG1 policy threshold (not
derived)"** territory for FL-filter, not a new CV-sort-shaped derivation.

**Int-key (`FL_INLINE`) NL join**, for contrast (assignment's expected control shape):

> `T_old ≈ N_outer · N_inner · (C_dispatch + C_bswap + C_dbvalue_wrap)`
> `T_new ≈ N_outer · N_inner · (C_dispatch + C_bswap)`  (boundary-copy elimination: skip `transform_to_dbvalue`'s DB_VALUE wrap for a `VC_RAW`/`FL_INLINE`-class pass-by-value read, per `p1.1-valueslot-design.md` §a.3's `VC_RAW` row: "No materialization at all")

Also O(N_outer × N_inner) on both sides — **same order as the varchar case**, confirming the
assignment's own prediction that the int-key case is "boundary-copy-only (FL-shaped, small)" is correct
— but the varchar case turns out to be the **same shape**, not the hoped-for CV-sort-shaped
multiplicative one, once the lifetime-scope mismatch in §2 is accounted for.

## 4. Explicit scope statement

- **Inside stage-1's direct-op boundary**: the join predicate comparison itself (`eval_pred_comp0` →
  `fetch_peek_dbval` → `cmpval`, §1(d)) is exactly the "비교/필터/정렬/pass-through" category stage-1
  targets — ValueSlot's deform-once and boundary-copy-elimination apply here, within one row visit.
- **Outside stage-1's boundary, confirmed non-goal**: cross-rescan persistence of deformed/decompressed
  values. `p1.1-lifetime-contract.md` §2's "scan close" bump point tears down ValueSlot on every scan
  reopen — this is **not a bug or an oversight to fix in a later revision of this same document**, it is
  the direct consequence of ValueSlot being a **per-scan** structure (§a.1: "owned by the scan... not
  one struct per attribute per row," but also not one struct spanning multiple scan lifetimes). Making
  it span an entire NL-join outer loop would require a qualitatively different mechanism (inner-side
  materialization/caching across the whole join) — out of stage-1 scope, and structurally closer to what
  hash join already does natively.
- **Also outside stage-1's boundary, confirmed by design**: join **output** materialization (the
  assignment's item 2 non-goal) — unaffected either way by this review's findings, since the cost this
  review traces is entirely in the *input*/predicate-evaluation side of the join, not the output side.

## 5. Does CUBRID's optimizer even produce naive NL join for these shapes?

CUBRID's optimizer enumerates 4 join methods (`query_planner.h:62-65`):
`QO_JOINMETHOD_{NL_JOIN, IDX_JOIN, MERGE_JOIN, HASH_JOIN}`, all generated as competing candidate plans
and cost-compared (`query_planner.c:6362`/`6516`/`6676`/`8541` — each method's candidate plan is
constructed unconditionally when applicable, then compared by cost in `qo_find_best_plan`-class code).
For an equi-join on two tables with no usable index on the join column and non-trivial row counts (the
"outer 1K × inner 10K" shape the task brief proposes), CUBRID's cost-based optimizer would, by default,
be expected to prefer **`HASH_JOIN`** (O(N_outer+N_inner) build+probe cost model) over naive `NL_JOIN`
(O(N_outer×N_inner) cost model) — the same reason every cost-based optimizer avoids naive NL join at
this scale absent a forcing hint or a very small outer estimate.

This does **not** mean naive NL join is unreachable or unmeasurable: CUBRID exposes explicit
join-method hints (`csql_grammar.y:23896-23938`, `parse_tree.h:1211-1214`) — `USE_NL`, `USE_IDX`,
`USE_MERGE`, `USE_HASH`, `NO_USE_HASH` — precisely so a query can force a specific join method
regardless of the optimizer's own cost-based preference. `QO_IS_NL_JOIN` (`query_graph.h:589`) treats
`NL_JOIN` and `IDX_JOIN` as the same broad "nested-loop-shaped" family; to force the **pure heap-scan
inner** (no index at all on the join column) shape §1(a) analyzes, the bench query needs both
**`/*+ USE_NL */`** and **no index on the inner join column** (so `IDX_JOIN` is never a candidate) —
and its execution plan must be checked (e.g. `csql`'s `;plan` output) to confirm `NL_JOIN` was actually
chosen, not silently promoted to something else.

`IDX_JOIN` (index-NL, §1(c)) is, separately, a **very common naturally-occurring** plan shape in real
schemas (any join through an indexed foreign key) — more representative of "NL join" as it occurs in
practice than the naive heap-scan variant, and its join-key comparison cost is already O(log N_inner)
per probe under the legacy engine (§1(c)), unrelated to ValueSlot either way.

## 6. Verdict + recommendation

**Verdict: grounded rejection of the NLJ-CV multiplicative bench-cell hypothesis, as originally framed.**
Stage-1 ValueSlot does not deliver a CV-sort-shaped multiplicative win for any NL-join inner-scan shape
(heap, list, or index). The mechanism that looked promising in the task brief (per-comparison
decompress via `mr_cmpdisk_char_type_common`) does not participate in join-predicate evaluation at all
— that function is a sort-comparator/index-build-only code path (§1(d)). The mechanism that *is* real
(per-visit decompress via `mr_readval_char_type_common`, re-triggered on every rescan) is exactly what
stage-1's per-scan ValueSlot lifetime boundary is structurally unable to cache across (§2). What
survives is the same small, linear, k≥2-within-one-visit boundary-copy-elimination FL-filter already
covers — a compressed-varchar variant of it would show a modest constant-factor improvement (bigger
constant than plain FL-filter's dispatch+bswap saving, since it also skips a malloc+decompress on the
second within-row reference, but still linear, not multiplicative).

**Recommendation: do NOT add `NLJ-CV`/`NLJ-FL`/`W5` to the P2 bench matrix as multiplicative-win cells.**
Adding them would either (a) measure ~0% improvement (if the join predicate references the key exactly
once per row, the ordinary case) and produce a spurious "stage-1 doesn't help joins" narrative that
misattributes a lifetime-scope limitation as a general failure, or (b) measure a small FL-filter-shaped
improvement (if the bench query is deliberately shaped with a k≥2 within-row reference) that is
redundant with — not additive to — the existing FL-filter gate cell's own mechanism, just with a bigger
per-call constant. Neither outcome earns a new named cell.

**If a bench cell in this space is still wanted**, the honest options are:
1. **Skip it.** The existing FL-filter cell (gate) and CV-sort cell (gate) already bound the two
   mechanisms this review found (linear boundary-copy elimination; multiplicative detoast-once). NL
   join doesn't introduce a third mechanism — it just re-exercises FL-filter's linear one under a
   join-shaped access pattern, which the existing FL-filter cell's own methodology (predicate compare
   path, `p1.3-proposals.md` §b-2) already measures without needing a join at all.
2. **If measured anyway for narrative/documentation value** (e.g. to have a concrete answer the next
   time this question comes up), scope it explicitly as a **P2.3 measurement-only, non-gate** cell —
   consistent with the existing "3 named P2 release cells vs. 5 measurement-only cells" split
   (`p1.3-proposals.md` §b-2) — labeled to predict **~0%** for `k=1` (single join-key reference) and a
   **small, FL-filter-magnitude** improvement for `k=2` (join key also projected), with the query
   forced via `/*+ USE_NL */` + no index (§5) and the plan verified via `;plan` output before trusting
   any number. Do not call it "CV-sort-analog" in any prediction table — it is not analogous; it is
   FL-filter-analog, ported to a compressed type.

**Gate-cell impact: none.** The UG1.5 gate stays exactly `{FL-filter, CV-sort, NUM-sort}` per
`p1.3-proposals.md` §(b-2)/§(b-3) — this review adds no 4th gate cell and does not challenge the
existing 3. It also does not change `[X]_FL`/`[X]_CV`/`[X]_NUM`/`[Y]`/`[Z]`'s provisional values — those
were derived from the sort/dispatch cost structures directly, not from any join-shaped assumption this
review touches.

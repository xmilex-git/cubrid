### 1.3 `VERIFY(shape)` rows — default to legacy, name the exit trace

`[P0.2] §2` leaves 12 of the 29 creation-site groups as `VERIFY(shape)` — classification depends on
runtime query shape not resolvable by static tracing within P0's budget (e.g.

the whole mechanism already relies on (§1.1/§1.2) — a `VERIFY(shape)` row costs nothing at runtime beyond
staying on the existing legacy path.

**Named upgrade trace (P1-exit / P3-entry task)**: `[P0.2] §6 finding 2` identifies the exact mechanism
that would resolve these rows precisely: **`scan_manager.c:7863` (`scan_prev_scan_local`) is a generic,
optimizer-selectable backward-scan mechanism reachable from any `QFILE_LIST_ID` consumed as an
`S_LIST_SCAN` access-spec input with `SCAN_ID.direction == S_BACKWARD`.** The task — call it
**`P3.0a: S_BACKWARD-reachability trace`** — is: for each `VERIFY(shape)` creation site, statically or
dynamically determine whether its output list can ever be reached by a consumer whose `SCAN_ID.direction`
is set to `S_BACKWARD` (via `scan_prev_scan_local` or any `qfile_scan_list_prev` caller not already
enumerated by `[P0.1]` rows 16-18). A site proven **never** `S_BACKWARD`-reachable upgrades from
`VERIFY(shape)`/`format_version=0` to a caller-asserted `QFILE_FLAG_LIST_CLASS_D` candidate (still subject
to the FORBID cross-list check, §2); a site proven reachable stays legacy permanently, not just
provisionally. This closes P1 with an explicit, assignable follow-up rather than leaving the 12 rows as
an open question re-litigated at every future P-stage — the trace is scoped as a **P3-entry
prerequisite**, not a P1 blocker, because it requires the same kind of dynamic/exhaustive tracing P0.2
explicitly stated was out of its time budget.

```c
    return NULL;   /* class-(d) lists are never cache-eligible; class-(b) sites never set the tag anyway */
  }
```

This is redundant-by-construction with §1.1 (class-(b)/cacheable sites already never set

**Overflow-tuple exemption** (not a cross-list edge, documented here per the assignment's grouping):
per-tuple overflow status is a property discovered only after serialization

because overflow continuation bytes never pass through the tag-decision or the tag-check code path at

source list, not as the primary enforcement mechanism.

**INHERIT rule for page-level duplicates** (functions #4/#5): dest `format_version` = source
`format_version`, verbatim, no transcode — permitted only when source and dest classes already agree
(which holds today by construction, since the sole caller's source is always (a)/(b)).

## 4. §(e) — Temp framing volume verdict `[P0-CONDITIONAL]`

### 4.1 Framing design (unchanged content, summarized)

recdes-style framing for confirmed class-(d) intermediates only:
- Bound-bit vector + variable-length offset table, in the same shape as heap on-disk records
  (`OR_BOUND_BIT_FLAG`/`OR_GET_BOUND_BIT`/`OR_GET_BOUND_BITS`, `object_representation.h:505-623`;
  `BIG_VAR_OFFSET_SIZE`/`SHORT_VAR_OFFSET_SIZE`, `object_representation.h:507-508`) — reused shape, not
  reused code (temp lists have no class repr_id to look up bound-bit layout from; the layout is derived
  directly from `list_id.type_list`, see below).
- **No MVCC header**: heap records carry `OR_MVCC_FLAG_OFFSET`/`OR_CHN_OFFSET`/insert-delete-tranid
  fields (`object_representation.h:477-481`, `object_representation_constants.h:159-171`) that exist
  solely to support MVCC versioning and heap-page recovery; temp list tuples have neither concept and
  drop this component entirely.
- **Domain from `list_id.type_list`**: `QFILE_TUPLE_VALUE_TYPE_LIST type_list` (`query_list.h:432`,
  `struct qfile_list_id`'s first field) already carries a `domp[]` array resolved once at list creation
  — the framing's per-column domain lookup uses this instead of any per-value type tag, eliminating the
  existing `QFILE_TUPLE_VALUE_HEADER_SIZE = 8` (`query_list.h:233-234`) per-value header (4B flag +
  4B length, `query_list.h:235-236`) for every bound-and-fixed-length column.
- 8B length prefix retained as the *default* framing overhead
  (`QFILE_TUPLE_LENGTH_SIZE = 8` = `QFILE_TUPLE_LENGTH_OFFSET`(4B, tuple_length) +
  `QFILE_TUPLE_PREV_LENGTH_OFFSET`(4B, prev_length for backward scan), `query_list.h:229-231`); the 4B

### 4.3 4B length-prefix — computed rejection `[P0-CONDITIONAL]`

grilled_plan.md D-G6.4: "4B prefix is subordinate to the volume number: only stays on the UG1 agenda if
class-(d) share × 4B/tuple is material; otherwise auto-reject." Computing the actual number, using the
one exactly-reconstructible tuple-size ratio in `[P0.2b]`'s data:

- `qdata_process_distinct_or_sort` (Q1, DISTINCT MOD(c_int,100) over the 50,000-row `vh_profile` fixture):
  **1,200,000 bytes / 50,000 tuples = 24 bytes/tuple exactly** — every input row is written once to the
  dedup buffer before the DISTINCT filter reduces it to 100 groups, so the tuple count is known exactly
  from the query's own row-count check (`[P0.2b] §9` table, "result `100`... over 50,000 rows").
- The 8B length-prefix (`QFILE_TUPLE_LENGTH_SIZE`, §4.1) is a fixed **4 of those 24 bytes**
  (`prev_length`, `QFILE_TUPLE_PREV_LENGTH_OFFSET`, `query_list.h:231`) — dropping it to the 4B variant
  saves exactly 4/24 ≈ **16.7%** of this site's own bytes, independent of tuple count.
- Extrapolating this 24B/tuple ratio uniformly across all measured class-(d) bytes (**`[VERIFY]`
  extrapolation** — the other 3 class-(d) sites in `[P0.2b] §9` are also narrow single/few-column
  aggregate scratch buffers of the same general shape, but their exact tuple counts were not independently
  reconstructed by `[P0.2b]`):
  - Total class-(d) bytes = 1,226,400 → ≈ 51,100 tuples → 4B-prefix savings ≈ 51,100 × 4 = **204,400 bytes**.
  - As a share of **total measured list-file write volume** (10,116,048 bytes): 204,400 / 10,116,048 ≈
    **2.0%**.
  - As a share of the **Q1+Q2-only denominator** (99.2% class-(d)-weighted mix, 1,236,024 bytes):
    204,400 / 1,236,024 ≈ **16.5%** — i.e. even under the *most favorable* (highest class-(d) share)
    workload-mix evidence on record, the 4B-prefix benefit is bounded by the same ~16.7% intra-class ratio,
    which translates to a ~2% whole-workload byte reduction once class-(d)'s own share of total volume
    (12.12%, §4.2) is folded back in.

**Conclusion: auto-reject the 4B prefix**, per D-G6.4's own rule — a ≈2% total-byte-volume reduction
(bounded above by ≈16.5% even under the class-(d)-favorable Q1+Q2 mix) is not material, and it is
strictly subordinate to §4.2's framing-exclusion recommendation itself (there is no 4B-prefix benefit to
capture if framing itself is deferred to B/campaign — the 8B/4B choice is a sub-parameter of the framing
design, not an independent lever). This auto-rejection is `[P0-CONDITIONAL]` on the same 12.12%/24B-per-tuple
evidence as §4.2, and reverses under the identical condition (§4.2's reversal clause) — if a
DISTINCT/GROUP-BY-heavy target workload reopens framing at UG1, the 4B-vs-8B sub-decision reopens with it
using the same ratio math above, re-scaled to the new workload's own measured bytes.

**Numeric-nit closing note (`[architect LOW: numeric nits]`, pre-UG1 review)**: this section states two
*different* ratios, not two roundings of the same number, and each is stated exactly once above with its
own derivation: **16.7%** = 4/24 bytes, the *intra-tuple* saving at the one exactly-reconstructible site
(`qdata_process_distinct_or_sort`: dropping the 4B `prev_length` out of 24B/tuple). **16.5%** =
204,400/1,236,024, the *whole-Q1+Q2-mix* saving share (full precision 204400 ÷ 1236024 = 0.165369…,
which rounds to **16.5%**, not 16.6%). `ug1-packet.md` §⑤ currently states this second figure rounded to
**16.6%** ("믹스 상한 16.6%"); re-deriving it here to full precision shows 16.5% is the more precise
rounding, and `ug1-packet.md`'s 16.6% is a minor rounding drift rather than a second independent
measurement. Per this task's instruction, **16.5% is the authoritative figure this document commits to**
(the number already stated twice above, self-consistently) — the peer owning `p1.3-proposals.md`/
`ug1-packet.md` has been notified via IRC to sync those documents to 16.5%. Neither number changes this
section's conclusion (auto-reject), since both are far below D-G6.4's materiality bar.
